**Q2：初回の候補は、固定したC0'由来の同式hard negative＋既存cosineを使う識別項、とする。**

負例選択は **C0'のGL上位Kを優先**する。今の採点器が実際に取り違える候補を使えるからである。真とのTanimotoは安価で構造的に近い候補を得られるが、MS/MSで難しい候補である保証はない。両方を学習・評価して良い方を採る設計にはしない。

K=7は初回の上限として妥当。速度試験で全同式候補のC0'採点が予算を超えるなら、例えば固定上限のTanimoto事前選別後にC0'上位Kを選ぶか、Tanimotoのみへ切り替える。そのルール・上限・同点規則を学習前に確定する。前者の場合、「全窓で最も難しいK」ではなく「事前選別集合での上位K」と記録する。C0'スコアの順位は観測スペクトルとCEに依存するので、初回は学習スペクトルごとに、そのCE/adduct/instrument条件のC0'得点で選ぶ定義が分かりやすい。

負例の作成には以下を要求する。

- 真と同じ `neutral_formula` の定義を用い、official keyで重複を除く。真の全alias・同一identity groupを負例にしない。互変異性・立体表記の違いだけを分類させない。
- 候補の構造からgraph・原子式・結合・fragment入力を作り直す。共有するのは観測スペクトル、CE、adduct等であり、真の分子のgraphやMAGMa断片を負例の分子入力として使わない。
- **負例も学習露出に数える。** 正例の2,000 identityが評価から除外済みでも、評価/locked/val/ranker接続用の保留identityを負例として学習すれば、そのidentityは学習未見ではない。正例と負例の両方を、公式key・全体共通groupで除外監査する。単に構造索引に存在することと、負例の損失として勾配を流すことは区別する。
- K未満なら実在する異なる負例だけを使い、paddingはsoftmaxの分母からmaskする。同じ負例の複製でKを埋めない。負例0の正例も再構成学習には残し、識別項を0とする。負例のあるidentityだけへ正例集合を縮めない。
- 正例・候補・観測スペクトルの対応、式、選択理由、C0' score、入力hashを固定し、学習途中にA3で負例を選び直さない。学習用の真を用いる選択は許容されるが、評価の真や成績で負例やレシピを選ばない。

損失は、初回からrunnerのentropy処理全体を微分可能に作り直すより、**既存 `inten_loss_fn` のcosine距離を候補ごとのscoreへ使う**案を推す。

`s_j = −cos_loss_sparse(pred_j, observed)`

`L_ret = −log(exp(s_true / τ) / Σ_{j∈{true, negatives}} exp(s_j / τ))`

`L = L_A2_positive + λ · L_ret`

ここで `L_A2_positive` はA2と同じend-to-endの正例再構成項である。初回はこの項を残す。識別項だけでは負例の予測スペクトルを悪くすることで学習が進む可能性もあり、絶対的な予測品質を保持する基準になる。各項をquery単位で平均し、Kが多いqueryの重みが勝手に増えないようにする。

一つの登録値が必要なら **τ=0.1、λ=0.1** を開始案にする。これは最適性が実証された値ではなく、固定した一候補の提案である。λの「小さめ」という曖昧な記述は残さず、A2のinten_weightを含む実際の式を明記する。学習前の少数batchで、両項・正例/負例両経路の勾配が有限かつ非ゼロであることと計算量を確認し、評価値からτやλを選び直さない。

**既存のGLACIERには、この接続のかなりの部分がある。** Sparkの学習用 `ms_pred/glacier/dataset.py` に `IntenContrDataset`、`joint_model.py:684–778` にtarget/decoyそれぞれのforward、正例の観測スペクトルを各decoyへ対応付ける処理、対照損失がある。この入力・collate・対応付けをまず再利用する。既存の対照損失そのものはSinkhornの順位確率＋閾値処理であり、上の通常のsoftmaxとは同じではない。`_common_step`全体をそのまま呼んで、登録していないfrag損失・schedulerまで混ぜない。新規性も「GLACIERへ初めて識別学習を導入する」ではなく、**このtimsTOFデータ・同式負例・更新範囲で識別目的へ適応すること**に置く。既存checkpointの学習履歴は、コードに対照分岐があることだけから断定しない。

cosineを採るなら、runnerのentropyとは異なる代理目的であることを明記する。既存の `entropy_loss_sparse` も、質量binへのcoalesceを使う実装で、runnerのcleaning、entropy weighting、0.01 Da/20 ppmのピーク対応と同一ではない。名前やdocstringだけで「本番スコアと一致」と扱わない。技術段階で同じ予測スペクトルを使って、損失とrunner得点の関係を学習側の小fixtureで調べる。実際の能力判定には変更していないrunnerのentropy得点を使う。

更新範囲は **inten_encoder / inten_decoder / output_mapのinten3を維持**してよい。CE符号化、graph/fragment側、元から非学習のparameterとbufferを固定する。これは強度の割当てを変える仮説であり、必要なfragmentが提案されない問題まで解くものではない。正例・負例の予測断片を使い、正解断片を教えて学習時だけ有利にしない。

**Q4：並行してよい。ただしGPUでは小さな成立確認を先にし、長い負例採点を無条件に最優先にしない。**
