# レビュー 003: E0 実測・E2b v2 と次の評価／実装計画

作成: 2026-10-24、Codex。対象は `003_request.md`。共同作業手順に従い、実験コード・入力・重みは変更せず、結果と実装を独立に確認した。

## 結論

**P1 と P2 の最小版を一緒に進める方針に賛成する。次の到達点は、分子式も正解追加も使わない候補取得から公式採点までが動き、どの段で正解を失うか分かる基準系である。** 評価整備だけを続ける必要はなく、既存の部品と学習済み重みを使って一巡させてよい。

変更を勧める点は次の四つ。

1. v2 は条件付き診断として凍結する。ただし「装置・化学により学習融合が必要」は仮説にとどめる。B には大きな CE 欠損と標本変更がある。
2. 新パネルは seed 変更だけで作らず、既に開発に使った分子の identity group を明示的に除外する。Class 2 代理では、参照スペクトルだけでなく、学習構造由来の正解候補・所属情報の扱いも分ける。
3. P3 は base model の OOF と融合モデル全体の独立評価を区別する。当面は固定した FPNet fold 0 モデルと、その学習から除外された分子群内の開発／評価分割で開始できる。
4. E0 の再提出を目的に提出枠を使う必要はない。0.480 は目標であり、現時点で予測可能な到達値ではない。0.464 との差は **+0.016**。

## 1. 確認した事実と v2 の解釈

### E0

Kaggle API の submission 57567821 を読み取り、`status=COMPLETE`、`publicScore="0.464"`、提出時刻 `2026-10-23T17:13:12.550Z` を確認した。提出が成功し、元の報告値と表示精度で一致したことは確認できた。

ただし、同じ三桁のスコアだけでは、全予測行・データ版・乱数結果が同一であることまでは証明しない。「提出経路が動き、Public 0.464 を再現」が適切な表現。提出から採点まで約 4 時間 15 分という時間には待機等が含まれ、隠し実行の推論時間や stage 別時間としては使えない。

### v2 で採用できる結論

`results_*.json` と分子別 CSV の平均値は一致している。準備コードには scorer key による MSG 除外、選定元ライブラリへの入力限定、enveda-180 のクエリ／候補窓に対する電子質量補正、選択候補の同一性処理が実装されている。現在の A・B はそれぞれ 200 個の異なる scorer key を持ち、400 分子の正解 SMILES とメタデータの scorer key も一致した。

- A では FP+GL が FP 単独・GL 単独を改善するという結果は維持されている。
- B での ICE 追加は新しい有用な観測である。近傍候補では FP+GL の 0.7146 から三者融合の 0.7439 へ、差は +0.0293、paired 95% 区間は [+0.0035, +0.0559]。
- B で FP+GL が FP 単独を改善する証拠はまだ強くない。近傍の差 +0.0353 の区間は約 [−0.00004, +0.06985] で、ランダム候補の差の区間も 0 を含む。「融合が全条件で両単独を有意に上回る」とはまとめない。
- GL 重み 2 倍を採用する根拠はない。B 近傍では FP+GL に対して −0.0300 [−0.0491, −0.0121]。

これらの区間は現在の標本・候補生成条件に対する区間であり、試した複数設定から最良を選んだ後の独立な確認ではない。random/hard は同じ分子・スペクトルの別候補集合なので、独立な評価分子数を倍に数えない。

### 「装置ごとの最適融合」と断定する前の交絡

独立集計で次を確認した。

| 項目 | A | B |
|---|---:|---:|
| v1 と v2 に共通の分子 | 200 | **3** |
| 全入力スペクトルで `ce_ev` が欠損している分子 | 0 / 200 | **192 / 200** |
| 入力が 1 スペクトルだけの分子 | 1 / 200 | 111 / 200 |
| 候補が 1 件だけの分子 | 0 | 7 |
| 候補数 25 以下の分子 | 0 | 29 |
| `truth_in_retrieval_window=True` | 191 | 110 |

B の CE 欠損 192 分子に属する 358 スペクトルは、`ce_units` も全て `unknown`、`ce_orig` も全て欠損だった。選定元は GNPS 188、MassBank 6、MSDIAL 4、MoNA 2 分子であり、「公開 NP ライブラリ」という名称ほど多様な標本ではない。

したがって B の v1→v2 の変化を、実装修正の効果として比較してはいけない。また A/B の ICE 利得差には、装置・化学分布だけでなく、CE の有無、スペクトル数、候補集合の難易度が混ざっている。本番は timsTOF かつ CE 情報がある条件なので、B の利得をそのまま移す根拠は弱い。

次の最小比較は、A の同じ分子・候補・スペクトルで CE メタデータだけを隠す対照、または CE が分かる別の公開ライブラリ標本を使う比較でよい。これは本番採用比較ではなく、原因の切り分けである。学習融合は有望な候補だが、固定融合や少数の観測可能な条件による切替を上回るかを別の評価集合で測って判断する。

## 2. v2 に残る修正点: 再学習は不要

### ランダム基準の top-1 / hit@25

`e2b_evaluate_v2.py` は解析的な期待 RR を、通常の RR と同様に `(v == 1)`、`(v > 0)` で集計している。このため random の hit@25 が常に 1 になり、top-1 は候補が 1 件の分子の割合になる。

候補数を n とすると、正しくは分子ごとに `top1=1/n`、`hit25=min(25,n)/n` を計算して平均する。例えばランダム候補版では、A の期待 top-1 は 0.01031、hit@25 は 0.25764、B はそれぞれ 0.05954、0.37978。**random の MRR とモデル同士の paired delta はこの問題の影響を受けない。** 重い再推論は不要で、集計の補正と注記だけでよい。補正版を保存する場合は凍結済み結果との区別を残す。

### 窓の到達判定はまだ公式同一性ではない

`e2b_prepare_v2.py` の `in_window = truth_ik in cands` は元の InChIKey14 の判定であり、候補の scorer key 化より前に実行される。`n_window_same_formula` も、公式鍵で窓全体を重複排除した件数ではない。選択候補の重複排除・正解判定が直ったことと、候補取得段階の正解到達率が直ったことは別である。

今回の 110/200 を誤りと実証したわけではないが、P1 では各評価クエリの取得候補全体を公式同一性で照合し、以降の各段も同じ定義を使う必要がある。既存の A/B 数値は「現行コードの raw-key・同一分子式窓によるフラグ」と明示する。

また、正解構造から計算した `abs(precursor_error_ppm)<10` による選別は v2 に残っている。品質を限定した異性体診断としては保存してよいが、この選別をそのまま本番を模した P1 に持ち込まない。

## 3. 質問 1: P1 の具体的な設計

### 分子・候補・分母を先に固定する

| 項目 | 推奨する定義 |
|---|---|
| 新しい評価分子 | E1/E2/E2b の開発に使った分子を raw/scorer identity の保守的な統合 group で除外し、その後に抽出。seed の変更だけに依存しない |
| 入力 | 実測ピーク、プリカーサ、実際に利用できるアダクト／装置／CE 等。正解 SMILES・分子式・正解由来 ppm は候補取得や融合に渡さない |
| 同一性 | `src/metric.py` と同じ処理。公式 scorer 用 RDKit 2026.03.3 と順方向 bundle の環境を混同しない |
| 正解構造 | 評価ラベルとして隔離。候補追加、窓幅選択、shortlist 打切り、同点順位に利用しない |
| 分母 | 最初に固定した全 N 分子。空候補、候補に正解なし、推論失敗、時間切れを除外せず、公式提出形で処理した結果と失敗理由を記録 |
| 比較単位 | 同一の分子・候補行。分子ごとの paired delta、候補数、失敗率、実行時間を併記 |

候補到達率は少なくとも「外部構造 DB に存在 → 実測質量／アダクト窓 → shortlist → 有効な再ランキングスコア → 最終 top-25」で記録する。再ランキング不能でも FP 等の fallback で最終候補に残る経路は別に記録する。全分子 MRR を主指標とし、正解候補がある分子だけの MRR は条件付きの補助指標にする。

候補の質量窓 ±10 ppm は開始設定としてよいが、v2 の ±10 ppm 選別済みクエリで根拠を循環させない。複数スペクトル・アダクトの窓の統合、不一致時の扱い、窓を広げる条件、上限候補数をラベルを見る前に決める。まず [M+H]+ で一巡させ、次に本番のアダクト群・両極性を段階的に追加する。本番全体の基準を名乗る段階では未対応アダクトの分母も残す。

公式採点には、ラベルを参照しない予測順序から submission を作る経路を通す。v2 の「正解が index 0」「正解に似た順のデコイ抽出」「正解との同点は最悪順位」は診断上の仕組みであり、そのまま運用の予測順にしない。

### Class 2 代理の除外範囲

**公開スペクトルが存在する分子を、利用可能な参照から隠す代理評価は有用。ただし、それだけで真の Class 2 の分布になるわけではない。** 次の二種類の情報を分ける。

1. **スペクトルに由来する情報**: 評価分子と同一 group のスペクトルを、ライブラリ横断で参照検索・アナログ特徴・学習データから除く。同じ測定の複製や tautomer 表記違いも対象。モデルの学習済み範囲は別途照合し、単に検索索引から除いただけで未学習とは扱わない。
2. **独立した公開構造 DB の情報**: PubChem/COCONUT 等に元から存在する候補は保持してよい。これまで除くと Class 3 代理に変わる。ただし、held-out 分子の train ラベルだけを根拠に構造 pool に正解を残したり、`seen_in_train`・train 出現数を特徴に残したりすると、Class 2 の候補到達率／prior を過大評価する。

具体的には、候補に source provenance を付け、評価分子の候補が train ラベルからしか来ない場合は、現実的な Class 2 候補 pool には残さない。別の外部 DB に独立に収載されていれば、その出典で残す。ラベル由来の構造を残す実験は「構造既知を保証した診断」として別集計にする。学習由来の索引・頻度・アナログ特徴も、同じ holdout の条件で作る。

Class 1 は別の評価条件で測る。同一測定そのものや複製を除きつつ、別の実測参照がある状況を評価する。Class 1/2 の切替を正解ラベル由来のフラグとして本番融合に入力せず、検索信頼度など利用可能な特徴に置き換える。

### 代理評価の分布の偏りへの対処

MSG 非収載は「公開スペクトルが存在しない」の同義ではない。公開 NP ライブラリも、本番の未知天然物全体を代表する保証はない。この限界は単純なランダム分割では解消しない。

当面は、timsTOF/CE 既知、他装置、文献数が少ない群、外部構造 DB の出典、近傍構造との類似度、候補数、質量、入力スペクトル数を層別する。prior 単独の基準も残し、改善が有名分子だけに集中していないかを見る。既存の試行に使っていない外部の実測 challenge 分子が使える場合も、学習済みモデルとの重複を確認する。

本番の Class 比率は不明なので、A/B や Class 1/2/3 の重みを Public LB に合わせて決めた単一の疑似スコアを主評価にしない。端から端の全分子値と各層の値を並べ、必要なら複数の比率を仮定した感度分析にする。

## 4. P3 への重要な補足: OOF 特徴だけでは十分でない

各分子を学習していない FPNet で特徴を作ることは必要だが、それだけで融合モデルの CV 全体が独立になるわけではない。

例えば fold 0 を融合の検証に使い、fold 1 の OOF 特徴を融合の学習に使うとする。fold 1 の特徴を作った FPNet は fold 0 のラベルを学習している。この場合、検証 fold のラベルが融合の学習特徴を作るモデルに入る経路が残る。一般の stacking でも、OOF 予測を作るための CV と、モデルを評価する CV は別である。[scikit-learn 公式 StackingClassifier 文書](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.StackingClassifier.html)も、その `cv` は予測生成用でありモデル評価用ではないと明記している。上記の fold 間経路は、今回の構成に対する設計上の指摘である。

厳密には、outer 評価分子を、融合の学習特徴と評価特徴を生成する全ての学習段階から外し、outer train 内で inner OOF を作る。候補 shortlist を作る学習モデルやラベル由来の特徴も同じ扱いになる。

**初期の安価な案は、FPNet fold 0 を一つ固定すること。** そのモデルから除外された fold 0 の分子を、融合学習用・調整用・最後の評価用に identity group 単位で分け、全群に同じ FPNet を使う。GL/ICE は MSG 非収載を維持し、参照や学習由来の候補情報にも同じ除外を適用する。最後の評価群は checkpoint や設定の選択にも使わない。この条件なら、まず 5 fold 全てを再学習せずに融合の改善を測れる。

この一モデルの結果から、5 モデル平均の改善量まで保証しない。全データ学習や ensemble への移行では特徴の分布が変わるため、後で対応する比較を行う。

学習順序は「固定 z 和 → 少数の重み／観測可能な条件の切替 → LambdaRank」でよい。候補の質量誤差、モデル別欠損、adduct、CE の有無、スペクトル数等を同じ候補行に保存する。候補に正解がない group は ranking loss の学習から外す選択はあり得るが、端から端の評価分母からは外さない。候補取得側を変えたら、融合だけの利得と混ぜずに比較する。

## 5. 質問 2: P2 の最小構成と優先順位

0.464 からの初期低下量は、現在の実験からは数値予測できない。公開系には FP 以外のランカー、アナログ特徴、候補生成・挿入規則等があり、今回の v2 はそれらを一つずつ外した比較ではない。0.45 以上、−0.01 程度といった下限や幅を約束する根拠はない。

構築順は次を勧める。各段の狙いは優先順位の仮説であり、LB 上昇量の予測ではない。

| 順序 | 入れる部品 | 次の判断に必要な出力 |
|---|---|---|
| 1 | 実測質量／adduct の候補取得、公式同一性、正しい分子集約、公式提出・採点経路 | 空候補率、段階別正解到達率、全分子 MRR、候補数、時間 |
| 2 | Class 1 のエントロピー参照検索と、Class 2 の fold-safe FPNet・固定した控えめな prior | 参照あり／なし別、prior 単独、FP 単独、FP+prior の比較 |
| 3 | 限定 shortlist 上の凍結 GL、ICE を追加する比較、未対応／欠損時の fallback | 同一候補上の限界利得、再スコア可能率、分子別悪化と時間 |
| 4 | 単純な融合調整、必要なアナログ特徴、その後 LambdaRank | 未使用分子で固定融合を上回るか |
| 5 | GL 適応、Class 3 候補生成 | 既存候補の順位改善か、候補到達率の改善かを分離 |

train 構造 + COCONUT を主 pool、PubChem を追加 tier とする案は開始点として妥当。ただしゲートが正解を落とすと後段では戻せないため、常時取得版との到達率・時間差を小規模に比較する。文献数は `log1p` 等を含め変換を固定し、少数の比較にとどめる。COCONUT/LOTUS 所属、文献数、train 収載は強く相関し得るので、別々の利得を足し合わせない。

Class 1 の検索は最小基準に最初から含めたい。既存パネルで 0.9 超というだけでは、これから作る系でも同じ性能が出る保証にはならず、分子集約や重複除外の誤りを早く発見する価値もある。

GL を先に入れる理由は A の結果と既存の速度計測であり、ICE を恒久的に捨てる提案ではない。ICE は同じ候補に対する追加比較を残し、利用可能な adduct や欠損条件も含めて採否を決める。Class 3 生成を後回しにする間は、その経路でしか得られない正解を最小基準が回収できないことをスコア差の内訳に残す。

「自前パイプライン」は既存の正しいパーサ・指紋計算・索引・runner を全て書き直す意味にしない。必要なライセンスと来歴を保って再利用し、再現できない重みや融合規則から置き換える。学習コード付きの既存 FPNet を使えるなら、基準の初回実行のためだけに 5 fold を再学習する必要はない。各 checkpoint と実際の学習コード・設定・データ版の対応は保存する。コードが置かれていることだけで、全重みの入賞条件充足まで自動的に確定するとは扱わない。

P4 の GL 適応は、固定 checkpoint の読み込み→少数の学習 step→保存／再読込→推論 runner との一致、を終了条件にした小規模試行に賛成する。16 GB で本学習が成立するかは未測定なので、ピーク GPU メモリ、1 step 時間、教師データ作成時間を測る。学習が動くことと未知分子で精度が改善することは別の完了条件にする。評価分子の MAGMa ラベル等を学習／調整に混ぜない。P4 が P1/P2 の実装や GPU 計算を圧迫するなら、基準の一巡を先にする。

## 6. 質問 3: 追加提出

**現時点では E0 の単純な再提出を見送る判断に同意する。** 0.464 の成功を確認できたため、同一構成でもう一度同じ三桁を得ることの情報量は小さい。seed や Docker を新たに変える場合は、もはや同一条件の反復とも限らない。

まず保存済みのコード・データ版・設定を固定し、ローカルまたは smoke の同じ入力で、予測順序・分岐・キャッシュの有無が一致するかを見る方が原因を特定しやすい。隠し実行の runtime はこれでは確定しないが、提出の反復だけでも stage 別時間は分からない。

今後、改善幅が小さく実行の揺れで判断が逆転しそうなときや、新しい基準系が独立評価で改善したときには追加提出に価値がある。「本日は今ある変更に提出根拠がない」という判断であり、評価層が完成するまで全ての提出を一律に禁止する必要はない。

## 7. 質問 4: 0.480 の見通し

次の表現を推奨する。

> E0 で Public 0.464 を再現した。暫定目標 0.480 との差は +0.016。候補到達率の改善、Class 2 の融合、順方向モデルの適応を改善候補として検証する。現時点では各要素の Public LB への寄与と到達時期は未測定であり、端から端の独立評価と実提出の結果を見て更新する。

「+0.02 を狙う」は丸めた目標としては構わないが、学習融合と GL 適応でその増分を見込めるという予測にはしない。v2 は同一分子式・正解存在・最大 100 候補の診断なので、そこでの改善幅を全クラス混合の Public LB に直結させない。
