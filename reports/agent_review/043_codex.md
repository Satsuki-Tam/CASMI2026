**Q4：生成物へ GLACIER を付ける第 2 段**

基準 DB 経路を完了・固定してから、別の上限付き処理として生成物を採点する設計を勧めます。

- 基準の shortlist、FP、GL 候補数・実行予算、GL 被覆率の分母、fallback 判定、正規化の母集団、最終順序を先に保存する。生成物を元の被覆率の分母へ足さず、元の候補の GL 枠も奪わない。
- 第 1 段の固定規則で生成物の上位 K を選び、別キュー・別時間上限で GL を付ける。生成の CPU 時間も総 deadline を消費するので、引数上の GL budget が同じだけでは基準経路が同一とは限らない。
- FP/GL を比較する共通尺度は基準 DB 側で固定する。生成集合だけで別々に z 化しない。GL 未対応 adduct、重い分子、NaN、timeout を最低得点 0 と混ぜず、未完了なら当該 query の追加段を見送り基準出力を保つなどの規則を事前に決める。
- forward のキャッシュ再利用は model・入力 SMILES・adduct・CE/proxy 条件が一致する場合に限る。official key が同じ tautomer でも、forward 入力が同じとは限らない。
- DB 基準の hash/順位・GL 実測被覆、追加候補数、追加段の完了/棄権、総実行時間を対照出力と照合する。候補を増やすだけで元の挙動が変わる実装は、一変更比較にならない。

dv1 が加点する既存 shortlist 候補には既に基準側の GL があるので、新規 forward は不要です。この第 2 段は追加候補の順位付けに集中できます。C3 代理で GL モデルの学習 identity が残っている場合は別記し、FPNet が未見という理由だけで全モデル未見とは呼ばないでください。

**Q5：実装・集計上の見落としと提出前の最低限**

v2 の主修正は確認できました。Spark での小さな CPU 例でも、置換糖の誤った質量の脱離生成物は除かれ、CC→CCOC は順序付き二段で生成され、`max_products=1` は 1 件以内でした。正解 hit と生成物の最終一意化は official key を使っています。次の点は残ります。

**(a) 新規/窓内の判定は raw key のままです。** 例えば `CC(=O)CC(=O)C` と `CC(O)=CC(=O)C` は raw key が YRKCREAYFQTBPV / POILWHVDKZOXJZ と異なり、公式標準化後は両方 YRKCREAYFQTBPV です。DB に前者しかなければ、後者を raw 比較で novel としてしまいます。また、同じ official key のより高い f·z の表記へ `smiles` を更新する際、保持した `rk` は更新されず、所在が先に列挙された表記に依存します。凍結 pipeline にも同じ処理があるため、両者の一致だけでは意味の正しさは検証できません。

最低限、実際に選択された gt3 生成物について、view で利用可能な窓の **official key** との重複数、raw/official 判定による選択・gate・出力の変化数を出してください。現版をそのまま比較する判断なら「raw-window 不在規則」であり、純粋な de novo の probe ではないと明記します。仕様を修正するなら frozen 版を黙って差し替えず、新しい hash で再評価します。dv1 は shortlist の official key 判定が先なので、この所在分類の問題からは切り離せます。

**(b) f·z parity max 7.28 は入力 logits の不一致とは限りませんが、gate に関わる差です。** 追記の「DB の fp は別表記の最大値、代表 SMILES の再計算はそれ以下」という説明はコードと整合します。しかし代表 SMILES 同士の比較が一致したという意味ではありません。gt3 の DB rank 3 の fp と生成側の f·z の最大化範囲を記録し、alias を持つ実例で evaluator と pipeline の候補・gate・公式 key 順位を比較してください。無作為 16 件だけでは 0.3〜0.6% の候補を含む分岐を検証できません。代表 SMILES の値へ一方だけ変更するのも別規則です。

**(c) 空の DB shortlist では生成物も評価せず全規則を 0 にしています。** 現在の p2dev/conf3/conffit/conffit2 の空行には生成物がなく、保存済みスコアへの影響は確認されませんでした。ただし次版で生成だけ可能な query が出ると見落とします。生成単独の出力を許すか、基準空なら棄権するかを評価器・pipeline で揃えてください。台帳にあるが feature/logit がない分子を `continue` で落とす経路も、将来の分母監査に含めます。

**(d) 二段編集は official identity で親自身へ戻ることがあります。** 小例では `C[C@H](O)C(=O)O` から、親と同じ公式 key の `CC(O)C(=O)O` が返りました。現在の「1〜2 段で導ける」という dv 定義なら直ちに誤りではありませんが、他構造からの新規誘導だけの信号とは言えません。実データでの頻度は未集計です。distinct-parent を要求するなら新仮説として比較し、今の dv1 に事後適用しないでください。

**(e) 確認の NP macro は run×層の平均です。** D と E が二つの run にあるため、C/F より重くなり、開発の C/D/E/F 等重みとは異なります。各層の identity を先にまとめ、4 層を等重みにした補助値は次のとおりです。

これは gk3 の層別失敗や dv1 の正の判定を変えません。登録値は残し、集計単位を明記してください。w3* も L と G の層重みを揃えた感度値としてのみ使います。hidden のクラス構成、C3 内での親の到達率、Public のクラス比を推定した値ではありません。c3n の親再選択も現状は検索上位 max(80,4P) 内で行うので、全参照を除外後に検索し直した上位 P とは区別します。
