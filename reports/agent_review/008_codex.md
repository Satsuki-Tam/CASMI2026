# レビュー 008: B1 v2 診断から次に試すこと

作成: 2026-10-24、Codex。依頼 008、診断文書、run1_v2 / run_c1_v2 の結果・分子別 CSV・特徴表、診断／評価／特徴生成コードを確認した。保存済みスコアで FP 重みの反実仮想比較と paired bootstrap を CPU 上で行った。実験コードの変更、GPU 推論、学習、提出は行っていない。

本レビューの数値は、A は GL+ICE 完了、B 二集合は評価結果に記録された **ICE 不使用**の状態に合わせている。B の ICE 復旧後は同じ比較を更新する必要がある。

## 1. 結論: 次の一手の順序

**FP を順位付けから外す案と、GL を窓全体へ適用する案は優先しない。まず、既存スコアでの参照規則の損益と、forward 前の shortlist 到達率を測る。並行して、実際の fit 分子数を確認した小さな学習融合を完成させる。**

推奨順は次の通り。

1. 下記の診断の分母・解釈を修正し、B は ICE 無しの fallback 診断として保存する。ICE 復旧待ちでも、候補到達率と既存スコアによる診断は進められる。
2. 参照優先なしを対照として保持し、libpri(0.8,0.2) を有力な候補として比較する。C2 損失上限を先に決め、直ちに提出既定値へはしない。
3. FP/FP+prior の各 shortlist 枝を広げる比較を、まず到達率・候補数だけで行う。改善がある枝の新規候補にだけ GL/ICE を追加する。
4. 完成した P1 v2 を含む fit 台帳を確認し、28 特徴の LambdaRank を基準に、小さな特徴追加を一つ比較する。
5. 負の参照証拠は「同条件の有効な参照が実際にある」フラグを追加した上で、弱い prior 減衰から比較する。FP の微調整はその後。

W7 の共通パイプライン評価と、固定した molecule/view 台帳はこの順序の前提として維持する。

## 2. 診断から言えること／修正が必要なこと

### 数値と分母

- 依頼表の A の S(2,1,0.15)=**0.584 は結果ファイルと一致しない**。保存済み CSV/Markdown は **0.66224**、S(0.5) は **0.67111**。prior 変更の差は約 +0.00886 であり、+0.087 ではない。
- `b1_diagnose.py` の 0.702 / 0.639 / 0.515 は、到達可能分子だけを分母にした **条件付き MRR**。全 N 分子の strict は 0.671 / 0.377 / 0.427。層別の n_query・窓サイズの表も、到達可能群だけの平均である。
- B の C1 診断にある 0.913 / 0.581 / 0.800 は、usable 72 分子のうち正解が shortlist にある **71 分子**の値。評価表の全 72 分子では 0.900 / 0.573 / 0.789 となる。採否には後者を使う。

### 未到達 41% は Class 3 比率ではない

run1_v2 B は 300 分子中、選定表で外部候補源に存在と記録されたものが 191、B1 の測定窓で到達したものが 177。未到達 123 件は、現在の記録では **候補源で未発見 109 件＋存在するが窓で未到達 14 件**に分かれる。run_c1_v2 は同様に **26＋25=51 件**。

前者も「今回の candidate store と照合方法で未発見」であって、PubChem 全体や全公開 DB に無いことの証明ではない。したがって、B の 41% を「どこにも無い」「Class 3 相当」として生成へ直結させない。候補源の不足・同一性・adduct/質量窓と、真に生成が必要なケースを分ける。

E0 の 0.464 から B1 の到達率≥0.6 も導けない。一般に MRR は予測候補の正解到達率以下だが、0.464 が与えるのはその提出の候補到達率≥0.464 という関係まで。E0 は候補源・生成経路・融合が異なる。

### 「責任項」と「改善可能件数」は別

診断の `c2_blame` は、既に外した分子について、現勝者と正解の **重み付きスコア差が最大の項**を選ぶ定義である。GL は重み 2 なので大きくなりやすい。この集計だけでは、GL を弱めるべきとも、prior を消せば直るとも言えない。規則を変えると別の候補が勝つ可能性がある。

B では誤り 59 件中、prior の差が最大なのは 20 件、その勝者が train 構造なのは 16 件。C1 集合の C2 条件では 120 件中 35 件、そのうち 24 件。**80% / 69% はその部分集合での所属割合であり、修正できる誤りの割合ではない。** 同 adduct 参照の有無・低類似度条件・変更後の新勝者まで調べる必要がある。

また A の「98%」は **誤った勝者が正解と同一分子式の割合**。shortlist 候補全体の同一分子式率ではない。到達かつ shortlist 内の分子について、候補の同一分子式率は平均約 0.787、中央値約 0.907 だった。Tanimoto が低いことも、scaffold が異なることと同義ではない。

単独モデルを一つだけ選ぶ oracle は、その選択方式の上限であり、融合一般の上限ではない。B で S が oracle を上回ることは矛盾しない。A の差を、そのまま LambdaRank が獲得できる +10pt と解釈しない。

## 3. Q1: libpri(0.8,0.2) を固定規則の保険にするか

**候補として残すことに賛成するが、無条件に「保険」と呼んで既定化することには反対する。** C2 には測定できる損失がある。

保存済み CSV から、S(2,1,0.5) との差を分子単位で再計算した。

| 集合 | C2 strict 差 | paired 95% 区間 | 悪化した C2 分子 | C1 平均差 |
|---|---:|---|---:|---:|
| A、300 分子 | −0.01917 | [−0.03056, −0.00917] | 13 | +0.20238（n=7） |
| B、300 分子、ICE 無し | −0.00747 | [−0.01461, −0.00183] | 7 | +0.21639（n=72） |
| C1 集合 B の C2 条件、ICE 無し | 0 | [0,0] | 0 | +0.18445（n=257） |

例えば C2 の許容損失を 0.01 と先に置くなら、τ=0.8 は現在の A ではその条件を満たさない。τ=0.9, margin=0.2 なら、点推定の損失は A −0.005、B −0.00406、C1 集合の C2 条件 0 に縮むが、C1 の利得も変わる。これは比較候補であり、τ=0.9 の採用を確定する結果ではない。

### 期待値最大化より、先に許容損失を置く

Class 比率を根拠なく一点仮定して期待値を最大化するより、**各 C2 層の損失上限 ε と C1 で求める利得を先に決める制約付き比較**を勧める。点推定だけでなく区間も見る。ε は業務上の選択であり、結果を見た後に条件を通すために広げない。

ただし、全ての Class 比率を許した厳密な minimax なら「全て C2」という場合もあり、C2 を必ず少し落とす参照優先は選ばれにくい。ε 付きの比較は、この完全な minimax と同じではない。どの程度の損失を許して C1 を改善するか、という意思決定として明記する。

### C1 内の偽確信率を全体へ移さない

margin≥0.2 まで含む実際の C1 集合内の件数は、B が **0/43**、C1 集合 B が **1/119**。0/53、1/147 は同じ条件の分母ではない。さらにこれらは C1 かつ正解が shortlist にある群であり、本番の全 query における誤昇格率ではない。

「真の参照類似度が 0.6〜0.8 なら正解率が高い」は、真が分かる条件での診断である。本番で使える `lib_max`、margin、adduct・CE・ピーク情報量で条件を切り、C1 と C2 の両方を評価して閾値を決める必要がある。

E0=0.464、公開 C1≈0.95、手元の strict 値から **C1 比率の正の下限は現時点では出せない**。C1 が 0 でも、他クラスの条件付き性能が 0.464 なら同じ LB が成立する。下限には、本番の他クラス性能に対する信頼できる上限等が必要で、ローカルの平均値はその上限ではない。007 の結論を維持する。

## 4. Q2: shortlist をどの枝から広げるか

shortlist 再現率を主要 ledger に加える案に賛成する。全 N 分母の損失と、窓到達後の条件付き再現率を両方出す。

| 集合 | 外部窓到達 → shortlist | 到達後 recall | 全 N 分母で shortlist が失う割合 |
|---|---:|---:|---:|
| A | 287 → 275 | 95.82% | 4% |
| B | 177 → 159 | 89.83% | 6% |
| C1 集合 B の C2 条件 | 249 → 216 | 86.75% | 11% |

「K≈120」は主に union 後の候補数であり、各枝の K と分ける。現行は FP 上位 100、FP+prior 上位 100、参照上位 20 の union なので、設定を一つの K=120 として扱わない。

最初に GPU を使わず、同じ窓・FP・prior のスコアで次を比較するのがよい。

- 基準: `k_fp=100, k_fpprior=100, k_lib=20`。
- prior 枝だけ拡大: `k_fp=100, k_fpprior=200, k_lib=20`。
- FP 枝だけ拡大: `k_fp=200, k_fpprior=100, k_lib=20`。

各案で公式 identity の unique 件数、正解到達数、回収した分子の文献数、最大候補数、CE/adduct を含む予測ジョブ数を測る。良い枝だけを拡大し、追加候補にだけ GL/ICE を実行する。必要ならその後に 250 や両枝拡大を比較する。

prior が B の再順位で効くことは、shortlist を逃した低文献数の正解も prior 枝で回収できるという証拠にはならない。どの枝で回収したかを記録して選ぶ。

GL を窓全体へ適用する案は後回し。6,000〜10,000 構造は現在の約 120 件の 50〜83 倍で、さらに CE/adduct ごとの仕事がある。例えば 400分子×8,000候補×3条件で 960万予測。仮に 100予測/秒でも一モデルで約 27時間となる。実際には重複 cache や batching に依存するが、9時間内の第一案にする根拠はない。

候補拡大後は「新たに正解が入った分子の利得」と「元から入っていた分子の順位変化」を分ける。候補が増えると z の分布も変わるため、到達率が上がっても MRR が必ず上がるとは限らない。全 N 分母での正味差と時間を採用指標にする。

## 5. Q3: LambdaRank の特徴と学習規模

### 約 190 group の意味を確認する

手元の run1_v2 の fit 部分を、現在の view・出典条件で数えると、正解を持つ学習可能 group は次の通り。

| 集合 | C2 group | C1 group | 異なる molecule 数 |
|---|---:|---:|---:|
| A fit | 92 | 2 | 92 |
| B fit | 56 | 31 | 61 |
| 合計 | 148 | 33 | **153** |

合計は **181 molecule/view group、153 独立 molecule**で、約 190 という数に近い。一方、P1 600 分子を取り込む本試験全体の母数とは異なる。確認時、ローカルには `run_p1_v2` はまだなく、P1 を含む完成した本試験の件数は確認できていない。追加 C1 集合を使う場合も別に数える。

候補行が数万あっても、独立な query が数万あるわけではない。まず source×identity×view×正解到達の台帳を出し、何を fit に読んだかを確定する。P1 v2 の取り込み後に特徴規模を判断する。

### 特徴追加は小さなブロックでよい

提案の margin、候補順位、最良との差、窓サイズは本番で計算でき、有望である。ただし、全てを一度に追加して大量のハイパーパラメータ探索を行うより、次の順が分かりやすい。

1. 現行 28 特徴、固定規則 S(0.5) を基準として確立する。
2. 各モデルの tie-aware な候補順位と query 内 margin、`log_n_window` の小さな追加版を比較する。
3. 改善があれば、最良との差や候補分子式ごとの競合数を別の追加として比較する。

`in_train × lib_sim` は木モデルが既存特徴から表現できる相互作用でもあり、追加必須ではない。浅い木で表現しやすくなるかを測る程度でよい。

「同一分子式候補数」は **各候補自身の分子式**を使って、その実際の候補集合内で数える。診断 CSV の `c2_n_same_formula` は正解の分子式を基準にした値なので、そのまま特徴に持ち込んではいけない。

### 現行 v3 特徴の具体的な注意

`rank_desc([0.5, 0.5, 0.2])` が `[1,2,3]` を返すことを確認した。同じ値に入力順で別順位を与えるため、同点候補の並び順が特徴へ入り込む。同点には同じ順位を付け、欠損は別フラグと合わせて扱う。順位特徴を入れる前に、行順を変えても対応する候補の特徴が同じになることを確認する。

単調制約は「無し」を対照に、FP/GL/ICE の代表スコア正・絶対質量誤差負の少数制約を一つ試す案に賛成する。確認した `MONO` は prior、PMID、SID、LOTUS 等にも正の制約を広げているが、これは質問の範囲より広い仮定である。まずそれらは外し、制約の効果を切り分ける。特に prior の誤誘導を調べている段階で、全 prior 成分の単調性まで同時に固定する必要はない。

## 6. Q4: 「参照があるのに似ていない」を負の証拠にするか

**有望な仮説だが、現時点で hard に prior を 0 にする規則を既定化しない。** 先に「本来比較可能な参照がある」を明示する必要がある。

`in_train=True` は同 adduct・同 polarity・十分な品質の参照が使えたことを意味しない。`lib_same=0` も、参照が無いのか、実際に比較した結果 0 なのかを区別できない。

最低限、次の特徴を用意する。

- 重複・MAX_REF 処理後の同 polarity / 同 adduct の有効参照数。
- 比較に使った query と参照の CE の有無・差、ピーク情報量。
- 比較可能な参照が無い状態と、比較できたが低類似な状態を区別するフラグ。

この条件を満たす候補だけに、例えば prior を 0.5 倍にする弱い版を一つ試し、変更なし／0.5倍／0 の差を同じ候補で測る。閾値 0.3 や減衰係数は tune 側で固定する。数値は初期比較案であり、採用値として確定したものではない。

閾値設計に C1 の正解類似度分布を使うこと自体は、開発・tune の範囲なら問題ない。ただし正解側の分布だけでは偽候補を抑えられるか分からない。実際に適用条件を満たす C1 正解、C1 偽候補、C2 偽候補の全てで、正解を失う件数・回収する件数・最終 MRR を測る。別装置・別 CE、参照の乏しい群を別に見る。

先に LambdaRank へこれらの情報を渡す案もよい。その場合も固定された弱い減衰版を診断対照にすると、学習器が何を使ったかを確認しやすい。最大寄与項の割合を、規則による修復率として報告しない。

## 7. Q5: FP の順位付けを外す、ensemble、微調整の順序

**まず既存スコアで重みを下げる対照を測るのが最も安い。ただし今回の再集計では FP 除去は悪化したため、現在の主基準には FP を残す。**

候補・GL/ICE・prior を固定し、`w_FP*z(FP)+2*z(GL)+z(ICE)+0.5*prior` の w_FP だけを変更した。w_FP=1 が保存済み C2 結果と分子ごとに完全一致することを確認した。B は依頼時の ICE 無し条件を維持している。

| 集合 | w_FP=1 | w_FP=0.5 | w_FP=0 | 0 − 1 の paired 95% 区間 |
|---|---:|---:|---:|---|
| A | 0.67111 | 0.64786 | 0.59360 | −0.07751 [−0.10409, −0.05116] |
| B、ICE 無し | 0.37704 | 0.37455 | 0.35437 | −0.02267 [−0.04439, −0.00189] |
| C1 集合 B の C2 条件、ICE 無し | 0.42748 | 0.42720 | 0.41221 | −0.01526 [−0.03825, +0.00777] |

B の w_FP=0.5 と 1 の差は未確定で、A は 0.5 でも悪化する。FP 単独の top-1 が低いことと、融合で価値がないことは別である。B の ICE 完了後にこの小さな比較だけ更新すればよい。

### 5 fold 平均

現行 fold 0 検証に、そのまま 5 fold 平均を使うのは不可。他の fold 用モデルが検証分子を学習しており、局所的な改善を未学習性能として読めない。

短期の部品診断なら、全モデルが学習から除外していることを確認した別集合を使う。パネル 250 分子を使う場合は、各 checkpoint の除外を確認し、007 の方針どおり FP 部品の開発診断に限定する。MSG 重複のある GL/ICE を合わせた統合性能の確認にはしない。

本番候補として ensemble を採用するには、共通の outer holdout を学習から外したモデル群、または全モデル未学習の外部評価集合が必要になる。既存の 5 fold を平均しただけで局所 CV が上がったことを根拠にしない。

### 天然物への微調整

中期案としては有望。ただし今回の B の弱さには化学だけでなく装置・CE 欠損・候補分布も混ざる。まず固定候補での重み／信頼度の使い方、query 前処理、CE 条件を切り分ける。自然物への微調整は fit group のみで行い、同じ holdout・候補到達 ledger で比較する。今すぐ full training を増やすより、shortlist の回収と完成した学習融合を先に測る方を勧める。

## 8. Q6: 診断で開発集合の eval 群まで見たこと

**現在の 300 分子全体を開発診断に使ってよい。既に開発集合とした eval_set 内の `eval` を、後から未使用に戻そうとする必要はない。** その結果を独立な最終確認と呼ばないことが重要である。

今後の役割は明示する。

- fit: モデルの学習。
- tune と既使用の開発診断集合: 規則・特徴・閾値の検討。全体を見て作った仮説は開発由来と記録する。
- seed 4 の locked: 設定・候補集合・モデル・欠損処理・採否基準を固定した後に、一度だけ確認する。

開発集合の一部を今後見ない運用は追加の規律にはなるが、過去の観察を無かったことにはできない。新しい特徴を多数試すなら、同じ tune での最高値を成功と見なさず、比較数を絞って locked に送る候補を先に決める。

W7 の機械的な一致確認と、性能の採否は分ける。locked の結果を見て閾値やモデルを変えた場合、その集合は開発側へ移すという 007 の規則を維持する。

## 9. ICE 復旧と次の比較表

確認した meta では A の両モデルは完了し、B は ICE が error、C1 集合 B も途中の採点分を持つ error だった。現在の B の報告は「ICE 無し fallback の診断」として整合しているが、完成版 B1 の重み選択にはまだ使い切れない。

CPU への計算移動後は、小さな共通例で positional encoding と最終スコアの数値整合を確認し、再利用 cache にコード・checkpoint・query の版を残す。`ice_resume.py` の status は少なくとも一つの値がある分子数を基準にするため、正常終了でも未対応分子があれば partial になり得る。一方、各分子に一つ値があるだけでは全候補の被覆を保証しない。

「処理が終わった」「対象として対応する」「候補スコアが有限」の状態を分ける。terminal な partial と実行中の途中 JSON を区別して凍結し、採点済み候補を使う場合は明示した fallback と被覆率で評価する。`status=ok` だけで被覆を断定したり、partial という理由で全ての有効値を黙って捨てたりしない。

次の一枚の比較表は、以下で十分。
