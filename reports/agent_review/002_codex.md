## 2 E2b の除外・入力・採点で修正が必要な点

### MSG 除外に少なくとも2件の漏れがある

`e2b_prepare.py` は MSG の `inchikey[:14]` と train の元の `inchikey14` で除外しています。train の前計算したスコアラー鍵を使って別表記を調べ、次の2件を MSG 本文の SMILES と照合しました。いずれも `src/metric.py` の `score` で1.0となる同一評価構造です。

| E2b の分子 ID | 一致した MSG の元の鍵 | MSG fold | 公式スコアラー鍵 |
|---|---|---|---|
| `MBOKSSYXJPVPOA` | `JCYNMRJCUYVDBC` | val | `MBOKSSYXJPVPOA` |
| `HLUCICHZHWJHLL` | `HNNSUZPWERIYIL` | train | `BEBLLQPTMVOKAX` |

2件とも B にあります。前者は少なくとも「MSG 非収載」ではなく、後者は MSG train に同一構造があります。実際のチェックポイントの学習対象リストとの照合は別途必要ですが、現状の除外では完全な非含有を主張できません。今回の探索は train 側で既知の対応表を起点にしたもので、MSG全構造を最初から正準化した全件監査ではないため、件数は「少なくとも2」です。

この2件を保存済み RR の集計から除いても、B の FP＋GL − FP はランダムで+0.0705、hardで+0.1376でした。したがって今回の補完性の観測を丸ごと捨てる必要はありません。まず、MSGの構造を公式の順序・バージョンで正準化し、train の対応表と照合して分割を修正してください。

パネルについても「236件がMSG収載、うち204件がtrain」と「236件全てを順方向モデルが学習済み」は異なります。train、validationによる選択への関与、test、チェックポイント独自の再学習範囲を分けて記録してください。

### A は入力を組み立てた後に純粋な timsTOF 集合ではなくなっている

分子の抽出は `enveda-180` に限定していますが、その後 `sp` を train 全体から元の鍵で再取得しており、出典の制約がありません。実際の runner 入力には次がありました。

- `CDJIRCXSFAACDZ`：選ばれた8スペクトル全てが Orbitrap。
- `FTEDMEJEEMGEJB`：Orbitrap 5本＋timsTOF 3本。

A の入力は計703スペクトルで、13本が Orbitrap でした。前者は timsTOF の転移能力を測るクエリではありません。A の観測入力は `enveda-180`／timsTOF に制限したまま取り出してください。B にも timsTOF と他装置を混ぜた分子が1件あります。取得元のライブラリと、実際に入力したスペクトルの装置・出典を別々に残すと追跡できます。

`spectra_by[mid][:8]` は先にプリカーサ質量順にした先頭8本なので、CEの網羅や品質を基準とした選択でもありません。固定して比較するには使えますが、本番の複数スペクトル統合を評価する段階では、ラベルを使わずに再現できる選択規則へ揃えてください。

### 評価側でラベル由来の品質フィルタを使っている

分子抽出前とスペクトル取得後に `abs(precursor_error_ppm) < 10` を使っています。この値は正解構造がない本番では算出できません。テスト自体にも整合性に基づくクリーニングはありますが、その条件がこの10 ppmの一律フィルタと同じとは確認できていません。

特に丸め精度の違うライブラリで選択が変わります。B は実際に GNPS 173、MS-DIAL 11、MoNA 8、MassBank 6、RIKEN 2分子でした。GNPS等の所属だけで全てを確認済み天然物と呼ぶことも避け、「これらの公開ライブラリ由来の分子」としてください。

今の集合は高精度・H+に限定した診断として保存し、新しい評価集合はクエリを先に固定してください。品質条件を設けるなら、理由と除外率を出典別に記録し、既存の数値を後から別の母集団の性能として扱わないことが必要です。

### 候補の同一性と正解判定が公式方式に揃っていない

候補は raw InChIKey14 で重複排除され、`e2b_evaluate.py` と `e2b_fpnet_score.py` は「配列の0番だけが正解」として順位を測っています。同じ公式鍵の互変異性体が他の候補にあれば、それも公式では正解です。逆に重複候補が残れば順位や候補数が変わります。今回の正解400構造だけでも、元の鍵からスコアラー鍵が変わるものが Aで1、Bで12ありました。

正解・全候補・除外集合を公式鍵で揃え、候補一覧の重複排除と公式 MRR の照合を行ってください。truth-first の配置自体は現在の「同点を正解に不利に処理する」関数では楽観的な tie-break になっていません。ただしこれは公式提出の実際の同点順とは異なる保守的な評価です。運用と共通の決定的な同点処理を使うか、同点の期待値を診断として併記するのが適切です。

推論の欠損が主要因だった形跡はありません。保存された8実行は全て `status=ok`、各200分子を処理済みです。ICE の B で候補1件の失敗が random／hard にありましたが正解候補ではなく、GL は各候補を採点できていました。今後は z 変換で欠損を0に置く場合も、有効スコア率と欠損フラグを明示してください。

## 3 Class 2 の開発指標としての位置付け

**E2b は「分子式と正解候補の存在を与えた異性体識別パネル」として採用できます。Class 2 の端から端までの評価としては使えません。** oracle 条件を明示した部品比較は有用です。次の二層を並行して持つことを勧めます。

| 評価 | 固定する条件 | 判断できること |
|---|---|---|
| 修正した E2b | 正解分子式、正解を含む固定候補、公式同一性 | FP・GL・融合が同じ異性体をどう識別するか |
| 実運用に近い追加評価 | 実測プリカーサ＋アダクトから取得、正解分子式なし、正解の強制追加なし、正解の参照スペクトルを除外 | 質量窓→shortlist→再ランキング→top25 のどこに失点があるか |

`truth_in_pubchem` は現在「この版の tier の、測定質量窓かつ正解分子式の候補に、raw key で正解があるか」です。PubChem 全体への未登録を判定したものではありません。名前を `truth_in_retrieval_window` 等にして、窓外、tier未収載、標準化差、真の未登録を混同しないでください。電子質量の補正はスペクトル側では enveda-180 にだけ適用されており適切に限定されていますが、候補窓の `r.prec` は補正前の値です。同じ中性質量計算をクエリと候補取得で共有する必要があります。

正解の強制追加は Aで9件、Bで75件でした。また B には候補が正解1件だけの分子が5件、候補25件以下が18件あります。これらを含む絶対値を候補100件の性能として説明しないでください。可変候補数を使うならその分布と、競合候補のある部分集合を併記します。ランダム順位の期待 MRR は解析式 `H_min(n,25) / n` で計算でき、今回の A は0.039318、Bは0.088044です。

B の保存値を元の候補窓への正解の有無で分けると、効果の見え方も変わります。

| B の条件 | 分子数 | FP | GL | FP＋GL |
|---|---:|---:|---:|---:|
| random・窓に正解あり | 125 | 0.6543 | 0.7463 | 0.7950 |
| random・正解を追加 | 75 | 0.9369 | 0.7809 | 0.9004 |
| hard・窓に正解あり | 125 | 0.3998 | 0.5692 | 0.6087 |
| hard・正解を追加 | 75 | 0.8528 | 0.7040 | 0.8702 |

これは追加された正解の群がかなり異なる難易度を持つことを示します。原因を一つに断定はできませんが、正解を追加した診断と実際に検索できた構造の順位付けは分けて見る必要があります。

Tanimoto上位99は有用な難例ですが、正解構造を知って選んだデコイです。実運用では FP／prior／ライブラリ等が高く誤評価する候補が競合になるため、次は凍結した第一段階が選ぶデコイや、モデル間の順位が食い違う候補でも比較してください。大きい候補集合のうち99件への順位は、全数への順位を保証しません。候補100件への z 正規化も、数千件や最終40件での z 正規化と同じ尺度にはなりません。

MSG非収載条件は、MSG学習モデルの未見性能を調べるための条件です。Class 1 の検証まで常に同じ制約にする必要はありません。また E2b の分子は競技trainには公開スペクトルを持つため、Class 2 を模したモデル評価であり、実際の公開スペクトルの有無による Class 2 そのものではありません。複数シナリオを未公開のクラス比率で機械的に合算しない方針は維持します。

## 4 数日間の投資順序と GLACIER 適応の実現性

提案の順序を次のように変えることを勧めます。

1. **評価・データ来歴の修正と凍結。** 上記の公式同一性、MSG除外、観測装置、分母を直す。今回の400分子は既に設定比較に使った開発集合として残し、次の採用判断には未使用の分子集合を確保する。将来の fine-tuning に評価分子の別ライブラリ測定まで混ぜない。
2. **学習コード付きの既存 FPNet と、凍結した GL を使う基準系。** 公開キットの実際の学習コード・入力・除外リスト・checkpoint hash を確保する。来歴が満たされるなら、入賞要件のためだけに同じ5 foldを再学習する必要はない。自前変更は1 foldで比較し、有望なら広げる。full1の置換だけで、既存ランカーや中間学習表の再現性まで解決したことにはしない。
3. **実際の shortlist 上で候補・特徴・欠損を揃え、融合／ランカーを比較する。** FP、GL、ICE、参照類似度、priorと欠損を同じ候補行で持ち、実行時と同じ範囲で正規化する。小さな固定の融合を基準にし、十分な分子数の OOF 特徴を得てから LambdaRank に進む。これを GL の大規模学習より先に置く。
4. **GL 適応の小規模試行。** 実行可能性の確認は優先してよいが、最初から全件・全fold学習へ進まない。採用判断は GL単独のスペクトル類似度だけでなく、固定した候補と融合系での MRR 差で行う。
5. **生成経路。** 上の評価系を使い、生成候補の正解回収と既存正解の押し下げを測る。下位枠でも既存候補を置換すれば MRR は下がり得るため、下位挿入を無条件に安全とは扱わない。分子式推定が誤る場合も含める。

GL の timsTOF 適応・対照学習は合理的な研究仮説ですが、現在の結果は「既存 GL が FP にない情報を持つ」ことを示しており、「その情報を最も安く増やせるのが GL の再学習」とまでは示していません。A/Bで化学と装置が同時に変わるため、差を装置の効果だけに帰すこともできません。

実現性については、現在の Kaggle bundle は推論用の部分配布です。ローカルの `glacier/src/ms_pred/glacier/` は `dataset.py` と `joint_model.py` のみで、LICENSE-NOTICEにも推論に必要なモジュールだけの配布とあります。原著側には `train_joint.py`／`train_contr_joint.py` があり、後者は MAGMa の `magma_tree_with_inten.hdf5` やデコイ入力を要求します。推論用の DGL／LinSATNet 等の代替実装で学習まで再現できるとは限らないため、重みに対応する版の上流コードで学習経路を確認してください。[上流の対照学習コード](https://github.com/coleygroup/ms-pred/blob/main/src/ms_pred/glacier/train_contr_joint.py)

bundle が参照する commit `708148c2a8eb0c32120644436fefd2fe90cd2214` の README は、標準の GL 学習に24GB以上のGPUを2枚使う構成を記載しています。16GBで小さな fine-tuning が不可能という意味ではありませんが、推論の小さいメモリ使用量から学習の所要資源は推定できません。[対応版の README](https://github.com/coleygroup/ms-pred/blob/708148c2a8eb0c32120644436fefd2fe90cd2214/README.md#glacier)

最初の試行は、対応checkpointの読み込み、正しい教師データ作成、少数の正例・負例で有限の勾配と更新、保存・再読み込み、Kaggle側での推論一致までを確認する範囲にしてください。その実測から、バッチ・負例数・更新する層を決めます。検証する因子は「timsTOFデータでの適応」と「対照目的」の二つなので、両方を同時に変える前に、基準／適応のみ／対照学習を加えた版を区別できるようにするのがよいです。必要なら断片検出部分を固定して強度側から試す案がありますが、これは未検証の軽量化案です。

原著でも対照学習の利得は分布内で大きく、MassSpecGymでは小さいと述べています。表1では mass検索が69.69→69.95%、formula検索が48.49→49.88%です。NISTの大きな改善幅をそのままCASMIへ期待しないでください。[GLACIER 表1・§4.2.5・付録E](https://arxiv.org/html/2606.29161v2)
