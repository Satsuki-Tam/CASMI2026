# レビュー 009: locked 開封前の最終確認

作成: 2026-10-24、Codex。依頼 009、008 判断記録 §5、診断文書 §9〜§11、実行チェーンと評価／提出コードを確認した。ローカル未同期の開発結果は Spark 上の指定された開発用ディレクトリから読み取り、保存済みモデルによる CPU 再採点も行った。**locked のデータ・予測・採点結果は開いていない。** 学習・GPU 実験・提出・ジョブの変更は行っていない。

## 1. 結論

**M1 は事前登録の plain v2 を維持し、M2 は拡大 shortlist 上で再学習した plain v2_noice とする案に賛成する。ただし、現状のまま locked を自動開封することは勧めない。**

理由は追加の手法探索が必要だからではなく、次の具体的な不一致が残るため。

1. locked 評価器が M2 の 25 特徴に対応しておらず、既定の 28 特徴を渡す。
2. W7 の評価用マスクが、特徴表作成時と同じ参照環境になっていない。
3. GL 予算と GL 未計算時の fallback が、計画の説明と提出コードで違う。
4. 自動チェーンが前段の失敗でも完了印を出し、開封直前にも変更可能な `origin/main` を取り込む。
5. 採用規則が C1 の損失を制約せず、実測されていない「M2 の方が速い」を tie-break に使う。

この点を開発データ上で直して両候補を固定すれば、さらに新しい変種を増やさず、予定した一回の locked 比較へ進める。

## 2. 開発結果の独立確認

Spark の `rank_results.json` とモデルを読み、開発集合の既使用 eval 群に対する予測を再計算した。保存された C1/C2 平均と一致した。M2 用の新 shortlist で学習する `rank_v3` は確認時点では未完成だったため、その性能は本レビューでは判断していない。

### plain / noice / 単調制約の直接 paired 比較

次は各モデルと同じ固定規則との差ではなく、**同じ query 上で plain v2 との差を直接計算したもの**。

| 比較 | C2 strict 差、N=300 | paired 95% 区間 | C1 差、N=106 | paired 95% 区間 |
|---|---:|---|---:|---|
| v2_noice − plain | −0.00010 | [−0.01774, +0.01739] | **−0.04700** | **[−0.08559, −0.01131]** |
| 単調制約 − plain | +0.00075 | [−0.01448, +0.01619] | +0.01094 | [−0.02013, +0.04221] |

この結果から、単調制約へ差し替える明確な根拠はない。ICE 無しは C2 で同じ程度の点推定だが、性能が同等と確定したわけではなく、C1 には測定された低下がある。ただし、これは旧 shortlist 上でそれぞれ選択された学習器の比較であり、拡大 shortlist で再学習する M2 の損失量をそのまま予測するものではない。

### 母数・版の訂正

- JSON の C2 平均は空候補を含む **N=300**。一方、`eval_delta` の bootstrap は候補行を持つ **N=297**で計算されている。plain の全 N の差は `0.524616 − 0.450069 = 0.074546`、保存された delta は 0.075299。大きな結論は変わらないが、点推定・区間を同じ台帳へ揃える。
- 「1,492 分子」は fit/tune/eval 全体の候補行を持つ分子数で、fit だけの母数ではない。保存 JSON の実学習に使った正例あり molecule/view group は **884**、行数は 105,194。
- 確認した現在の plain `rank_v2` は **leaves=15、lr=0.1、100 round**。依頼の 300 round と異なる。M1 を名前だけでなく、実際のモデル hash で固定する必要がある。

## 3. 開封前に直す実装上の条件

### 3.1 M2 の特徴 schema

`v2_noice` は `z_ice / ice / ice_missing` を除いた 25 特徴であり、保存モデルも 25 特徴を持つ。確認した `b1_locked_eval.py` は `feature_matrix()` に `feats` を渡していないため 28 列を作る。

提出パイプラインと同じくモデルの feature names を読み、**名称・順序・列数を照合して**行列を作る。列数のチェックを無効にして通してはいけない。M1 を先に採点してから M2 でエラーになることを避けるため、両モデルのこの確認を開発 fixture で完了させてから locked へ進む。

### 3.2 W7 は「完走してスコアが出た」だけでは完了しない

現行の `make_eval_test.py` は対象全分子の正解 identity を一つの `exclude_identities_c2.json` にまとめ、パイプラインは全 query にその global mask を使う。一方、`b1_features.py` の C2 は基本的に現在の query の正解を隠す。これでは、別の評価分子が decoy/reference となる場合の世界が異なる。

C1 も、特徴表側は正解の選定元ライブラリの参照を除くが、パイプライン側の `exclude_rows_c1.json` は抽出した query 行を除く方式である。どちらを採るかを決め、同じ reference ledger を両経路に渡す必要がある。

さらに、評価用 test は raw train のピーク・precursor をそのまま書く一方、特徴表側は enveda-180 正モードの電子質量補正を行う。学習データを test 形式へ変換する段階で、入力の規約・dtype を共通化し、二重補正も避ける。

まず 20〜50 分子で、query、参照マスク、候補 official key、出典、shortlist、特徴、保存済み forward スコアを使った top-25 が一致することを確認する。global holdout へ統一する場合も、それ自体は有効な設計だが、同じ環境で作った特徴を学習・評価に使う。

### 3.3 台帳・固定保険・直接比較

locked 評価器は `--eval_csv` を受け取るが、確認時のコードでは評価対象を `M.index` から作っている。最初に凍結した molecule/view 台帳を分母とし、欠落は 0、意図しない query 欠落は監査に出す。M1/M2 の C1 台帳も共通にする。

登録された保険は `libpri(0.9,0.2)` 付きだが、現在の locked 評価器の固定出力には libpri が入っていない。保険を評価対象にするなら、その実際の規則を登録して採点する。旧判断記録に残る「τ=0.8/0.9 を locked で比較」と、§5 の τ=0.9 固定も一本化する。

M1/M2 の比較は、同じ分子の公式 RR を結合して **RR(M2)−RR(M1)** を計算する。それぞれ異なる shortlist の固定規則との差を、M1/M2 間の差の代わりにしない。

### 3.4 自動チェーンの失敗時動作と凍結

`spark_post_chain2.sh` は W7 や学習の終了コードを表示するが、その後も処理を続けて完了印を出せる。`spark_v3_chain.sh` も同様に、成功を保証しないまま後段の待機条件を満たし得る。

各段の終了コード、必要成果物、モデル schema、parity の合格を確認した場合だけ次へ進むようにする。開封前に M1/M2 両方が準備済みであることを一つの manifest で確認する。

開封直前の `sync_code()` が任意の最新 `origin/main` を checkout する方式も凍結にならない。code commit、モデル、候補・query 設定、feature names、scorer、forward 出力、fallback と予算の hash/設定を固定し、その版だけを使う。これは追加のモデル選択ではなく、一回の比較を成立させるための条件である。

## 4. Q1: M1 と M2 の構成

**M1 は plain v2 維持を推奨する。M2 も、拡大 shortlist に対して再学習した plain v2_noice を第一候補とする。**

単調制約版は C2 約 +0.0008、C1 約 +0.011 の点推定だが、直接比較の区間は両方 0 を含む。現時点で候補を増やしたり、直前の差し替えを行ったりするほど強い根拠ではない。

開発集合の eval 群は既に開発扱いなので、そこで 4 変種を比較してから locked 候補を決めること自体は許容される。事前登録の変更も、locked を見る前に理由・版を記録するなら可能。ただし開発上の選択バイアスは残るため、その最高値を独立性能と呼ばない。今回は差し替えない判断の方が単純である。

M2 の `rank_v3` は、既存の `rank_v2_v2_noice` をそのまま載せ替えるものではない。拡大後の候補・z 分布で学習し、開発集合の結果とモデル hash を記録したものを M2 として固定する。

## 5. Q2: ICE の扱いと上位 25 件だけの再採点

ICE を外して GL の候補を増やす M2 は、計算配分として試す価値がある。ただし「固定規則で小差だから ICE は不要」とは言わない。学習器同士の現在の比較では C1 に低下があり、主目的を C2 に置く場合もその損失を監視する。

上位 25 件だけ ICE を計算する案も有望だが、**今回の locked に第三の候補として追加せず、次の独立した二段階方式として扱う**ことを勧める。

設計上は、先に固定した no-ICE の規則／モデルで対象 25 件を選び、その選択を本番でもそのまま再現する。開発では既存の full ICE スコアを対象外だけ欠損にすることで、GPU を回す前に部分被覆を模擬できる。

全 shortlist の ICE z と、選択された 25 件内の z は別である。対象外を単に z=0 にして full-ICE モデルへ入れる方法は、平均スコアを観測したことと未計算を混同する。次のどちらかに定義を絞る。

- 選んだ top-25 の位置だけを ICE で再順位付けする。top-25 外の正解は回収できないが、挙動が明確。
- 「ICE を計算したか」と欠損理由を特徴にし、同じ選択マスクで学習した二段階ランカーを使う。fit の第一段選択には OOF または固定規則を使い、学習 query だけ第一段が有利になることを避ける。

候補数に比例した削減に加えて起動費・CE 条件・cache があるため、25/全候補数だけで wall time は決まらない。実ジョブ数と最終 MRR の両方で判断する。

## 6. Q3: 拡大 shortlist で追加して見る指標

予定している「新たに正解が入った分子」と「元から入っていた分子」の分解に賛成する。加えて次を保存したい。

- 同じ公式 identity での旧→新候補の所属と、各枝の増分。候補集合が本当に包含関係にあるか。
- 新規回収群の到達率だけでなく、最終順位・MRR・forward 被覆。既存群の悪化との正味差。
- query ごとの候補数と予測ジョブ数の中央値・95% 点・最大。平均 230 件だけでは予算を決めない。
- C1 の参照正解が押し下げられた件数、低文献数群、負モード／未対応 adduct の値。
- 実際の予算打切りを入れた値と、全 forward 計算を終えた理想状態の値。

監査の到達率からは、おおむね A 8 分子、B 11 分子、C1 集合 B 17 分子が新たに shortlist へ入る見込みである。仮に新規回収分子を全て 1 位にできても、その成分だけの全 N 分母の利得は約 +0.027 / +0.037 / +0.057。既存群の順位変化は別に加わる。到達率の伸びだけで、M2 の最終利得を予測しない。

候補上限を安全策として後から入れる場合も、監査の包含関係が崩れ得る。上限値と切り捨てる枝の順序を含めた構成を、M2 として開発・locked の両方で評価する。

## 7. Q4: locked の採用規則

**「C2 が高い方、差<0.01 なら M2」だけでは不十分。C1 は比率不明だからこそ、少なくとも損失制約として扱う。**

提案する規則は次の形。

1. 両候補が、同じ query/view 台帳、公式 scorer、同じ実行資源制約で比較可能な状態にあることを先に確認する。
2. C2 は A/B 別の paired 差を主に確認する。必要なら等重平均も使えるが、それは 1:1 の開発上の効用であり、本番構成比の推定ではない。
3. M2 に許容する C1 損失幅 ε_C1 を開封前に数値で登録する。例えば 0.02 を許容幅とするなら、それを超える悪化がある M2 を、C2 の小差だけで M1 の置換としない。保護を統計的に確認したと述べるには、下側区間も −ε_C1 を上回る必要がある。
4. C1 と各 C2 層の保護条件を満たした候補間で、C2 の差が 0.01 未満なら **実測で短い**方を速度優先で選ぶ。点差<0.01 だけで性能同等と宣言しない。
5. 区間が広い、または A/B/C1 が異なる方向なら「勝敗未確定」として M1 と M2 を別の失敗傾向を持つ候補として保持する。開封後に ε や重みを広げて勝者を作らない。

0.02 は統計から決まる値ではなく、ここで提示する許容損失の案である。現在の no-ICE 旧 shortlist 比較では C1 −0.047 なので、C1 を無視する規則は実際に選択を変え得る。拡大後の M2 がこれを回復するかを確認したい。

保険の固定規則を最終候補へ昇格する条件も、開封前に一覧へ入れる。M1/M2 の主出力、固定保険、比較用対照の役割を曖昧にしない。

### 開封後の改善

開発を続けることは問題ない。ただし、locked が確認したのは凍結した M1/M2 だけである。v3 の派生に同じ保証は引き継がれない。派生を最終候補にするなら、新しい未使用集合で確認するか、独立確認がないことを明示する。

旧 locked を繰り返し参照しながら調整すれば、その時点で開発集合になる。「一回使い切った後は、新手法を開発結果と LB だけで選んでも locked 済み扱い」という運用にはしない。

## 8. Q5: 時間予算と fallback

### 実時間の見積もりを修正する

GB10 の 140 jobs/s の 1/3〜1/4 を T4 の仮定にすると、約 35〜47 jobs/s。50〜70 万ジョブは **GL だけで約 3.0〜5.6 時間**であり、3〜4 時間とは限らない。400×230×8 は 73.6 万で、35 jobs/s なら約 5.8 時間。これに CPU、起動、出力の時間が加わる。

そもそも候補×スペクトル本数は概算で、CE/adduct の bucket と cache により実ジョブ数は変わる。runner が作る unique job を数え、代表例と重い側で時間を測る。GB10/T4 比だけで 9 時間内を保証しない。

**確認した提出コードの GL_BUDGET は依然 4,000 秒**。上の速度なら約 14〜19 万ジョブ相当で、50〜70 万全件を計算する構成ではない。ICE をスキップしても、この定数は自動では増えない。

GL 予算は global deadline、CPU 段終了時刻、出力に残す時間から計算する。予算、分子の実行順、候補上限、打切り時の規則までをモデル構成に含めて固定する。全件 forward がある locked 値だけで、4,000 秒で打ち切る提出を承認しない。

### S(1,0,0.5) は FP+prior だけではない

現在の記法は `S(w_GL,w_ICE,lambda)` で、FP の係数は 1。従って **S(1,0,0.5) は FP+GL+prior**である。診断文書の「FP+pop だけでも A 0.664」という説明は誤りで、この値には GL が入っている。

保存済み v2 候補で、forward を全て外した `z(FP)+0.5*prior` を再計算した C2 strict は次の通り。

| 集合 | FP+prior のみ |
|---|---:|
| A | 0.41049 |
| B | 0.24717 |
| C1 集合 B の C2 条件 | 0.25617 |

これは M2 拡大 shortlist の値ではないが、GL が無いときの低下を小さく見積もってはいけないことを示す。fallback は曖昧な S 記法でなく、使用する項を明示する。

### 現行コードは GL 未計算だけでは固定規則へ戻らない

`b1_pipeline.py` は `booster is not None` なら、GL が全欠損でもランカーを呼ぶ。固定規則へ戻るのは主にモデル不在／推論例外時であり、計画の「GL 超過分子は FP+prior で埋める」と一致していない。

GL の必要被覆を満たさない query には、事前に固定した fallback を明示的に選ぶ。その fallback が FP+prior＋参照規則なら、そのまま開発集合で GL を欠損させて測る。全欠損に対して未検証のランカーを使い続けない。

最低限の運用条件は、CPU を含む全体 deadline、途中成果の保存、モデル別・query 別の終了／未対応／失敗／予算切れの区別、常に全 molecule の出力を完成させる経路である。候補数を抑える場合は、後付けの切捨てでなく、開発・locked で同じ cap と枝順序を使う。

## 9. Q6: LB の読み方

E0 と E4 が表示上ともに 0.464 という報告からは、丸めた Public score の正味差を観測しなかったことまで言える。予測が同一、各分子への効果が 0、P1 が無効、とまでは言えない。

B1 と E0 は候補取得・重み・参照処理・生成経路等が異なるため、LB 差を LambdaRank の寄与として読まない。Notebook 版、モデル hash、候補・予算・fallback が、ここで凍結した M1/M2 と同じかを先に確認する。

また **A の固定 0.671 に、学習の +0.075 を足して本番の見通しを作らない**。+0.075 は A/B/C1 検証用 B の開発 eval 三群を混ぜた値で、固定対照は 0.450。再採点した plain の C2 は、A eval 100 分子で 0.73746、B eval 100 分子で 0.35279、C1 集合の C2 eval 100 分子で 0.48360 であり、分布ごとの違いが大きい。

±0.02 を事前に決めるなら、**追加調査を始める運用上の閾値**として使う。「有意差の閾値」とはしない。Public の N、分子別 RR 差、対象の構成比が不明なので、一定の score 差だけでは統計的な確実性は決まらない。小差でも採点値としては差であり、大差でもコード・被覆・対象集合の違いが原因になり得る。

保存するのは、同じ実行の learned / fixed 出力、候補・モデルの被覆、fallback 数、最終行の変化、実時間、artifact hash。LB が大きく下がればまずこれらを調べ、Class 比率を逆算して説明を作らない。

## 10. 開封のための最小完了条件

次を満たした時点で開封へ進む、という有限の条件にすることを勧める。

1. M1/M2 の完成したモデルと候補・特徴・予算・fallback を hash/設定で固定する。M2 の開発結果も記録する。
2. 両 schema と、同一 scenario の小さな W7 parity が成功する。固定保険も実装と採点が一致する。
3. 共通台帳、空候補、C1 条件、M1−M2 の直接 paired 比較を評価器が扱う。
4. C1 の許容損失と、差が小さい／不確実な場合の扱いを追記する。
5. 上記が失敗したら自動採点へ進まず、開封時に code/model を更新しない。

機械的な修正後に再び多数のモデル探索を行う必要はない。M1 plain と M2 plain no-ICE の二つを、実際に提出する条件で確認することが今回の目的である。
