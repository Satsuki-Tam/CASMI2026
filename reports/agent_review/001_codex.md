### 取得済みパネルで V18 全体は replay できない

`panel_benchmark/README.md` と実ファイルは、旧単一エンジン構成、ICEBERG／GLACIER の再ランキングなし、と整合しています。V18 の第2エンジン、N1、最新の PubChem 追加分、五つの fold モデルによるアンサンブルまで含む対照にはなりません。

さらに `main_eval.py`／`merge_eval.py` は、そのまま取得済み parquet を読むプログラムではありません。入力に `lib.pkl`／`nospec.pkl`／`dbdrop.pkl`、分子別 `.npz`、`pool_meta`、`poolfz` を要求します。取得済みフォルダにある該当形式は `panel_logits.npz` だけでした。parquet から旧処理を組み直す余地はありますが、「同梱スクリプトを実行すれば V18 の E1 ができる」という計画にはしないでください。

`prior_replay.json`／`replay_public_priors.py` は、**正解の分子式に一致する候補だけを残す annotation-only の診断**です。スペクトルの shortlist、pool 除外、融合は使いません。正解分子式は本番入力にありません。またこの処理では正の prior 係数を一律に掛けても順位は変わらないので、V18 の `POP_LAM` を調整する実験にはなりません。同一式パネルとして利用するなら「分子式を正解とした条件付き評価」と明記してください。

PubChem 候補1,939,476行のうち、元の `scorer_key` が空の行は1,062,226行あります。追加の exact identity キャッシュは49,319行＋8行です。新しい shortlist やルールで以前は評価対象にならなかった候補を持ち上げる際は、その候補の公式鍵が補完されているか確認が必要です。raw connectivity への fallback を、新たに公式スコアラーとの完全一致を確認したものとして扱わないでください。

## 2 H1〜H4 と E1→E3 の判断

| 仮説 | 判断 | 次の扱い |
|---|---|---|
| H1 順方向モデルの拡張 | 優先するが再定義が必要 | 既存の対象・分岐・有限スコアの不足を測り、未対応部分を一つ選ぶ。全アダクト拡張とランカー新規学習を同時に行わない |
| H2 ルール削除で頑健化 | 実験仮説としては妥当、改善予測は未成立 | 一度に全削除しない。対象ルールが何分子に作用し、正解を上げる場合と下げる場合を分ける |
| H3 カバレッジ飽和 | 未確認 | DB全体、質量窓、各エンジンの shortlist、融合40件、最終25件で正解到達率を別々に測る |
| H4 自前の指紋モデル | 中期課題として妥当 | 今夜は既存 fold モデルの学習除外範囲と推論経路を調べる方が先。新規学習は、対象・分割・基準・所要時間が決まった小規模試行から |

98% という参加者報告の条件は、「その参加者の候補に正解が存在するのに1位でない場合、誤った1位が正解と同じ式」です。全失点の98%でも、V18 のカバレッジが98%以上という意味でもありません。DB が構造を収載していても、前処理・質量窓・top K・生成候補選択・融合で正解を落とし得ます。[元の議論](https://www.kaggle.com/competitions/enveda-CASMI26-molecule-id-mass-spectra/discussion/743254)

ルールが Public で選ばれたことは過適合を疑う根拠になりますが、外した版の方が Private に強いとは限りません。旧パネルの保存結果でも、PubChem insertion を除くと pool-removal の MRR は0.5191→0.3605に低下しています。これは旧パネルでの条件付きの事実であり、V18 への採用推奨ではありませんが、「削除＝頑健化」の反証にはなります。

E3 の条件を「パネルの95%区間が0を跨がないこと」だけにする案には同意しません。構造単位 bootstrap は同じパネル内の標本変動を示しますが、学習への混入、既にこのパネルで選んだルール、多数の試行から最良を選ぶこと、分布差を補正しません。一方、少数の対象分子にだけ効く変更は有効でも区間が広くなります。判定材料は、凍結した比較での効果、作用した分子数、悪化例、学習への混入、別の分子集合での方向、実行時間です。独立評価が用意できない場合の提出は探索的比較と呼び、Private 改善の証拠とは分けてください。

## 3 パネル replay を信用できる範囲と指標

保存結果の引用に加えて、`main_candidates.parquet` と `pubchem_candidates.parquet` を集計しました。

| 旧キャッシュのシナリオ | 候補に正解がある分子 | キャッシュ上位25件に正解がある分子 | 旧 main の MRR |
|---|---:|---:|---:|
| 他ライブラリの参照あり | 250 / 250 | 250 / 250 | 0.9800 |
| 正解の参照スペクトルなし | 250 / 250 | 250 / 250 | 0.9883 |
| pool から正解除外 | 99 / 250 | 99 / 250 | 0.3605 |

MRR は `results_main_channel.json` の `pop mu=0.15 top60`、到達数は parquet の `is_truth` と1始まりの `rank` の集計です。PubChem の質量窓に正解があるのは246 / 250、COCONUT 収載は249 / 250です。

この結果から次が言えます。

- この旧 main キャッシュでは、正解が25位より下に残っている分子がありません。したがって、このキャッシュを使って40→80の候補回収効果を測ることはできません。別の候補集合を再生成する必要があります。
- no-reference の0.9883は、未知構造への性能評価には楽観的すぎ、改善の測定余地も小さいです。特に full1 の学習への含有と、公開済みのルール選択に使われたパネルである点を無視できません。
- pool-removal でも PubChem にはほとんどの正解が残ります。これは主に「主 pool の外だが別DBでは既知」の評価であり、真の Class 3 の評価ではありません。
- FPNet A/B がこのライブラリを除外しているだけでは、同じ分子の他ライブラリの測定まで除外している証明にはなりません。fold-safe 側も、どの鍵・分割を使って除外したかを確認します。

主指標は引き続き**全対象分子を分母にした分子単位 MRR@25**にしてください。top-1 だけでは下位候補の回収を捉えられず、条件付き MRR だけでは候補から正解を失ったことを隠します。診断用として次を併記するのが適切です。

1. 各段のカバレッジと候補数：質量窓、エンジン shortlist、融合40／80、最終25。
2. 正解が同じ固定候補集合に存在する分子での条件付き MRR と top-1。候補集合が変わる比較では、各版固有の条件付き指標だけで優劣を決めない。
3. 分子ごとの RR 差、改善／悪化／不変の数、top-1 の入れ替わり。乱数や tie-break を固定する。
4. 順方向モデルが有効な分子の割合と、最終候補の有限スコアの割合。アダクト、実測 H+ の有無、N1、質量、スペクトル数、学習への含有で層別する。

分割は identity と analogue/scaffold の両方を残すことを勧めます。identity-disjoint は同一分子の混入を防ぎ、analogue/scaffold-disjoint は近縁構造への依存を調べます。「InChIKey 分割はスペクトルのランダム分割と同程度に漏れる」と一括りにしないでください。CASMI の Class 2 は「公開スペクトルがない」であって、「学習分子と骨格が遠い」とは限りません。今回取得した `identity_folds/SPLIT_METHOD.json` は identity link に Morgan Tanimoto >= 0.7 の連結成分を加えた分割を記録しているので、この用途に再利用できます。[MassSpecGym の分割の定義](https://arxiv.org/html/2410.23326v3)

なお、V18 は PubChem 側で `A+B + 0.5 * mean(fold0..fold4)` を使います。通常の train 内の検証構造には、その構造を学習した fold モデルも混ざり得ます。検証では対応する除外 fold の予測を使う必要があり、五つのモデルの平均を OOF と呼ばないでください。パネル250分子を全モデルが別途除外している場合は、その除外記録に基づいて区別します。

## 4 今夜の具体的な変更候補

広いアダクト拡張より先に、**計算した GL スコアが最終ランキングに使われない分岐**を調べる価値があります。

V18 セル44の `rerank_row` は `if ice and gl:` で GL の再ランキングへ入ります。そこで、実際の関数を AST から取り出し、候補2件・有限の GL スコア2件を与えて分岐だけ確認しました。再ランキング関数は呼び出しを数えるスタブに置き換えています。

| ICE 辞書 | GL の有限スコア数 | 実際の branch | GL reranker 呼び出し |
|---|---:|---|---:|
| 空 `{}` | 2 | `unrescored` | 0 |
| 2候補とも `None` | 2 | `glacier` | 1 |
| 2候補とも有限 | 2 | `glacier` | 1 |

これは**分岐条件の再現**であり、実データで何件起きるか、修正するとスコアが上がるかは未確認です。まず同じ実行の `experiment_audit_factorial.csv` 等で `branch == unrescored` かつ `gl_finite_count > 0` の件数を調べてください。存在すれば、ICE が空でも有効な GL 証拠を利用する変更を単独で比較できます。0件なら今夜の改善候補から外せます。GL の有効性判定では `None` だけでなく NaN／Inf も扱ってください。

次点は、既存スコアを使った40→80の最終窓の比較です。ただし、(a) 入力2リストの union に40件を超える異なる候補がある、(b) 追加候補に有効な順方向スコアがある、(c) 凍結した評価集合で回収対象がある、を確認してください。単に `window` を80にした比較と、予測対象候補自体を増やす比較は別実験です。

最初から新しい学習ランカーを作るより、現行順位・FP・ICE・GL・fragment のスコアと欠損フラグを、学習への混入を確認できる分子で揃えることを先に勧めます。この表がない状態でランカーだけ学習しても、パネルへの適合を測ることになります。

新しい公開部品を足す前に、V18 に既に五つの fold FPNet、PubChem 追加構造、外部ライブラリ拡張、N1、24位の追加候補があることを確認してください。今回、これらをまだ未統合の伸びしろとは数えていません。

## 5 提出回数と時間

E0 と、候補を絞った E3 の原則2本にする方針には同意します。ただし、9時間は上限であり実測時間ではなく、週間30時間も固定値と仮定しないでください。Kaggle の公式説明では週間枠は需要等で増える場合があるため、アカウントの残量表示を確認します。commit と採点用 rerun の扱いを確認せず、一律に「2本で18時間消費」とは見積もりません。[Kaggle の GPU 利用説明](https://www.kaggle.com/docs/efficient-gpu-usage)

V18 の visible commit は12分子の smoke です。ここでの成功は全400分子相当・長いスペクトル・高質量・全アダクトの性能や所要時間を示しません。実測ログでは、処理分子数、各段の時間、GPU メモリ、有限スコア率、timeout／fallback、最終 placeholder 数を見てください。予算を使い切っただけの stage を成功した推論と混ぜないことが重要です。

節約できるのは、順位変更ごとに同じ候補・モデル推論を再実行することです。ラベル付き診断実行では、候補、各スコア、キー、メタデータを一度保存し、同じキャッシュで少数の事前に決めた変更を比較します。GPU を必要としない集計と bootstrap は CPU で行います。省かない方がよいのは、変更した分岐が実際に動くこと、公式指標、提出形式、全体の実行時間の余裕の確認です。

各 subprocess の個別 timeout の合計は9時間以下とは限りません。現行コードは engine 2 と PubChem にそれぞれ最大4時間、ICE に5400秒、GL に4000秒、N1 に1200秒を設定しています。これらは実測ではありませんが、候補数を増やす際は全体の経過時間から残り予算を配分し、submission と検証を書き出す余裕を確保する必要があります。

0.480 到達を保証する未使用の手段は、今回の資料からは見つかっていません。E0 が0.464を再現したとしても、0.016の Public 改善を研究ベンチマークの差から予測することはできません。今夜は基準の実測、証拠がある不足一つの修正・比較、採用した一変更の提出を優先する方が合理的です。

## 6 調査知見で修正しておきたい表現

- **「順方向モデルは指紋検索の4〜5倍」**：そのまま手法の優劣として使わないでください。GLACIER 論文の mass 検索69.95%と formula 検索49.88%は確認できましたが、MassSpecGym の simulation 課題は H+ と QTOF／Orbitrap に対象を制限します。指紋側の数値と評価対象・候補・メタデータ条件を揃えた比較ではありません。同じ V18 の候補集合上での追加効果を測る理由にはなっても、効果量の予測にはなりません。[GLACIER 表1](https://arxiv.org/html/2606.29161v2)、[MassSpecGym §3.2](https://arxiv.org/html/2410.23326v3)
- **FOAM の95.2%**：NIST’20 で反復探索中に、正解以上の予測スペクトル類似度を持つ decoy に遭遇した検索の割合です。固定の候補集合で95%誤答するという意味ではなく、学習ランカーへの統合が必ず改善することの証明でもありません。モデルの誤差を探索が利用し得る、という警告として使います。[FOAM 本文・補足図S2](https://arxiv.org/html/2602.07709v1)
- **「主催者が prior を近道と見るので外す／Class 2 でのみ正当」**：論文の問題提起から CASMI の採点方針や許可範囲は推定できません。MassSpecGym in the Wild の約50%は PubChem API の既定順序を用いた特定のベンチマークでの結果です。文献数 prior の有効性は候補とクエリの分布によって評価すべきで、ルール削除の根拠にはしません。[同論文 §5.2](https://arxiv.org/html/2606.19624)
- **「GLACIER の重み公開は未確認」**：論文著者の配布版の確認状況と、現在の Kaggle 公開 bundle に何が含まれ実際に読み込まれるかを分けて記録してください。基準コードは既にその runner を呼び出しています。E0 の読み込み成功・モデルと入力の manifest・学習コードとデータの来歴を確認するのが先です。
