# 021 レビュー: full_rkの開始判断

2026-10-25。**15:35の判断としては、下記の除外・初期化・停止条件を満たせるなら、今日full_rkを開始することを推奨する。full_evalの最終評価を待つ必要はない。** 理由は、同じFPNetで「学習済みidentityの独立query」と「identity未見」のranker学習例を作れる点にある。「rankerが律速と証明されたから」ではない。今夜のfull_eval評価・提出判断とは別の実験として扱う。

**前提: FP単独の増分が小さくなった理由は、まだ分離できていない**

- パネルC1はFP-onlyが0.226→0.806だが、登録出力は既に0.8819で、新FPでは0.9259。元から他の証拠で救えていた分子が多く、+0.58をそのまま最終出力に上乗せできない。パネルC2も0.9045→0.9433で、改善余地が小さい。
- `fp_reach_compare.py`は`truth_fp_rank`を使い、strict C2の外部構造資格を適用していない。例えばW7 Bのfull1 FP-only 0.636は、現行の外部到達177/300=0.590を超える。登録C2とは採点対象の候補資格が違うので、この差をrankerの損失としない。同窓の確認も現在は候補数の一致であり、厳密にはidentity集合のhashも照合する。
- E/FのGL不足群では登録出力は保険で、rankerは呼ばれない。そこでのFP利得の減衰は、FP＋prior・候補選択・fallbackの問題として切り分ける。
- 一方、full1のパネルC1ではlearned出力0.7826に対して固定0.9089、blend21 0.9259で、C1の学習分布を合わせる動機はある。C2ではlearned 0.9438とblend21 0.9433であり、全体に同じ問題があるとは限らない。

保存済み結果から、同じN・C2資格・候補集合でFP、FP＋prior、固定、learned、blend、fallbackの順位変化を比較する診断を並行する。full_evalの値がfold0とfull1の間に入る保証もない。

**Q1 — 除外設計は条件付きで成立する**

| ranker用の行 | full_rkで必要な状態 | 扱い |
|---|---|---|
| p1_run1のC2 | identity group全体のMS/MS–構造対がFP学習外、参照もマスク | 未見C2代理として使う |
| p1_run1のC1 | identityはFP学習外、独立参照は利用可能 | C1-unseenとして残してよい |
| W7/eval_c1のC1 | query取得が学習外、同identityの独立取得が実際に学習対象に残る | C1-seenとして使う |
| W7/eval_c1のC2 | identityの学習例が残る場合 | C2学習・評価から外す。記憶残存の診断に留める |
| query除外後に学習用MS/MSが0となるgroup | FPに対してidentity未見 | 実数確認後にC2行として使える |

**「他ライブラリ参照が使えない」ことと「FPNetに未見」は同義ではない。** 参照照合に使わない極性・adduct・cap外のスペクトルをFPNetは学習している可能性がある。`c1_usable=False`だけでC2へ移さず、除外後の実際の学習SID・スペクトル数と照合する。各行に監査用の`identity_group / query取得群 / 残存学習スペクトル数 / 独立参照数 / rankerのfit,tune,eval`を残す。真の露出状態やクラスを推論特徴にはしない。

重複基準は019bと同じで、**同adduct・5 mDa・類似度0.95だけでは取得の独立性を保証しない**。検索はraw keyでなくidentity group／公式同一性まで広げ、元の取得ID・出典、同一取得のCE違い・別処理版をまとめて除外する。queryの選択ライブラリ全行を外すのは保守的でよいが、別ライブラリというだけでは独立と扱わない。由来不明の群は先にラベルを付け、取得独立性を確認したC1と分けて読む。取りこぼしが後で確認された場合、その版の結果を独立queryの証明には使わない。

開始前に特に必要なのは次の3点。

1. **full_rkは新規初期化する。** full_evalはp1_run1やW7のquery取得を学習対象に含むため、それをfine-tune／resumeしても新しい保留条件にはならない。別run・別checkpoint名とし、再開時は除外manifestまで一致を確認する。前処理キャッシュの適切な再利用と、学習済み重みの再利用は分ける。
2. **FPNetのsplitとrankerのsplitを別々に固定する。** W7/eval_c1の既存fit/tune/evalを維持し、まずfit行だけでrankerを学習する。全行をfitに再用途化するなら明記し、従来のW7/eval_c1成績を保護・未使用評価として使わない。パネルはranker学習に入れず、dev2/locked2は上流FPNetからもgroup単位で除外する。
3. **出力する行と重みを明示する。** 現行trainerは各runから両viewを読むので、W7/eval_c1のC2を除く設定・コードが必要。C2行を減らすとC1比率が増え、C1×3を維持しても元レシピと同じバランスにはならない。旧表の有効群数でW7等のC2を一律に落とすと、C1反復後の比率は約46%から約56%になる。再生成後のpositiveを含む群数・露出別の数を出し、重みを性能を見る前に固定する。019のG72で起きた全体の重み変更を繰り返さない。

また、今回のC1-seenの主な供給源はNPライブラリqueryのW7 B/eval_c1である。W7 AのC1 usableは全体で7、既存fitでは2と少ない。これだけで「timsTOFのC1-seenを十分学習できる」とは言わない。G72を足す場合も、そのqueryをfull_rkの除外対象に入れる別の明示的な設計が必要。

**Q2 — 除外を残したfull_rkを使ってよい。最後の全量再学習は必須ではない**

約0.6%は学習集合内の比率で、隠しC1がそれらに当たる確率ではない。除外集合はNP等に偏って選ばれており、query取得の除外による学習量の変化も別にある。ただし、この比率を理由に保留条件を壊して全量再学習する必要もない。まずは**学習表を作ったfull_rkそのもの**で、rankerと提出経路まで一貫した候補を評価する。

新rankerの効果を測る主比較は、`full_rk＋旧v4b` 対 `full_rk＋新ranker`。同じ特徴表・候補・forward・blend21/fallbackを使い、初回は固定paramsを使う。これとは別に、採用比較として凍結M2xにも対照を置く。`full_eval＋旧ranker`と`full_rk＋新ranker`だけを比べると、FPNet変更とranker変更が分離できない。

full_evalへ差し戻す、または最終的に全量で再学習する場合は、FPスコアの分布と下流の挙動が同じとは仮定せず、同じ学習手順の保留群評価を先に行う。最終全量化後に旧保留集合で未見C2性能を主張しない。

**Q3 — 今日の開始は推奨。ただし15:35時点で準備が整っていること**

full_evalの成績が良くても悪くても、ranker学習用の未見C2例を用意する必要は残る。full_evalではp1_run1が学習済みなので、既存の表をそのまま取り直すだけでは目的を満たさない。この点でfull_rkには独立した価値がある。

15:35のGO条件は、(i)除外manifestと実際の`Data.tr`の交差ゼロ、(ii)新規初期化、(iii)C1-seenとして使う群の残存取得数・重複監査対象の確定、(iv)20:50までの停止・保存・worker終了、の確認とする。元コードの0直書きgateや「ファイルが存在する」だけで通さない。条件が整わなければ、誤ったsplitで4時間学習するより準備を完了して翌日に回す。

確認したfull_evalの進捗記録は45,000step/7,523秒、約5.98step/秒。単純換算で82,855stepは約3時間51分だが、データ構成・評価・I/Oで変わる。full_eval完了後に手元GPUを引き継ぎ、開始時に残時間を再計算する。19:40完了は見込みであり、20:20頃に保存・終了へ移れる余裕を取り、20:50以降の自動再開は行わない。

今夜の提出候補は既定どおり「現行M2x＋full_evalのみ」を別に評価する。full_rkの学習開始を、full_eval提出や新ranker採用の承認とは結び付けない。full_rkの特徴生成・ranker一対比較が翌日になっても、今回の学習目的は満たせる。
