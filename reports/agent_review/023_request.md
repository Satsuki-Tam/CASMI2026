## 2. 新しい読み(提出前に確認したい): dev 集合はすべて「未見 FPNet」の領域で、隠しクラス 1 の大半は「既見 FPNet」の領域
- 現行の FPNet(fold-safe `fpnet_fold0.pt`)の学習除外は **identity fold 0(55,102 構造)+ パネル NP の identity 群(265)だけ**(`data/external/fold_safe_fpnet/make_split.py`、`SPLIT_AUDIT.json`:学習 identity 219,155 / 除外 55,031 → 学習済み約 80%)。
- 確認: パネル 250 分子の identity fold は 0〜4 に 54/57/44/49/46 と散らばるが、fold-0 FPNet の FP-only MRR は fold ごとに 0.20/0.23/0.23/0.26/0.21(どの fold でも未見 — パネル群が明示的に除外されているため)。full_eval では 0.61/0.57/0.67/0.63/0.68。
- dev2・locked2・W7・p1 はすべて identity fold 0 から選んだ(dev2/locked2 は 500/500 が fold 0)。**私たちの開発・評価はすべて「FPNet が未見の分子」でしか測っていない。**
- 一方、隠しクラス 1(公開ライブラリにスペクトルがある = train にある)の分子は、identity fold がランダムなら **約 80% が fold-0 FPNet の学習済み identity**(query は未見の timsTOF)。つまり隠しクラス 1 の大半は、パネルで full_eval が置かれた「identity 学習済み・query 未見」の領域に、現行 FPNet のままで既にいる。
- 帰結 1(full_eval の提出価値): 隠しテスト上で full_eval が変えるのは「クラス 1 のうち fold 0 の約 20%(+ パネル群と重なる分子)」だけ。分子あたりの登録利得 +0.03〜+0.05(パネル C1 clean、W7)を当てると、**期待 ΔPublic ≈ 0.2 × p1 × 0.03〜0.05 ≈ +0.002〜+0.008**(p1 = 0.3〜0.5)。クラス 2/3 では dev2 のとおり ≈ 0。±0.02 の読みではほぼ確実に「未確定」で、1 枠と checkpoint のアップロード(容量問題でユーザー判断が必要)に見合う情報が無い → **今日は full_eval の比較提出を見送る**のが私案。
- 帰結 2(ranker): rank_v4b は未見 FPNet の特徴(fold 0 分子)でしか学習していないので、隠しクラス 1 の 80% で FP が強い(パネル full_eval の FP-only 0.63 vs 未見 0.23)状況は学習分布の外。021 の full_rk 計画(identity 学習済み・query 除外の C1-seen 行で ranker を学習)は、full_rk を提出に使わない場合でも、現行 fold-0 FPNet の隠しクラス 1 に関係する。ただし fold-0 FPNet 用の「identity 既見・query 未見」の行は作れない(fold 1–4 のスペクトルはすべて学習済み)ので、検証は full_rk / full_eval 上でしかできない。

## 3. 提案: 今日の残り 3 枠のうち 2 枠を「クラス分解の probe」に使う(候補ではなく測定)
B1 の登録主出力(M2x blend21、GL 不足時は保険リスト)をそのまま計算し、最後に候補を train 構造かどうか(window 内の pool 項目に train の source bit がある公式 identity = `rows[i]["in_train"]`)で絞るだけの 2 版:
- **probe T**(train 構造だけ、順序は主出力のまま上位 25)
- **probe N**(train 構造以外だけ = PubChem/COCONUT のみの構造)
定義と不等式(同じ隠し分子・同じ順位付けなので対の比較は決定的、GL の非決定性のみ):
- 真が train にある分子(≈ クラス 1)では RR_T ≥ RR_main、RR_N = 0;真が train に無い分子(クラス 2/3)では RR_N ≥ RR_main、RR_T = 0。
- よって P_T ≥(主出力のクラス 1 寄与)、P_N ≥(主出力のクラス 2 寄与)、**P_T + P_N − 0.354 = クラス間の取り違え(他クラスの候補に真を押し下げられた分)の総量** = 完全なクラス判定があれば取り戻せる上限。p_train ≥ P_T。
事前に固定する読み:
| 結果 | 読みと次の行動 |
|---|---|
| P_T + P_N − 0.354 ≥ +0.05 | クラス間の取り違えが大きい → クラス判定・ヘッジ(E0 の交互配置のような 2 経路の上位を交互に置く形)を最優先で設計(開発集合で C1/C2 混合比を振って検証) |
| P_N ≤ 0.05 | train 外の分子でほぼ得点していない → クラス 2 経路(PubChem/COCONUT の順位付け)が主な不足、または p2 が小さい |
| P_T ≥ 0.30 かつ P_N 小 | B1 の得点は主にクラス 1 → E0 との差 0.11 がクラス 1 の順位付けにある可能性を優先して調べる |
| P_T + P_N < 0.354 − 0.01 | 実装か定義の誤り(in_train の判定)→ 調査 |
- 実装: `b1_pipeline.py --probe_filter {train,nontrain}`(主出力の order を最後に絞るだけ;絞る前の主出力も `submission_unfiltered.csv` に保存;空なら "CCO")。ローカルの dev 表で「probe T/N の RR が上の不等式を満たす」ことと、`--probe_filter none` が現行と同一出力であることを確認してから push。
- 残り 1 枠は予備(今日は使わない予定)。
