# 094 回答: B専用の順位付けから自前pool経路へ進む設計

2026-10-27。094_request、069のE0棚卸し、071・077/078の結果、085のB経路台帳、093の登録、10/28の提出計画、現在のview・特徴構築コードを確認した。091・093の性能結果は読んでいない。計算、ジョブ変更、提出は行っていない。

**方向は支持する。最初は「既存shortlist内のBだけを並べる専用ranker」として試し、統合も既存のBの位置だけを並べ替える形から始めるのがよい。T∪Bを主にしてPcを挿入する構成は、その後の別段階にする。** ただし、full poolの候補到達・候補構成の監査は早めに行いたい。既存shortlistでの成否だけを条件にすると、E0との本来の違いである候補生成を調べ損なう可能性がある。

まず背景の解釈を二点限定する。B probeが0.202→0.204と横ばいでも、Bの真がT/Pcとの混合リストの中で上がっていれば、通常のMRRには利得がある。したがって「これまでの改善はBに届いていない」とまでは言えない。また、0.259−0.204はBだけを残した方策の差であり、そのまま全体スコアに足せる+0.055ではない。現在のv7f/v8w7aの隠しB性能も未測定である。**0.41〜0.43という到達予想や金圏への必要条件は、これらの数値だけでは確定できない。** B経路は優先して調べる価値のある残差として扱う。

**Q1: 最初の役割をB内の順位付けに限定すれば、筋のよい比較になる。**

「Bだけ」と「T∪B」は別の問題なので、最初から二案を混ぜないことを推す。

- **Bだけ**：Bが正解である場合の候補内順位を学ぶ。学習・評価の目的と、COCONUT正解の群を厚くする理由が一致する。
- **T∪B**：B内順位に加えてT/Bの取り違えを扱う。COCONUT正解だけで学習すると、T正解の条件を十分に学べず、統合時の費用が出得る。E0のc1/c2等の模擬学習に対応する設計が別に必要になる。

最初のB専用実験では、次の契約を固定したい。

**所属と分母。** 公式identityで重複を処理し、各viewで`B = COCONUT所属 AND NOT train所属`、T優先の排他的な定義にする。train所属は構造の所属であり、残存参照が0という条件とは別である。候補は先に`view_frame`でC1/C2のshortlistへ限定してからBへ絞り、保存されたC1/C2和集合をそのままBの候補集合にしない。

C2代理では正解identityのtrain所属・参照を隠すので、元はtrainにもCOCONUTにもある真がBへ移るのは、意図した模擬である。一方、COCONUTに無いtrain正解はBにならない。DBに残ればPc側、候補に残らなければ未到達として、非Bの費用評価に残す。**B主指標の対象は、候補表に真があるかどうかと無関係に、正解keyを固定の所属台帳へ結合して列挙する。** 071で訂正した「真が候補に無いと非COCO扱いになる」問題を繰り返さない。aliasの全体でC2のmaskと所属を揃える。

**三つの順位を区別する。**

| 指標 | 定義・用途 |
|---|---|
| B内順位 | viewの全shortlistからBを取り出して順位付け。B正解の全対象を分母にし、真が候補外なら0。B内順位が25を超えた場合もRR@25は0。専用rankerの識別力を見る |
| PublicのB probe相当 | 最終出力の先頭25件を作った後、Bだけを抽出してRRを計算。B内順位に加えて、最終25件へBの真を採用できたかを含む |
| 通常の最終MRR@25 | T/B/Pc等を混ぜた提出リスト上の順位。統合の採否と他層の費用を見る |

提案の「B候補の中の真の順位」は一段目の指標であり、そのままPublic probe相当とは呼ばない。Publicの0.204/0.259は全Public分子平均で、ローカルのB正解だけの平均とも分母が異なる。候補外の0を残した値に加え、到達済みの条件付き順位も診断として出すが、後者を主指標へ置き換えない。

**特徴の再計算。** 生のFP・GL・analog・library類似度等は同じquery・モデル・参照maskのものを使い、Bに絞った後のz、順位、gap、候補数を学習・評価・本番で同じ関数から作る。現在の`feature_matrix`では、`z_fp/z_gl`だけでなく`lib_margin/lib_max_mol/z_ana_ap/ana_gap/n_cands`等も候補集合に依存する。B内で定数化する所属特徴も記録する。

`fp_rank_window`は現在、元の質量窓での順位である。B shortlistを並べた順位を同じ意味の「pool窓順位」として代入しない。最初は元のglobal window順位として明示して残すか、その列を外して`rank_in_B_shortlist`等の別の定義へ変更し、対応する特徴で再学習する。full poolを採点していない段階で、窓内順位を旧順位の割当て等で近似することは推さない。

**学習と対照。** np061_f3poolは既に071で使用した群なので、新しい確認集合ではない。新rankerの学習へ使うこと自体はよいが、fold-safe FP特徴、identityごとの重み、候補選択、固定パラメータ、真の所属を明記する。093用にこれから予約する確認群も、094の学習・選択へ流用しない。

学習に使うB正解でも、B候補内に正例が無い群は通常のLambdaRankでは学べない。その件数を記録してfitから外し、評価では0として残す。正解を候補へ注入して評価したり、到達した正解だけを評価集合にしたりしない。

対照は、実験開始時に固定した主系の**既存の最終scoreを、そのままBへ制限した順位**とする。Bへ絞って旧rankerへ新しい相対特徴を入れ直すだけの出力は、入力分布を変えた別案であり対照の置換にはしない。新しいB専用rankerとの差は、学習母集団・候補文脈を含む専門化一式の効果である。原因まで分けたい場合は、同じCOCONUT学習群・同じ設定で元の全候補を学習する対照を追加する。

GLありの群だけで学習する初回は、適用条件も事前固定する。Bへ絞るとGL被覆率の分母が変わるため、従来fallbackだったqueryまで自動的に専用rankerへ入れない。初回は元の主系でGL経路になるqueryを対象とし、他は元のB順位を維持する構成が切り分けやすい。NP_Hだけの利得を、GLの無いNP_N等へ外挿しない。

**窓の監査は段4を待ちすぎない。** 085では053 devの640分子に対して、真の窓到達560、shortlist到達551で、窓からshortlistの間の損失は9分子だった。この集合で順位から始める根拠にはなる。しかし隠しの到達や、Bデコイの残り方まで同じとは限らない。旧FP・priorで選ばれたBだけを使うと、full poolとは難易度や候補分布が変わる。

既存の窓台帳が使える範囲で、Bの窓内件数・shortlist件数・真の到達・最初のB位置を先に調べる。窓とshortlistの差が大きい層なら、少数queryでのfull pool評価を前倒しする。差が小さい層なら、既存表でのB順位付けを先に進める。**既存表で失敗してもfull poolの仮説全体は否定できず、成功してもE0型経路を再現したとは言えない。** 生成物を同じrankerへ入れる変更は、候補分布と正解クラスをさらに変えるので、full poolの確認後の別実験にする。

**Q2: BASE_Bは優先順位を決める材料とし、engine1か後段かの二択にはしない。**

計画にある±0.015の範囲は、結果前に固定した運用上の読みとして維持してよい。SをBASE_Bとすると、分岐は次の表現を推す。

| 結果 | 言えること | 次の優先順位 |
|---|---|---|
| 0.244 < S < 0.274 | engine1のBASEだけでfinal_B=0.259に近い得点を再現する。後段の救済と損失が相殺している可能性も残る | B専用順位付けとpoolの候補・特徴の監査を優先。後段を丸ごと移植する根拠にはしない |
| S ≥ 0.274 | 後段を通した方策はB probeでは低下している | engine1側のB順序を活かす小さな統合から試す。T/Pcの利得との交換も調べ、E0の全体融合をそのまま模倣しない |
| S ≤ 0.244 | 後段を通した方策がB probeを上げている | ENG_Bと候補追加・RRF・forward・rank-2の補完を優先して調べる。ただしSと旧B1_B=0.204の関係も併記する |

低い場合でも、例えば0.204より明確に高ければ、engine1単体にも旧B1に対する差が残る。B専用化を止める必要はない。Sが0.204以下なら、E0の優位をengine1単体の模倣だけで説明する根拠は弱く、後段の別表現・候補・補完性へ優先度を移す。ただし0.204は旧0.379版のprobeで、現在のv7f/v8w7aのB性能ではない。

この比較には、同じ公式identity・所属判定、BASE先頭25→B抽出、順序維持、補充なしという凍結方策を使う。Bを先に抽出して25件まで補充する出力は別の診断であり、途中で替えない。単一の集約スコアから、候補到達・B内順位・最終25件への採用の内訳や、個々の特徴の寄与は決まらない。

また、BASE_Bが高くても「人気度特徴が無いから強い」という090の仮説が支持されたとは書かない。BASEには弱い人気度の再順位があり、FP、元素・部分式、analog、学習群、窓等も同時に違う。10/28計画のこの仮説に結び付ける説明は、**engine1方策で得点を再現できた、特徴ごとの原因は未特定**という読みへ整理するのがよい。

**Q3: B内順位専用ならCOCONUT正解で学ぶことは許容できる。群をまたぐ配置能力は別に評価する。**

071の観測は、COCONUT正解を厚くした全体rankerでCOCO C2が改善する一方、非収載C2やパネルC1に費用が出た、というものだった。C1比率も変わり、077で比率を戻しても非収載C2の費用が残った。これは専門化を禁止する根拠ではなく、**専門化した順位を全候補へ適用する際の分布変化を警戒する根拠**になる。

Bだけの条件付き順位では、COCONUT所属は原則全候補に共通になる。COCONUT正解を学習することは目的に合う。ただし、公共libraryにスペクトルを持つCOCO分子の中でも、有名さ・化学骨格・取得条件の偏りは残る。B内の人気度の高低、library、GL経路で差を報告し、090の不合格を理由なく覆して人気度列まで同時に削除しない。

**最初の統合は、全shortlist上のBの位置を保存した並べ替えを推す。**

1. 元の主系で、公式identityが一意な全shortlistの順序を確定する。
2. その中でBが占める位置の列を保存する。
3. 全shortlist内のB候補だけを専用rankerで並べ、その順に保存した位置へ入れる。
4. T/Pc等の位置はそのままにして、最終25件を取る。

この処理は、正解がBかを知らなくても全queryへ適用できる。**同じ候補identityと所属定義なら、非Bの真の最終順位は不変**である。C1の真がTに属する通常の代理では、その順位も変わらない。C1というクラス名とT所属は同義ではないので、保証する対象は正確には非Bのidentityである。

最終25件内のBだけを入れ替えると、元々26位以下だったBの真を救えない。全shortlistのBを並べてから同じ位置に入れる方式なら、B枠の数を増やさず、その中身を改善できる。B枠が最終25件に一つも無いqueryは救えない。この制約の大きさは、Bの真を最初の既存B位置へ置く場合の到達・MRR上限を台帳で見ると分かる。

この段階では、非BのRR差は統計的非劣性だけでなく**出力位置の完全一致**として点検できる。変化したら、重複処理、所属、候補追加、view、同点処理等も動いている。B内MRRの平均が改善しても、最終位置の間隔がqueryごとに違うため、通常のMRR平均まで必ず改善するとは限らない。最終出力のstrict C2でも利得を確認する。

次にB枠を増やす・T∪Bを主とする・RRFで混ぜる段階では、この不変性が失われる。

- **T∪Bを主経路にする場合**：T正解のC1を含む模擬行が必要。COCO正解だけで作ったrankerを、そのままTを含む全体の順位器とみなさない。真がpool外のqueryで、強く見えるpool候補がどれだけ押し上がるかも測る。正例がpool外の群を除いたLambdaRankだけでは、「今回はpoolを信用しない」という判断は学べない。
- **RRFの場合**：identityごとの重複票を除いても、B候補だけ追加の経路から票を得る。順位融合は、Bであることへの加点にもなる。専用rankerの生scoreは他経路のscoreと校正されていないため、直接連結して比較しない。
- **Pcの固定枠挿入の場合**：Pcの真を上位へ置ける位置や件数を制約する。COCOの改善だけで採用せず、非COCO C2、C1、既存生成経路を使う場合はその出力も保護する。

いずれの統合にも、**旧B順位のまま同じ統合をする対照**を置くとよい。例えばVと新BリストのRRFだけを見ると、専用rankerの改善と、Bへ追加票を与えた効果が混ざる。Vから取り出した旧Bリストを同じ規則で混ぜる対照なら、その差を切り分けられる。

採否は、B内順位の改善だけでなく、通常の最終MRRの一対差、非COCO C2、パネルC1 clean、G C1、GLなし経路の費用で決める。候補未到達は全分母に0で残し、identity単位のpaired CIと既定のεを使う。重み・枠位置・RRF定数を多数試した後に確認集合を共有しない。093用の新しい確認群と094用の確認群は、使う前に分けて予約する。

推奨する進め方は、**B所属・到達の監査 → 既存B shortlistでの専用順位付け → Bの位置を保つ統合 → full poolでの候補と特徴の再評価 → 群をまたぐ配分 → 生成物の追加**である。full poolの小規模な監査は早めに行い、そこで見つかった到達損失に応じて本実装を前倒しする。こうすれば、B内の識別、候補到達、群間の配分のどこが効いたかを残しながら進められる。
