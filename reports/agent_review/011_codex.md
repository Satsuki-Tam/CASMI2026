**結論：0.334 は比較系を見直す十分な理由だが、差0.130の主因はまだ特定できない。優先するのは、同じ入力・候補条件での参照優先の切り分けと、forward を外した prior 診断。パネルだけで λ を決め直すことや、さらに候補を増やすことは先にしない。locked は今回の診断を待ち、変更する候補は開封前に再登録することを勧める。**

**最初に訂正すべき事実：保存された実行記録は隠しテストの記録ではない。**

`runs/v2_fixed` と `runs/v3_M1` の `b1_stage_stats.csv` を、Spark の `data/raw/test.parquet` と照合した。両 run の400分子の ID 集合は公開ダミー test と完全一致する。昇順 ID を改行結合した SHA256 は3者とも `f300cbe427300469664a60d074db35c0f02cf2ad184f0778599ceec7175d6802`。ログの1,213スペクトルも一致する。公式保存資料 `docs/official/pages/data-description.md:6` は、このファイルが train 由来の例で、採点再実行時に隠し test に置き換わると明記している。

従って、参照類似の中央値 **0.77863**、libpri 発火59件、GL/ICE 使用371件、所要12,414／11,427秒は**可視実行**の観測値。隠しテストの C1 比率、参照の強さ、forward 被覆、実行時間の根拠にはできない。両 manifest の `gl_mols=400` も全分子で GL が有効という意味ではなく、ログ上の有効対象は371。M1 の `learned=400` は旧 fallback 方針で全分子に学習器を適用した記録である。LB 0.334 自体は依頼の採点報告として扱う。

**Q1：0.130 の差と、最短の切り分け。**

E0 と B1 は候補生成、参照の扱い、学習モデル、prior、候補の混ぜ方が異なる。差を LambdaRank、C1、prior のいずれかへそのまま帰属させられない。B の0.373より低いことも、未知のクラス構成・化学分布を持つ Public への外挿では検証破綻の証明にならない。一方、同じ Public 上の0.130差は、E0を対照から外して B1 内部の比較だけを続けるべきでないことを示す。

まず、既存開発集合の固定した小集合とパネルを別々に扱い、同じ query、参照マスク、公式 identity、全分子分母で E0 の対応版と B1 を比較する。E1 の保存 main list は公開系の部品診断に使えるが、E0 の最終提出全体と同一とは見なさない。学習データとの重複があるモデルの値は、挙動の診断と未見性能の評価を区別する。

| 切り分け | 最小の対照 | 記録するもの |
|---|---|---|
| 候補生成・絞り込み | 同じ query／マスクで、E0 と B1 の候補を公式 identity で照合 | 正解が「DB／質量窓／shortlist／top-25」のどこで消えるか。E0だけが当てる分子について、候補不在と順位不足を分ける |

既存スコアの再順位付けから始めれば、重い再学習は要らない。参照と prior の両方が効いた場合にだけ「参照優先なし／あり × 現行 λ／選んだ λ」の小さな比較を追加し、相互作用を確認する。可視ダミーの重複は照合処理のデバッグには使えるが、C1 汎化性能の評価には混ぜない。隠し実行のログが得られない場合、実行時の欠損については公開された隠し仕様を模した負荷・未対応 adduct の確認で補い、可視の371件を代用しない。

パネル診断だけでは主因の確定には足りない。とくに以下の解釈を修正する。

- E1 の71.1%は、PubChem キャッシュにある **246分子・正解分子式に限定した候補集合**での `doc only`。`doc = log_substances + log_pubmed` である。B の21%は「到達可能かつ shortlist に真がある159分子」での `pop_public`。候補集合、分母、prior の定義が違い、隠しテストの prior が強いことを示す直接比較ではない。パネル自体も、公式説明で意図的に一般的な天然物を選んだ集合とされている。
- E1 の C1 `ranker_only` 0.95483 は、複数特徴を使う ranker の値で、純粋なライブラリ照合の未見性能0.95ではない。同パネルでは参照なしでも0.97064であり、この値から C1 の本番性能を推定しない。
- §10 の `S(1,0,0.5) = FP+pop` は、009で訂正済みの誤記が残っている。この規則には GL が入る。パネルで λ=0.5/1/2/4 を比べるなら、**`S(0,0,λ)` の対照も必要**。現行 `b1_evaluate.py` の追加グリッドは GL を含むため、それだけでは「forward 汚染を避けた prior 診断」にならない。GL/ICE を外した系列と、それらを含む参考系列を分ける。

v3 の固定規則 A=0.65237／B=0.37677 は Spark の JSON でも確認した。到達増加と全体 MRR の悪化は両立する。ただし「新規回収した真は上位に来ていない」まで集計平均から断定せず、既存到達群・新規回収群の ΔRR を分解する。候補拡大をさらに進める前に、どちらの損益が支配するかを確認する。

**Q2：優先順は、(a)を診断に使い、(c)で採用判断を補強し、その後に(b)。**

すでに走っている λ グリッドは感度を見るために使ってよい。しかし、パネルで最大だった λ をそのまま採用しない。まず同じ公式 identity に付く E0 の `doc` と B1 の `pop_public`、結合欠損、スコアを標準化する候補範囲を照合する。λ の数値だけでは二系統の prior の強弱を比較できない。

開発集合を全部捨てて作り直す必要はない。既存 A/B を残し、天然物・アナログ、低／高文献数、同装置／他装置、forward 対応状況の層を追加・明示する。可能な範囲で MSG 非重複かつ identity が学習から独立した確認群を設け、候補や λ の選択前に固定する。本番の未知クラス比率を LB から逆算して重み付けしない。

その確認でも prior の過小利用が再現したら、小さな固定規則の改訂を先に比較する。パネルを GL/ICE 付きで LambdaRank に追加すると、学習済み分子にだけ成立する関係を再学習するおそれがある。汚染のない対応データで再学習する段階まで、(b)や prior の単調制約を最優先にはしない。パネルの forward を欠損にしただけで、本番の完全被覆時にも有効な学習例になるとは限らない。

**Q3：公開系の参照処理の移植には賛成。ただし、検索と最終順位の保護を分けて評価する。**

保存 E0 Notebook の最終 merge は `lib_max >= 0.9` なら main list を維持する。これは「最大類似度の候補を直接1位にする」規則とは異なる。B1 へ移す際は、参照スペクトルの選択、ピーク前処理、同 adduct／複数 query の証拠、候補取得、順位保護のどこが効くかを一つずつ確かめる。最初は既存 B1 の libpri を対照とし、閾値0.9だけを同じ意味として移さない。参照候補を守る規則には C1 の救済だけでなく、近縁異性体を誤昇格する C2 の損失も報告する。

C1 は現在の「他ライブラリ参照のみ」を維持し、別の条件として「同じライブラリ・装置の**独立した取得**を参照に残す」を追加する。query と同じ取得の CE 違い・派生ピーク列・他ライブラリへ複製されたスペクトルはまとめて除外する。取得を分離できるメタデータがなければ、この条件は楽観的な近似として表示し、正式な未見性能とはしない。C2 の全 identity 参照除外も併置する。C1 の参照利用と、ranker/FP/forward の学習重複は別に監査する。

**Q4：未開封なら、今回の小さな対照結果を待つ延期を推奨。**

診断で構成を変える見込みが高い時点で、旧候補だけの確認に locked を使う必要はない。今回のパネル対照、M2 の開発結果、E0/B1 の差の所在を確認する一巡を区切りにする。改訂不要なら登録済み M1/M2 で進む。改訂が必要なら旧登録を保存したまま、候補数を増やさず新しい版・保険・比較規則を開封前に登録し直す。未使用集合を見ていない限り、この更新は locked に対する調整ではない。

M1/M2 の選択自体を今確定する必要があるなら、旧登録で開封し、改訂候補を独立した locked 2 で確認する運用も可能。ただし未使用の identity を別に確保するコストがあり、今回はこちらを第一選択にしない。既に採点値を一部でも見た場合は、その集合を再び未使用とは扱わない。機械的条件は010を継続し、W7 の旧95%基準と報告86〜92%の違いは、同一 forward cache での一致と独立 runner の実行差を区別して記録する。本依頼では010対応の全面再監査はしていない。

**Q5：保険に1枠を使う価値はある。ただし、M1 が0.464未満だったことだけを提出理由にしない。**

「参照を保護する固定規則と学習融合のどちらを次の開発対照にするか」が変わるなら、登録済み保険の提出は有用。先に開発側の同じ予測行で変更分子数、C1 の救済と C2 の損失を確認する。M1 の `submission_fixed.csv` は libpri 0.9 付きで、0.334 の旧固定版は参照優先なし。コード・候補・forward 条件が揃っていれば、**保険と旧固定版の差**は参照優先の診断に近く、**保険と M1 learned の差**は最終順位方式の比較になる。条件や fallback が違えば、その変更を含む比較として記録する。

保険が上がっても Public 全体の順位改善が分かるまでで、C1 比率や C1 単独の改善量は分からない。両方低ければ、LBで τ・λ を順に選ぶことへ進まず、上の候補・prior・参照経路の対照へ戻る。0.464 を出した E0 は保存して比較基準に残す。残り枠を使い切る必要はない。
