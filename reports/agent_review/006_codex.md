# レビュー 006: B1 の初回評価と学習融合へ進む条件

作成: 2026-10-24、Codex。`006_request.md`、B1 設計、run1 の結果と特徴表、評価・学習・提出コードを確認した。保存済みデータの CPU 集計と関数の照合のみ実施し、GPU 実験・学習・提出・Spark への接続は行っていない。コードは更新中だったため、以下は保存済み run1 と、末尾に示す確認時のコードを区別して記載する。

## 1. 結論

**B1 を主軸に進める方針と、P1 の開発分子をランカーの fit に利用する方針に賛成する。ただし、現在の C2 評価には C1 から候補が混入する経路があり、学習融合の採否を決める前に修正が必要。** 重複参照の再構築だけではこの問題は直らない。

優先するのは次の三点。

1. C1/C2 の参照条件を候補選択の前に適用し、各条件の shortlist と標準化を分ける。
2. 参照重複を「類似度 0.98 以上だから同一取得」と確定せず、確実な複製と近似的に重複を疑う群を分ける。
3. `eval_set` は既に固定規則の比較・prior 選択に使った開発集合とする。独立な最終評価は、設計文書にある別の locked eval で行う。

参照優先なし、prior=0.5 を当面の固定比較に置くことは妥当。ただし、参照信号が不要と結論づけたり、LambdaRank が文献 prior の分布差を自動的に解消すると期待したりしない。

## 2. 最優先: C2 の shortlist に C1 の参照が使われている

`b1_features.py` は C1/C2 の類似度を別々に計算するが、shortlist の参照枠は次の一つだけである。

```python
top_lib = ... argsort(-lib_c1)[:20] ...
short = union(top_fp, top_fpp, top_lib)
```

`b1_evaluate.py` とランカーは、この共通 shortlist のまま C2 の参照類似度を 0 にする。したがって「参照があったので初めて候補に入れた正解」が、参照を隠した C2 に残る。

run1 の特徴表で、正解が **参照枠だけ**から入った分子を数えた結果は A 0、B 7 分子だった。いずれも `lib_sim_c2=0`、`in_top_fp=False`、`in_top_fpprior=False`、`in_top_lib=True` である。

| B の分子 | 窓全体での FP 順位 | C1 類似度 |
|---|---:|---:|
| `UYDSWRORAHRACW` | 829 | 1.000 |
| `XVNJBDKWBSRNOE` | 418 | 0.938 |
| `HDYWOHRLZIAAHQ` | 531 | 1.000 |
| `HIMBNYXSHQNLGW` | 172 | 1.000 |
| `FBEOMFUXNKYIIU` | 4,027 | 1.000 |
| `CIJDGSBMVPUFQD` | 324 | 1.000 |
| `UVLDZZAYYQKDSL` | 3,874 | 1.000 |

7 分子とも現在の strict マスクでは到達可能であり、S(2,1,0.5) の既存 RR 寄与は合計 2.90476、B 全体 MRR にして **0.00968**。これは修正後の MRR 差そのものではない。候補の補充と z の再計算でも順位が変わるためだが、無視できない混入経路である。

修正は、各 view について `FP 上位 ∪ FP+prior 上位 ∪ その view の参照上位` を作ること。GPU 計算用には両 view の候補の和集合を使ってよいが、評価・学習に渡す候補行と z の計算は各 view の所属マスクで分ける。C2 の参照枠から正解を外した後は、次の参照候補を補充する。

既存の GL/ICE は、query・モデル・設定が同じ候補について再利用できる。新たに shortlist に入った候補だけ追加計算する形にすれば、全てを再推論する必要はない。既存表から問題行を落とすだけの CPU 集計は暫定診断には使えるが、補充前なので正式な端から端の値にはしない。

### strict の到達判定も B1 の窓へ更新する

現在の `window_external` は選定時の P1 形式 CSV から読み込む。一方、B1 は観測された複数 adduct の窓を合併しており、同じ候補取得ではない。

具体例として `UOZODPSAJZTQNH` は、選定 CSV の `window_external=False` だが、B1 shortlist の正解には `in_tier=True`、`in_coconut=True`、質量誤差約 2.31 ppm が記録され、S(0.15)/S(0.5) とも正解 1 位だった。旧マスクにより strict では 0 になっている。

B1 の実際の query・adduct 窓・候補源から、shortlist 前の公式同一性による外部到達フラグを記録し、固定規則とランカーで共通に使う。依頼の「DB 不在 102、質量窓外 19、shortlist 外 17」は以前の P1 B の値である。現在の選定集合では DB 存在 191、旧窓到達 175 であり、B1 の漏斗はさらに再集計が必要。

## 3. 学習コードで対応済みの点と、残る評価上の問題

確認した最新版では、次の変更を確認した。いずれも妥当である。

- `b1_rankfeats.py` の 28 特徴から `view_c1` が除かれた。本番では正解が C1/C2 のどちらか分からないため、scenario 名は特徴に入れない。共有関数の呼び出しと引数の対応も確認した。
- ランカーの C2 行では、tier / COCONUT / train の全出典が偽の候補を除去する。
- 固定対照を S(2,1,0.5) とし、0.15 も併記する。

出典なし候補の除去は重要である。保存済み特徴表には「tier=False、COCONUT=False、in_train_c2=False」の行が A 13、B 93 件あり、**全て正解、非正解は 0 件**だった。train 由来の正解行を残してフラグだけ消すと、ランカーがこの組合せを正解の手掛かりにできる。最新版の除去でこの経路は塞がれるが、保存済み固定規則の計算は旧候補表なので、比較時には同じ候補条件で再集計する。

残る点は以下。

1. **空候補の分母**: `b1_rank_train.load_run` は特徴行がある分子だけを読み、`mrr_of` もその行から分母を作る。B の `MWKQPIROPJSFRI` は分子 CSV にあるが特徴行がない。評価では最初に固定した molecule/view 台帳へ戻し、空候補を 0 にする。現在の B 全体で S(0.5) を特徴行のある 299 分子だけで平均すると 0.38060、全 300 分子では 0.37933 になる。
2. **paired delta の strict**: `eval_delta` は C2 でも raw RR 差を平均・bootstrap しており、保存した `reach` を使っていない。主指標に合わせ、C2 strict の差と区間を出す。
3. **identity の検証**: 現在の `identity=mid` は raw 分子 ID。既存選定では group を分離しているが、複数 run を結合する際には `identity_group` を保持し、fit/tune/eval 間の共通 group がないことを assert する。同じ分子の C1/C2 は同じ split に置く。
4. **本番と同じ特徴表**: 共有関数は有効だが、参照集合・候補集合・query の選び方が違えば、関数だけ共通でも特徴は一致しない。後述の shortlist λ 等も設定として揃える。

これらを直した後に学習融合を評価すればよく、P1 の分子を捨てたり、FPNet を再学習したりする必要はない。

## 4. 質問 1: 参照優先を外して学習融合に任せるか

**重複の問題が未解決な間、参照優先なしを固定比較にする判断には賛成。ただし最終的な Class 1 対応を省く判断にはしない。** 学習融合を試す価値はあるが、上記の候補混入を直した結果で比較する必要がある。

参照優先が C2 を落としただけでは、全体で悪いとは決まらない。例えば現在の B の τ=0.8, margin=0.2 は、S(0.5) に対し C2 約 −0.008、C1 約 +0.285 という交換になっている。C1 の値は重複込みで楽観的だが、両方の損益を見る必要があることは分かる。未知の Class 比率で単一の平均を断定しない。

三条件ゲートは比較候補にはなる。ただし S 上位 k を必須にすると、「FP/forward が外した正解を参照で救う」という補完性も制限する。既存の top-3 結果が小さかったことは、参照信号を捨てる根拠にはならない。

次の最小比較は、独立性を確認した参照で、S(0.5)、参照類似度のみ、固定参照規則、LambdaRank を同じ候補集合上で並べること。C1 で参照が正解首位だった分子を融合が落とした件数、C2 で誤った高類似参照へ昇格した件数を別に出す。学習融合には raw 類似度、同 adduct 類似度、別 identity への margin、一致ピーク数・説明強度・複数 query での整合を使う方が、scenario フラグを与えるより本番に対応する。

A の C1 は 7 分子しかなく、今回の中央値 0.678 から本番 timsTOF 対 Orbitrap/QTOF の類似度が同程度と予想する根拠は弱い。「この 7 分子で観測した中央値」に留める。

## 5. 質問 2: precursor 5 mDa ＋ 類似度 0.98 の重複除外

**重複を疑う候補を集める基準としては使えるが、同一 acquisition の確定条件にはしない。** 高い spectral entropy similarity は取得 ID を表していない。

現行の `entropy_similarity` に、m/z が `[100,150,200]` と `[100.004,149.997,200.006]`、強度が両方 `[0.5,0.3,0.2]` という異なるピーク列を与えても 1.0 になることを CPU で確認した。許容幅内で対応するピークの強度が同じなら起こる。`clean_peaks` による弱いピーク・precursor 近傍の除去も、異なるスペクトルを同じ比較対象にし得る。

run1 の B C1 82 分子中、正解参照類似度が 0.98 以上なのは 65 分子。再登録を多く含む可能性は高いが、この数をそのまま複製確定件数にしない。独立測定でも高い一致はあり得るし、疎なスペクトルでは別構造も強く一致し得る。

推奨する扱いは二段階。

- **確実な複製**: 元 accession/取得情報が同じ、または元のピーク列・強度・adduct・CE 等が厳密に一致するもの。識別できる範囲で acquisition の cluster として query/reference を分離する。
- **重複の疑いが強い群**: precursor 近傍かつ similarity≥0.98 等。主結果からの除外版と保持版を併記し、この群の除外に結論が依存するか調べる。出典が確認できない場合は「近似重複を除いた評価」と明記し、「独立取得を保証」としない。

過剰除外の検出では、少数例を最高類似度だけで選ばず、ピーク数、装置の一致／不一致、CE、adduct、元の強度差、precursor ppm 差を層別して確認する。明らかに異なる CE・取得メタデータを持つ高類似参照が大量に消えるなら、独立測定を消している疑いがある。

### 現行の除外実装で注意する点

1. 除外は正解参照だけでなく、全候補の参照に適用される。したがって高類似の異性体・別構造の参照まで消え、C2 の誤一致を人工的に減らす可能性がある。`n_truth_dup_refs` だけでなく、非正解側で消した参照・候補も数える。
2. `MAX_REF=24` の打切りが重複除外より前にある。最初の 24 件が複製なら、その後にある独立参照まで使えなくなる。適合 polarity・adduct・重複 cluster を整理してから、CE/装置の多様性を保って上限をかける。
3. `c1_possible` は「他ライブラリに何かある」で決まり、重複除外、polarity、ピークの有効性、MAX_REF の後に利用できる参照があるかを反映しない。事前の eligible 数と、処理後の usable 数を分け、残った C1 の件数を明示する。高類似の参照だけを消して C1 が下がった結果を、独立測定の一般的な性能と断定しない。

「0.98 を超える独立測定は稀」という仮定を固定規則の採用理由にせず、上の差分と確認例で判断したい。

## 6. 質問 3: prior=0.5 の採用と LambdaRank

prior=0.5 を暫定の固定基準にすることには賛成するが、証拠の強さは A/B で異なる。保存済み run1 の C2 strict を分子単位で再集計した。

| 0.5 − 0.15 | 平均差 | paired 95% 区間 | fit / tune / eval の差 |
|---|---:|---|---|
| A | +0.00697 | [−0.00472, +0.01937] | −0.00018 / +0.02293 / −0.00184 |
| B | +0.03400 | [+0.01797, +0.05144] | +0.02832 / +0.04446 / +0.02922 |

従って「A/B の平均が同じ方向」は正しいが、A まで安定した改善が確認できたとは言わない。C1 では A の 7 分子で平均 −0.1465、B 82 分子で +0.0209。C1 専用集合の暫定結果は GL のみなので、同じ完成パイプラインでの第三の確認とも区別する。

LambdaRank に prior 成分を分けて渡すと、参照・forward・出典との相互作用を学べる。ただし、学習にない文献数分布や天然物の希少性を自動的に補正する保証はない。強い相関があれば、固定 λ より prior に依存することもある。

モデル選択では λ=0、0.15、0.5 の固定基準と、prior あり／なしの学習融合を少数比較し、PMID=0 の群、低文献数群、COCONUT 所属、質量・候補数等で利得を確認する。これ以上細かい λ を現在の全 600 分子で追うより、候補混入を直した値と locked eval を優先する。

### λ の変更が候補選択まで変わっている

`b1_features.py` の shortlist は λ=0.15。保存済み評価の「S(0.5)」は、その同じ shortlist の最終融合だけを 0.5 にした比較である。

一方、確認した `b1_pipeline.py` は `LAM=0.5` を最終融合と `top_fpp` の両方に使う。従って提出版は、prior の順位重みだけでなく、候補集合と forward 計算量も変える。

既存評価をそのまま再現するなら `SHORTLIST_LAM=0.15` と `FUSION_LAM=0.5` を分ける。shortlist 自体も 0.5 にするなら、候補到達率と新候補の forward スコアを含めて別変更として評価する。これは prior 採用判断に直接関わる実装差である。

## 7. 質問 4: fit に P1 を使う構成

**P1 600 分子を fit に使ってよい。** 過去に固定規則の重み選択に使った分子を、後のモデルの訓練データにすること自体は問題ではない。最終評価を別の未使用 group に置くことが重要である。

ただし依頼の「tune/eval は未使用の eval_set」は修正が必要。現在の eval_set 全 600 分子について、多数の固定規則と prior を比較し、群別結果も見ている。既に B1 の開発集合であり、同じ中の eval 100+100 を独立な最終評価とは呼べない。設計文書と 005 判断記録にある **別途の locked eval** を採用判断に使う。

推奨する役割は、P1 と既使用 B1 の指定部分で fit、既使用 B1 の tune で学習設定を選択、別の locked eval で固定したモデルと S(0.5) を一度比較する、である。既使用 eval 群は開発上の確認値として残してよい。

現在の `eval_set` と `eval_c1` の identity group に共通はないことは確認した。複数 run の結合時には、この確認をコードの assert にし、同一 group の再利用や別表記を防ぐ。C1/C2 二条件は同じ split に置き、二条件を持つ分子だけが fit を過度に支配しないよう重みを決める。

選択指標 `C2 strict + 0.5*C1` は、事前に決めた開発上の効用としては使えるが、本番の Class 比率を表すものではない。現在の C1 は重複込み・小標本なので、この一値だけでモデルを選ばない。C1/C2 の個別値、参照正解を落とした件数、低文献数群の値を並べる。合成指標の区間を作る場合は、同じ identity の二条件をまとめて再標本化する。

## 8. 質問 5: FP 窓採点がボトルネックの場合の優先順位

**K の縮小は、窓全体の FP を計算した後の処理なので、主として GL/ICE の時間を減らす。FP 全件採点の解決策とは分ける。** 優先順位は次の通り。

| 優先 | 対応 | 理由と確認する指標 |
|---|---|---|
| 1 | 段階別時間を測り、重複計算・thread 過剰を除く | parse/key、fingerprint、参照検索、forward を分離。Spark 2秒/分子を Kaggle 4 CPU の時間と見なさない |
| 2 | 重なる adduct 窓をまとめ、同じ SMILES の静的計算を再利用する | 現行は adduct ごとの候補を連結してから `_feat` を呼ぶため、重なった候補の FP を繰り返し計算し得る。出典・窓情報を保って先に重複を除く |
| 3 | 部分 fingerprint の pass-1 → full FP の pass-2 | full FP の対象を減らせる。参照検索の強い候補と prior 枠を保持し、正解到達率の減少と時間を比較する |
| 4 | forward の対象 K を縮小、または優先順位付きで計算 | GPU/runner が支配的な場合に使う。固定候補上で K=60/100 等の回収率・MRR・fallback を測る |
| 5 | ppm 窓の縮小 | 正解が後段から戻せなくなるため最後。校正・adduct 整合・到達率の実測なしに狭めない |

部分 fingerprint の上位数は、最初から K=100 に直結させない。安価な pass-1 で数千候補を残し、full FP と参照/prior の候補を経て最終 shortlist にする形がよい。P1 の全候補 full FP を対照にし、どの質量・候補数・adduct で正解を落とすかを記録する。

参照検索も候補数×参照数×query スペクトル数で増える。CPU 時間がここに偏っている場合は、full FP の pass-1 だけでは速くならない。参照の cleaning と適合条件を cache し、同じ比較を C1/C2 用に繰り返さない。duplicate 判定で計算した similarity を、その後の本スコア計算でも再利用できる。

最終的には「残り時間 − 出力・検証の余裕」に基づいて forward の実行量を決め、計算できない分子も FP+prior で提出を完成させる。同じ cutoff/fallback をローカル評価に入れる。Kaggle 可視 test は本番とは候補分布も参照条件も違うので、総時間に加えて候補数・query 数・adduct 数の分布を残す。

## 9. 次の一巡で確認したいこと

大きな手法追加より先に、次を一つの版として揃えることを勧める。

1. C1/C2 別 shortlist、出典なし候補の除去、B1 の実窓による reach、空候補込みの分母を共通化する。
2. 重複除外前後の参照件数・消えた非正解参照も記録し、確実な複製と高類似の疑い群を分ける。
3. λ の候補選択／最終融合を分離し、評価と提出の query 選択、候補源、参照上限を揃える。現在は評価側 MAX_Q=8 の adduct を分散した選択、提出側 MAX_Q=16 の順序選択、評価側には追加 COCONUT store、提出側は tier+pool という差もある。
4. 同じ候補とスコアで固定 S(0.5)、参照基準、学習融合を比較する。locked eval は設定確定後に使う。

既存 forward スコアは再利用し、候補の追加分と変更した query だけを主担当の Spark 環境で再計算すればよい。最終的な順位は公式 scorer にも通し、独自の worst-case tie 計算だけで提出順との一致を判断しない。
