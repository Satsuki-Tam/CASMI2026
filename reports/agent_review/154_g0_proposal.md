# 154 G0 の提案(2026-10-30 15:12 JST、Claude Code)— CASMI のハーネスのワークスペース v1 の CV・指標・fold・資源

利用者の指示(ハーネス v1 を導入し、以後それに従う)を受けた、最初のワークスペースの設計案。G0 は利用者が自分の端末で承認する。承認の前に Codex が Critic として点検する。

## 1. 何をこのワークスペースの課題にするか
- **W135 の世界での「最終の並べ替え」**。候補の母集団を固定した学習した採点器(153 の FH の系統)を、ハーネスの内側のループで改善していく。
- 理由: 0.500 までの主な損失は、COCONUT の異性体の順位と class 3 で、どちらも「最終の候補表で何を何位に置くか」に集約できる(152 / 153)。W135 の世界は、class 1 / 2 / 3 の混合と、バッチ単位の知識の mask を再現した、手持ちで最も隠しテストに近い開発の設計である。
- 上流(P = v8w7a、生成 B、GLACIER、fold-safe FPNet)は固定した資源(G4)として扱う。新しい証拠(例: 極性の観測の型)は、同じ候補の母集団に付ける特徴の資源として G4 で追加する。候補の母集団自体を変える変更(E2 の候補を足す等)は、新しいワークスペース(または G0 の版上げ)にする。

## 2. 評価の単位と fold
- 単位: W135 の 31 世界の全 query(3,095)。d 側(fold 1)6 バッチ × π3 {0, 0.3, 0.6}、c 側(fold 2)6 バッチ × π3 {0, 0.3} + cU1 の π3 0.3。
- **fold: バッチの組ごとの 7 fold**(d1 = dF1 + dR1、d2、d3、c1、c2、c3、cU1)。同じ identity の π 違いの世界は同じ fold に入る。確認済み: scorer key・identity group・構造の家族が、バッチをまたぐことは 0 件。
- 候補の母集団(1 query あたり最大 75 枠): P の上位 25(v8w7a の世界の P、P が選んだ SMILES)+ 生成物 B(最大 50、P の上位 25 と official key が交わらない)。枠の順は P の順位 → 生成器の順。足りない枠は無効の旗。

## 3. 指標(src/metrics.py)
- MRR@25: 各 query で、有効な枠を予測値の降順(同点は枠の順)に並べ、上位 25 件の中の正解(scorer key)の逆順位。正解が候補に無ければ 0。
- **主指標 = π3 0.3 の世界の query の平均**(1,297 query。139 / 153 の主指標と同じ)。部分集合に π3 0.3 の query が無いとき(π0 / π0.6 のスライス)は、その部分集合の全 query の平均を返す(スライスの記述用)。
- row_errors = 1 − RR(全 query)。予測は有限値だけ(無効の枠は −1e9 を推奨。指標は無効の枠を予測値によらず無視する)。
- スライス: pi0 / pi30 / pi60、π3 0.3 の C1 / C2 / C3、π3 0 の C1 / C2、d / c 側、P が空、GL の経路。

## 4. test と holdout
- **test_ids = fold 0 の e バッチ(eF1–3 / eR1–3)の π3 0.3 と 0 の世界の query**(約 1,192)。いま Spark で世界を作成中(15:10 開始、データだけ)。
- ワークスペースには e の特徴だけを置き、正解は置かない。正解は CASMI リポジトリ側に保管し、最終候補を人間が選んだ後の一回だけの holdout の評価に使う(ハーネスの「自動探索で評価しない」)。
- e は「FH / W135 の設計・学習から保留した fold 0 での確認。以前の B1 の開発で既使用の identity を含む」(Codex 153)。

## 5. 学習の adapter と基準(src/adapter.py)
- 設定 `mode: p_order` = P の順をそのまま返す(決定的。σ = 0 の参照)。
- 設定 `mode: fh` = 153 の FH v0(LightGBM の二値、37 特徴、num_leaves 15、300 rounds 等)。学習は train fold の全 π の query、identity の重み = 1/(含まれる世界の数)、行の重み = 1/|U|。arm は db / gen。
- 基準(G0 の後): `fh` gen の同じ設定で seed 11 / 12 / 13 → σ。P の順は別の参照の実験として登録する。
- 153 の FH v0 の結果(π0.3 で P 比 +0.0097 / +0.0129、生成物は 1 位に出ない)は、このワークスペースでの事前の情報として problem_model に記録する(ハーネスの外で得た結果であることを明記)。

## 6. 資源(G4 で承認)
- res-w135-u-dev-v1: 31 の開発世界の U / Q の表(CASMI の experiments/w135/w135_fh.py sha 2e404100… で作成、各表の sha を一覧)。上流: v8w7a(自前)、b1_gen v2(自前)、GLACIER の公開重み、公開の fold-safe FPNet(学習コードつき)、PubChem tier / PubChemLite / COCONUT / ChEBI・LIPID MAPS、競技の train スペクトル。
- res-w135-u-hold-e-v1: e の世界の U / Q の表(特徴だけ。作成後に sha を付けて登録)。
- 外部のモデル・データを新しく使う変更は、別の資源として G4。

## 7. 計算資源・予算・モデル(G0 で決めること)
- 実行の場所: Windows の PC(Claude Code と同じ機械)。sandbox は `local`(bubblewrap は Linux 専用のため。**学習プロセスの OS 隔離が無いことを逸脱として記録**)。CPU だけ(gpus_per_job 0、max_concurrent 2、timeout 60 分)。GPU の上流の計算は、ハーネスの外で作った資源を G4 で取り込む。
- Python: CASMI の `.venv`(numpy・PyYAML・pandas・pyarrow・LightGBM を含む)。ワークスペースで Claude Code を起動する前に、この venv を有効にして `python` がこれを指すようにする(PATH 上の `python` はいま Microsoft Store のスタブで、そのままだとフックが全て失敗する)。
- モデル: claude = claude-opus-5-5、codex = 利用者に確認(Judge の採点に必須)、gemini = 未導入(Claude で代替し記録)。
- 予算: GPU 時間(v1 は CPU だけ)、API の USD(Judge / Ideator の CLI 呼び出し)は利用者が決める。
- 再構成の G1 不在時の自動採用: 既定どおり無効。

## 8. 既知の限界(承認の前に共有)
- W135 の分子は主に公開ライブラリのスペクトル(timsTOF は少ない)で、Enveda の取り方ではない。π3 0.3 は隠しテストの比率の推定ではなく、開発の主な混合として選んだもの。
- 候補の母集団の固定により、E2 の候補・新しい生成の方式・窓の拡張は、このワークスペースでは測れない(新しいワークスペースで)。
- Public LB は最適化の目的にしない(違和感の検出だけ)。0.500 の目標とは、この CV と Public の関係を違和感の監視で確かめながら付き合う。
- Kaggle への組み込み(FH を提出用のカーネルに入れる)は、CV の外の工程(G3 の前に parity を確認)。
