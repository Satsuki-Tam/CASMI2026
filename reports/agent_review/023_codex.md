# 023 レビュー: full_evalの判断、既見領域、T/N probe

2026-10-25。**full_evalは022の「非劣性未確定だが一回の比較提出は可」に該当する。容量・作業負担を理由に今夜保留する選択は妥当だが、期待利得がほぼ無いという推定には同意しない。** T/Nは二本そろえば固定ランキングの有用な診断になる。ただし、測るのはtrain所属による分割の効果であり、C1/C2の寄与やE0との差の所在そのものではない。

私なら、アップロードが現実的に可能ならfull_evalの一回の直接比較を優先する。容量制約が解決できず見送る場合、T/N二本へ振り替える案は、以下の定義・読み方・実装確認を固定することを条件に支持する。

**Q1 — 022の判定には同意。見送り理由は性能判定と分ける**

保存予測からclean 202分子のΔを再集計し、**+0.035033、95%区間 [+0.008969,+0.062041]**を確認した。uncertain 48は+0.010417 [−0.020833,+0.041667]。dev2の全保護層の点推定は−0.02以上だが、挙げられた7層で下限が−0.02未満であり、非劣性未確定という判定は正しい。

parityもC1/C2それぞれ16分子で、query差0、主出力・保険のtop-1/RR/集合/順序付きtop25が16/16一致していることを確認した。従って「比較提出できる候補」である。これは「提出しなければならない」という意味ではなく、保留しても性能上の判定はそのまま記録する。

直接提出から得られる情報は、**実際の隠し集合・既見性の混合・候補生成・forward・融合を通した、FPNet置換全体のΔPublic**である。T/N probeは別の問いで、この情報を代替しない。容量制約が理由なら「比較可能だが資源配分により保留」と記載し、「利得がほぼ確実に0.02未満なので無価値」とは書かない。

**Q2 — 約80%という基準集団の数字は正しいが、隠しへの移し方が強すぎる**

`make_split.py`は指定foldとNP-example群を除外し、`SPLIT_AUDIT.json`は学習identity key 219,155、除外55,031を記録する。元の学習対象の約80%を学習側に置いたという理解は妥当。パネルはfold番号にかかわらず群全体が除外され、従来のfold0ベースの開発配置はFPNetに未見のidentityを中心に測っていた。この点は、C1-seen行をrankerへ加える重要な動機になる。

ただし次は別々の仮定である。

- **公開参照あり＝このtrainにある、ではない。** train外の公開ライブラリ分子もC1になり得る。学習済み率80%が適用されるのは、学習対象の台帳に入る分子という条件の下である。
- foldはidentity群をseed付きで分割し、Enveda由来比率も揃えたもの。隠しC1が元の全学習分子から一様抽出された保証はない。パネル群との重複、化学領域・出典・質量帯、小さい隠し標本のばらつきもある。SPLIT_AUDIT自身も、歴史的batchでの露出を再構築した監査ではないと明記している。
- **full_evalが予測を変えるのは未学習だった約20%だけ、ではない。** 新しい学習データと学習過程で重み全体が変わるため、元から既見のC1、train外C1、C2/3でもFP値・順位・候補・融合結果は変わる。dev2の区間が広い結果を「C2/3への差は0」と置くこともできない。
- パネルのfold0→full_eval差は「未見→既見」に加え、学習データ量等も変わった比較である。これを隠しの未見20%へ一律に掛け、他群を差0とするのは感度シナリオに留まる。p1=0.3〜0.5も観測値ではない。なお提示した積そのものの範囲は0.0018〜0.005で、0.008には別の仮定が必要になる。

従って、既見性を考慮した評価が必要という帰結には賛成するが、これでfull_evalのPublic利得を小さく上限づけることはできない。

また、現行fold0で「既見identity・未見query」を作れないというのは、**元の学習コーパス内の取得だけを使う場合の制約**である。同じidentityの、元の学習コーパス外の独立した取得が入手できれば評価できる。full_rk/full_evalで作る条件も有用だが、異なるcheckpoint上の代理である点は残る。

**Q3 — T/Nの代数は、train所属と固定順位を厳密に定義すれば成立する**

まずTを「公式scorerで正規化したidentityがtrainに存在する」、Nをその補集合と定義する。**T/NはC1/C2のラベルではない。** Nにはtrain外の公開参照を持つC1も含まれ得る。Nの得点がC2寄与と等しいとは言わない。

全分子・同じ分母で、元出力Mのうち真がT/Nに属する寄与をM_T/M_Nとする。同じ候補集合・完全な順位列から、所属だけで絞ってtop25を作り、空の代替出力が偶然正解しない条件では、

`M = M_T + M_N`

`P_T = M_T + G_T`、`P_N = M_N + G_N`、`G_T,G_N ≥ 0`

となる。従って、`P_T + P_N − M = G_T + G_N`は、**真のtrain所属を知るoracleが、現在の候補と群内順位を固定したまま得る改善量**である。候補生成・群内再順位付けまで改善した手法全般の上限ではない。また、現実の観測特徴でそのoracleを近似できると示したことにもならない。

二本から元出力の寄与に付けられる範囲は、

`max(0, M−P_N) ≤ M_T ≤ min(M, P_T)`

`max(0, M−P_T) ≤ M_N ≤ min(M, P_N)`

である。真がTにある比率p_Tについては、`P_T ≤ p_T ≤ 1−P_N`という範囲まで。P_Tをそのままクラス1比率や元のクラス1寄与と置かない。

**in_trainの判定は、現在のwindow内フラグだけでは厳密なtrain所属にならない。** 確認したコードは、窓に入ったpoolのsource bitをORし、shortlist内の公式identityへ集約する。一方でC2評価ではそのフラグを書き換える。窓外の表記や未収載の構造もあるので、意味を固定したglobal集合を別に使うのがよい。

実測では、`data/processed/train_scorer_keys.parquet`の`scorer_ik14`のunique集合は **274,195**、poolのtrain bit集合は **274,186**で、**global trainにだけある9 key**があった（逆差0）。差は小さいが同一ではない。global train集合を固定し、各`rows[i]["key"]`をそこで判定する。poolを使った高速な集合構築でも、この差とscorer版を照合する。`official_keys_of_train()`は確認時点で`return None`のstubなので、関数名だけを根拠にglobal照合済みとは扱わない。

実装上の最低条件は以下。

1. **上流を変えず、top25への切詰め前の全順位列をfilterする。** モデル・候補生成・prior・forward・blend・fallbackは元のM2xと同じ。公式identityで重複を統合し、TとNは互斥かつ全候補を被覆する。確認時点のコードは同じ`order`から両probe CSVを生成しており、この位置はよい。
2. **元出力、T、Nを各run内で同時に保存する。** 各提出の最終`submission.csv`へどれを出すかを明示し、元出力の選択ミスを防ぐ。probe無効時の出力が凍結基準と同じであること、順位が相対的に保持されることを確認する。
3. **空出力を別に監査する。** `CCO`を使うなら、対象の質量条件で正解にならないことと、空になった分子数を記録する。そうでなければ反対群のRR=0という式に例外ができる。候補ゼロの分子も分母から落とさない。
4. **ローカルでは分子別に不等式を検査する。** train由来集合をglobal Tで分けると真が全てTになるので、それだけでN側を検証したとは言わない。Nの正解を持つ条件は、既存C2の反実仮想でheld-out identityをTから除いた検査等で補い、global所属での性能診断とは区別する。

**Public二本と過去0.354には、同じ完全順位列という保証がない。** 同じコードでも隠し再実行は別になり、FP/forwardの数値差、候補境界、時間予算・欠損で順位列が変わり得る。`submission_unfiltered.csv`を保存しても、その隠し版のMRRを手元で確認できるわけではない。従ってPublicでの`P_T+P_N−0.354`は、同じ順位付けを再現できる範囲での近似測定とし、丸めと実行差も注記する。ローカルでは同一保存スコアを使った等式が成立することを確認する。

読みの表は次に置き換える。

| 観測 | 言えること／次の行動 |
|---|---|
| P_T+P_N−M ≥ 0.05 | この順位列では群をまたぐ候補の競合を除く余地が大きい。ローカルで観測可能特徴によるgateやヘッジを検証する。クラス判定可能性やE0との差の原因は未証明 |
| P_N ≤ 0.05 | 元出力の**N所属の真からの寄与は高々0.05**。Nの頻度が低いのか、候補不在か、群内順位が悪いのかは分離できない |
| P_Tが高くP_Nが小さい | M_Tは少なくともM−P_N。元出力がT側から多く得点しているという理解はできるが、E0が追加で得る0.11がT側かN側かは分からない |
| 和がMを明瞭に下回る、または1を超える | 同一順位・互斥性・key判定・空出力・実行差を点検する。Publicの丸めや別実行を無視して直ちにクラス構成を解釈しない |

**二枠の価値は目的次第だが、提案の競合量を測るならT/N両方が必要。T一本では足りない。** T一本からはM_Tの上限等しか付かず、P_Nとoracle差を復元できない。もし一枠に絞り、問いを「train外側の寄与がどこまであり得るか」に限定するなら、むしろNを優先する。どちらの場合も「B1がT中心だからE0との差もC1にある」という帰結は取り除く。

この固定ルールの全分子共通ablationを行うなら、対象と解釈を提出前に記録する。Publicから個別test記録のラベルを作って予測へ組み込む実験とは区別する。公式規定は人手によるvalidation/test記録のラベルや予測情報の利用を禁止し、現在の日上限は5件である。[公式Rules](https://www.kaggle.com/competitions/enveda-CASMI26-molecule-id-mass-spectra/rules)

**Q4 — full_rkでは「C1-seenを足す」だけでなく、適用先まで固定して比較する**

1. 19:25頃の学習完了後、final checkpoint・hash・コード/設定・除外と露出台帳を保存し、Sparkへ引き継ぐ。20:50までにローカル処理を終える条件を維持する。今夜中に新rankerまで完成させることを学習完了の条件にしない。
2. p1のC2-unseen/C1-unseen、W7/eval_c1のC1を、実際の残存学習取得数でタグ付けして学習表を作る。C1 usableとFPNetの既見性は別なので、全てのW7 C1を一律にseen扱いしない。fit/tune/evalを維持し、C1/C2の有効群数・重みを先に固定する。パネルはranker学習へ入れない。
3. まず**full_rk＋旧v4b 対 full_rk＋新ranker**。同じFPNet、候補、forward、出力方針で、C1-seen/unseenと未見C2を分けて見る。T/N gate、pool60、PCL加点をこの比較に混ぜない。
4. 新rankerを現行fold0へ移すなら、**fold0＋旧ranker 対 fold0＋新ranker**を別に確認する。raw FPの尺度や誤り方が異なるため、full_rk上で良いことだけで移植成功とはしない。既存のfold0パネルはunseenなので、この試験だけでfold0の隠しC1-seenを検証したことにもならない。
5. 比較が良ければ、学習表と同じfull_rkを使う候補をまず検討する。全量への再学習やfold0への移植は必須ではない。T/N probeが大きいoracle差を示しても、観測可能な情報でその差を回収できるかは別の一対比較にする。
