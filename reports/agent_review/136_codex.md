- 旧評価器：`3f7d3dc4…`、新評価器：`33250ca4…`。手元の新評価器の hash は後者と一致した。
- 判断 reader：`01518c0d…` のままで、手元のファイルとも一致した。
- モデル・得点 JSON・学習コードの manifest 行は変わっていない。

## Q2：共通世界と情報条件

### 支持する部分

バッチ全体で C2/C3 の参照を隠し、全 query の P を一度作り、その P から peer を取る構成は135の要求に沿う。`b1_world.py:123–145,207–234` は raw / pool / identity group / tautomer / official key を使った mask を作り、`w135_p.py:59–99` は同じ mask を analog に適用している。生成後に C3 の正解を再び排除する処理も見当たらない。

手元の選択 CSV でも、開発6バッチが各100 identity で、fold 内の identity group と家族がバッチ間で重複しないこと、CSV hash が登録と一致することを確認した。ただし、これと既存 C2 parity の合格だけで新しい world mask の正しさまで証明したことにはならない。

### (a) C2 は妥当。C1 の適格性は実際の除外後に確認する

C2 を「train 以外にも構造がある分子」に限るのは正しい。COCONUT 所属の母集団なら条件を満たし得る。最終的には raw key だけでなく、採点で使う official identity が非 train 資産に残ることを確認する。質量窓に入るか、shortlist に入るかは別の測定対象であり、適格性に順位やモデル得点を使わない。

**C1 の現在の適格性は、要求した条件の近似にとどまる。** `w135_batches.py:38–56` は `(adduct, precursor 3桁, CE 1桁, n_peaks)` の組を比較する。一方、world は cleaned peaks の exact / suspected 判定を使う。メタデータが違う複製を C1 適格と数えたり、メタデータが一致する独立取得を除いたりできる。さらに、前者は丸めた CE で query を選び、world は元の CE で選んでいる。`b1_world.py:326` の `c1_usable` も実測ではなく、C1 と割り当てたかどうかの値である。

full mode 前に、**world と同じ query 行・同じ極性条件・同じ exact/suspected 除外後に、有効な独立参照が1本以上残ること**を監査する。`n_ref_after_world_mask` と選択 query / 参照 row ID を残し、analog の代表も確認する。ここでの「独立」はこの重複除去規則を通った代理であり、取得履歴による独立性の証明とは区別する。

不適格者がいれば、結果を読む前に適格性を訂正し、同じ hash 順の割当規則を再適用する。C3 の入れ子集合は維持し、変更された世界の参照・train flag・P・親 bank を更新する。**表の C1 ラベルだけを書き換えて済ませない。** 不適格者が0なら既存世界を再計算する必要はない。C1 が21〜32で変動すること自体は許容できるが、これは C1/C2 半々の世界ではなく、実際の比率を持つ世界として報告する。

### (b) C1 analog の再選択の向きは正しい

`w135_p.py:59–63` は選択 library と `c1_excl` の行を除いてから `Store.pick` を適用し、元の C1 代表を検索対象から外して代替代表をマージする。したがって、「最初の代表が除かれたので独立参照まで失う」実装にはなっていない。

追加で必要なのは、性能を使わない次の不変条件の確認である。

- C1 の代替代表は自分の query library / exact / suspected 除外行に含まれない。別の query が検索した場合にも同じ禁止行を使わない。
- C2/C3 の全 official key が analog 出力から消えている。
- C3 の key が raw window、shortlist、P top25、train 親へ戻らない。生成された候補はこの禁止対象に含めない。

既存の `--parity_c2` はこの C1 の再選択分岐を通らない。小さな C1 fixture で、元代表が複製、代替代表が独立、代替なし、という境界を確認すればよく、性能比較を追加する必要はない。

### (c) KEY_SMI が存在するだけでは漏洩ではない。ただし利用境界を閉じる

読んだ経路では、`KEY_SMI` を全件から探索して C3 の親を追加する処理はなく、mask 済み analog key に対する構造の取得に使っている。人気度は C3 候補を取り除いた後の候補に計算される。この意味で、**C3 の表がメモリにあること自体を、実際に真を使った証拠とは判断しない**。

ただし `w135_gen.py` は `world_masks.json` を直接読み直さず、P の親リストが正しいことに依存する。生成前に親の official key と train-hide の整合を assert し、実際に使った親 key・由来・類似度を保存してほしい。C2 が構造 DB 経由で peer の予測となるのは合法なので、peer 全体に train-hide を適用してはいけない。禁止するのは、C2/C3 の隠した参照を train 親として使うことと、C3 の構造が P に残ることである。

将来、生成候補の人気度・source 特徴を作る場合も world 側の資産を参照する。元の未マスク表への照会で、C3 の既知所属や人気度を復元しない。一方、COCONUT / PubChem の公開属性が利用可能な C2 まで、一律に未知扱いにする必要はない。

## Q3：生成、B、oracle、判断表

### 親選択：主案は支持。二つの境界を明記する

P top1 の構造、query 由来の中性質量、編集集合の質量差、query-query 類似度だけで選ぶ案は label-free であり、正解構造から「届く親」を選んでいない。この設計で進めてよい。

ただし現実装には次のずれがある。

1. **比較可能な極性がない peer も選べる。** `qq_sim` は比較対がなくても0を返し、親選択は0を排除しない（`w135_gen.py:110–115,129–135`）。同極性の有効なスペクトル対を少なくとも一つ持つ peer に限ることを明示し、存在しない場合は候補から除く。有効な比較の結果が0の場合を許すかは別の規則であり、今固定する。新しい類似度閾値の探索は不要。
2. 現在は **上位10 query を取ってから構造を重複除去**する。同じ top1 構造が10件続けば peer 親は1種類になり、11番目以降で埋めない。また train と重なった peer は train 側が優先される。「最大10の query を選んでから重複除去」と登録に明記すれば整合する。意図が「異なる構造の上位10親」なら、今のうちに official key でまとめて最大類似度の代表を残し、上位10を取る実装に直す。私は後者を推すが、これは漏洩の修正ではなく親予算の定義である。

どちらの定義でも自己 query は除き、同じ構造を多数の独立票として数えず、train / peer の両方から来た由来は記録する。

### B=50：維持してよい。実行可能性は別に測る

到達を見る前に速度と件数で固定しているので、初回の採点予算として妥当である。B10/25/100/all は記述にとどめ、見た後に良い B を主結果へ差し替えない。

ただし B は採点件数の上限で、生成時間の上限ではない。`b1_gen.BUDGET=600` は `derive` 一回、すなわち親ごとの編集処理予算で、query 全体600回ではない。親10+10、親あたり300件なら、重複除去前には最大約6,000件になり得る。「約8万 GL job が Kaggle に収まる」は現時点では見積りとして記録し、段階2以後に全パイプラインの所要時間を確認する。時間打切りを追加した時点の候補集合が、最終的な採用評価の対象になる。

### `novel` の定義と alias の保存を修正する

**現在の `novel` は「world DB にない」ではない。** `w135_gen.py:89–90,151–155` が見るのは query の raw window key と shortlist の official key である。DB にあるが質量窓の外の構造や、shortlist 外の別 raw alias は `novel` になり得る。生成の許容誤差は最低2 mDaで、DB の10 ppm窓とも常に同じではない。

さらに `gen_job:71–75` は同じ official key で高い f.z の SMILES を採用しても `rk` を更新しない。保存された SMILES と raw key が別の代表になり、この誤分類を増やせる。代表を変更するなら raw key も一緒に更新し、DB 所属の判定は代表一つの raw key に依存させない。

登録した分類を実装するなら、world の各資産に対する official identity の所属を用い、少なくとも「P top25」「DB内・top25外」「DB不在」を分ける。質量窓外は別の補助列にする。巨大な全資産を毎回変換する必要はなく、固定した索引や生成候補へのキャッシュ付き照会でよい。全 DB 所属を実装しない場合は `novel` を `out_of_window` と改称し、DB不在という主張・漏洩判定には使わない旨を登録する必要がある。

これは主に分類・監査の問題である。現在の事前選別は window と novel の両方を残すので、**この指摘だけから U が水増しされているとは言わない**。しかし現在の reader の「C3 の生成された真が short/window なら停止」だけでは、C3 の DB 不在を保証できない。真が生成されなかった場合には、その検査自体が働かないため、world 資産側でも独立に確認する。

### U の式は正しい。全件分母と前提を機械的に確認する

`T25_i` を P の提出上位25、`B_i` をそこから official key で重複を除いた生成・事前選別集合とすると、

`U = mean_i 1[y_i in B_i]`

は「正解が B にあるときだけ1位へ挿入し、他では P を保持する」oracle の P に対する MRR@25 差になる。`y_i in B_i` なら P の得点は0だからである。したがって、**許された action の到達上限として採用してよい。実際の方策の利得ではない。**

reader には次を追加する。

- batch / world / P / generation の `(set, molecule)` が一対一で完全一致。欠落だけでなく余分な行・重複も STOP。現在の `set` 差と通常の `merge` では重複行を防げない。
- `reach=True` なら `main==0`、`rP` は0または25超、真の official key は P top25 にない。B は official key で unique、長さ50以下。
- 空の P、親0、生成物0、B0も一行を残す。到達不能は0、欠損・実行失敗は STOP と区別する。
- `reach` と登録した B、`truth_rank_fz` が整合し、FP / 質量 / 順序の必要値は有限である。

`w135_gen.py:109` の入力集合の共通部分だけを黙って処理する方式より、生成開始前に roster の等値を確認する方がよい。C3 と C1/C2 の寄与は、各群内の平均だけでなく全 query 分母の寄与として足し合わせ、`U=U_C3+U_DBmiss` を確認する。B、親一覧、候補順の hash も残すと、後の selector が同じ集合を使ったか検算できる。

### CI と拡張規則は修正してから固定する

**現在の家族をバッチ内で resample する CI を、新しいバッチへの不確実性の主区間には使わない。** 一つの peer の正しい top1 が別家族にも効くため、依存は Butina 家族の境界を越える。`w135_read.py:40–48` は元バッチを固定しており、この変動を含まない。

主たる読みは6バッチの U と家族型・無作為型の各平均を併記し、外側を丸ごとのバッチ単位にする。対応を保つなら `(dFj,dRj)` の3組を復元抽出し、各組内の全 query を保持して50:50の設計平均を計算する。4,000回・seed136は維持できる。ただし独立単位が3組しかない段階の区間は探索的なものと明記する。現行の家族 bootstrap を残すなら、固定済みの peer 環境に条件付けた補助値として分ける。

INVEST / LIMITED は小さな次段への投資判断としてよい。LIMITED の境界は `0.02 <= U < 0.04` と明記する。全バッチ0などで percentile bootstrap の上限も0になっても、母集団の上限0を証明したことにはならない。STOP はこの凍結方式への工学的な投資停止と区別し、不確実性を根拠にした判断ならその場合は UNDETERMINED とする。

**dF4–6 / dR4–6 は、現状では「登録済みの拡張」と呼ぶには未完成である。** `w135_batches.py` は全 family batch を作った後に random batch を作る。単純に `n_family=6,n_random=6` で再実行すると、既存 dR1–3 の選択候補まで変わり得る。初回6バッチの identity と家族を固定・除外して追加を作る方法、追加可能数、hash、総分母、最大一回の拡張、最終的にも未確定の場合の扱いを初回 U の前に決める。

追加集合を今固定できなければ、初回は UNDETERMINED で止め、追加は別登録の追試とする。都合のよい区間が出るまで繰り返す規則にはしない。拡張を選択した後の通常の95%区間を、逐次判断全体で95%を保証する区間とも呼ばない。

## Q4：確認用の予約

**現状の3バッチだけでは、独立な有効性と C1 費用の両方を確認するには足りない。段階1の実現性測定を止める理由にはしなくてよい。**

手元の `c_manifest.json` / CSV は cF1・cR1・cU1 がそれぞれ **99件**。cF1 は66件、cR1 は68件が used、cU1 は used=0だが C1 は1件である。登録・reader は実数99を使う。cF/R は W135 の新しい条件での再現・保護の検査として有用だが、既使用 identity を新たに独立確認と呼び直さない。cU は未使用 identity での C2/C3 確認として残し、C1 の非劣性を保証する役割は持たせない。

また家族は fold ごとに別々にクラスタリングされている。各 fold 内の `fam` 不一致や重複なしは、fold1とfold2で構造家族が未見であることを保証しない。census の used 判定も `p[0-9]*_molecules.csv` と既存 `in_dev` を主に使っており、「全ての利用履歴を網羅した」とはコードだけでは断定できない。

段階2を登録する前に、次の形にするのを推す。

1. **未使用 identity の家族型・無作為型を複数予約する。** 選択用・selector学習用との構造近縁性を同一の家族定義で監査する。厳密な家族未見を求める場合は、fold別の番号でなく共通の構造クラスタや固定した近縁判定で隔離する。単に「別 Butina cluster」だけで全ペアが低類似度になるわけでもない。
2. **C1 保護用には、実際の除外後にも参照がある別群を確保する。** C3 混合世界と π3=0 の世界で、同じ凍結方策による費用を見る。既存 cF/R は補助に残す。未使用の C1 が十分になければ、独立 C1 保護は未確認と明記し、cU の結果から補わない。
3. 使用済み roster・学習 roster・panel / MSG を official key と全体共通 identity group へ写して除外する。`w135_census.py` の panel 除外は raw key なので、別 raw alias が同一 group として残らないかも確認する。選択には性能を使わない。

この追加設計は結果を見て良い家族を選ぶためではなく、確認の役割を分けるためである。現母集団は COCONUT に載る公開スペクトル保有分子、query は timsTOF 以外が中心である。本物の C3、新しい骨格、timsTOF の合成 NP 様分子への利得は、ここからそのまま保証できない。N=100から本番規模へ広げた際の peer の機会数も別に確認する。

## Q5：full mode 前に行う修正と、実行を再開する条件

優先順は次のとおり。

| 順序 | 必須の対応 | 既存 world の再計算 |
|---|---|---|
| 1 | C1 の実参照適格性、query 行、C2/C3 資産・親 mask の不変条件を確認する | 割当・利用資産が変わった世界だけ必要 |
| 2 | peer の極性条件・重複除去と親数の定義、alias 代表の raw key、novel の意味を訂正する | 親選択・生成側だけなら P / GL は再利用可 |
| 3 | roster 一対一、空行、oracle 前提、B=50 と有限値の検査を加える | 通常は不要 |
| 4 | バッチ依存を扱う CI、追加バッチの固定方法、終了規則を登録する | 不要 |
| 5 | 実行前の provenance 確認と、結果ファイルの出自を固定する | 入力・モデルが同じなら不要 |

5について、現状の `manifest.txt` は生成物・world出力と一部のソースを固定している一方、生成の本体 `b1_gen.py`、reader、親計算の依存コード、P のモデル、FP bit 順、実行引数などを十分に束ねていない。reader も full-mode parquet の生成時の code / input / 引数との対応を確認できない。既存の資産 manifest を参照する方法でよいので、これらを run manifest に含め、**生成前**に照合し、生成出力の hash と終了状態を保存する。大きな資産を毎回読み直してハッシュする必要はない。

world 構築時と生成時で `fp_bits.npy` が同じ順序であることも確認する。world は fold1/2 用ディレクトリを使うが、生成は既定の `fold_safe_fpnet` から bit 配列を読む。生成が別 fold の FPNet を再推論しているわけではないため、これだけで漏洩とは言わないが、bit 順不一致は f.z を壊す。

`spark_w135_stage1.sh` は world の DONE 文字列だけで進まず、manifest と必要な schema を先に確認する。`spark_w135_p30_rest.sh` は子ジョブが失敗しても後続を実行し、最後に DONE を表示し得るので、各子の終了値を集約して失敗を返す。parity も PASS の文字列だけでなく roster と非0終了値で担保する。現在の `w135_parity_tables.py` は new に現れた分子に ref を絞るため、想定した12分子の一部が丸ごと欠落しても検知できない。`w135_p.py` の parity FAIL も終了値へ反映する。

実行中の世界構築に使っているコードを途中で差し替えず、修正版・旧 manifest を分ける。単なる reader / generator の修正で既存 world のコード hash が変わった場合も、古い manifest を上書きして履歴を消さず、再利用する出力と変更箇所を記録する。
