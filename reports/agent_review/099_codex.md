**探索する価値はある。ただし現在のC3評価は、他分子のC2予測をそのまま親にするため、バッチ全体の「未知構造・参照なし」という条件が揃っていない。099のA〜Dは探索として記録し、採否の前には、全queryが同じ利用可能DB・参照を共有する評価を作ることを推す。** 最初の提出候補は、親の予測を一度だけ作るtest側生成と3位挿入に限定し、DB候補への加点は別に扱う。

**Q1: 30%は家族構造を調べる根拠になるが、隠しでの到達率や実用利得ではない。**

`tgen_panel.py`は、親に真の構造を使うだけでなく、対象質量も`ExactMolWt(真の構造)`から作っている。75/250は、**この親集合・真の質量・編集集合・探索上限の下で、正解keyを生成できた対象の割合**である。実際にはquery由来の質量、予測した親、列挙された多数の異性体からの選択、挿入gateが必要になる。

また、真の親集合と予測した親集合は異なるため、30%は予測親を使う全方式に対する厳密な上限ではない。誤予測された構造が偶然よい親になることもある。「真の親を与えたoracle到達率」と呼ぶのが正確である。099登録の「親の正答率分だけ下がる」も一般には成立しない。一つの対象に親が複数あり、親の誤りは家族内で相関し、誤った親も大量の候補を生むためである。

パネルと無作為NP集合の差には、家族の密度だけでなく、集合サイズ、化学領域、有名さ、使った変換との相性が含まれる。同じEnvedaの装置・NPというだけでは、隠しにも同じ家族密度があるとは言えない。まずquery由来質量でのoracle到達、予測親での到達、生成物内の正解順位、gate通過、最終RRを分けて記録する。

**最優先の修正は、親bankとC3 viewの整合である。** 現行コードは`--tparents`の入力を常に`view == c2, rank == 1`へ絞り、C1/C2/C3の全viewに使う。C3のtrain親はUNION maskを通すが、その後にtest親を置き換え/追加する部分は、そのC2予測bankをそのまま使う。

これでは、C3扱いの分子iの正解構造が、別の分子jの候補DBやラベル付き参照・analogに残り、jの予測を通じてiへ戻る可能性がある。`i != j`だけでは防げない。例えば未知の配糖体iのラベル付き参照を使って、別の分子jの予測を強めてしまうと、そのjを親にiを生成する評価は、隠しで使える情報より多い。全対象をC3と呼びながら、親は全員C2として作る構成も、単一の隠しバッチの模擬にはならない。

確認用には、次のように**バッチ単位で一つの世界を作る**のがよい。

1. バッチ内のC1/C2/C3代理のidentity集合を、scoreを見る前に固定する。
2. C2/C3に指定したidentityのラベル付き参照・train analogを、全queryから見えなくする。C3の構造は、全queryの候補DB・構造を持つ親資産からも除く。C1ではquery取得とその複製を除き、独立な公開参照を残す。testスペクトル自体は、ラベルの無いpeer情報として使える。
3. この共通の情報条件で全queryの基準予測を一度作り、seed bankを凍結する。対象iだけの正解を消した表から、他queryの未修正C2予測を借りない。
4. 同じ凍結bankから親を選び、生成・挿入する。この回の生成結果を親へ戻さない。反復伝播は別の方法として後で扱う。
5. 親の正答率や家族関係は、結果の診断にだけ使い、親選択・gate・対象選択には使わない。

これは本番で隠しラベルを使うという意味ではなく、既知ラベルを持つ開発データで「利用可能な知識」を一貫して模擬するための処理である。C3の真が単に現在のshortlistから消えているだけなのか、全候補資産から消えているのかも区別する。

FPNetも、同じバッチのC2/C3対象全体に未学習である条件を確認する。パネル全identityを除くfold-safeモデルはこの目的に使える。新しいtrain由来バッチで、各queryにそれぞれのfoldモデルを当てるだけだと、親jのモデルは対象iを学習している場合がある。初回は同じidentity foldの分子でバッチを構成し、共通のfoldモデルを使う方が明瞭である。foldをまたぐ家族を使う場合は、対象全体の学習除外を別に保証する。ranker等の学習露出も台帳で区別する。

**別の家族集合をtrainから作る案には賛成する。** ただし、b1_genで正解を作れる対だけを集めると、この編集集合に有利な試験を作ったことになる。それはpositive controlにはなるが、代表的な新しい確認集合とは呼ばない。

- 取得run・試料・library内のシリーズ情報が利用できれば、それを使ってscoreと無関係にバッチを決める。構造から作る場合は、編集の成功そのものではなく、事前固定したscaffold/構造類似の基準で家族を作り、その選別の偏りを記録する。
- 家族を開発用と確認用に分け、同じ家族の別メンバーだけを確認へ移さない。C1 anchorの公開知識を許すことと、C2/C3対象の学習露出を除くことは別に管理する。
- パネルと同程度のサイズの、家族を多く含むバッチと無作為バッチを用意する。250と400の違いでも親の機会数が変わるため、サイズと家族密度を混同しない。
- C3割合と、正しい親を得られる状況を変えた少数の事前固定条件を使う。例えばC3=0/25%/50%で、残りのC1/C2割合も固定する。C3を分子単位で割り当てる条件に加え、家族全体が未知になる条件もstressとして残す。各条件で共通maskとseed bankを作り直す。

この方式では分子間の成績が依存する。75件が75個の独立な成功とは限らず、一つの正しい親が多くを救い、一つの誤った親が多くを壊すことがある。**通常の分子単位bootstrapだけで強い確証を出さない。** 独立に構成した複数バッチでの差をまず見て、家族・予測関係の連結成分を単位にした区間も検討する。巨大な一成分になる場合は、有効な独立単位が少ないと明記する。親を含むバッチを変える評価では、固定したRR行を再重み付けするだけでなく、そのバッチの予測・生成も対応させる。

最低限、パネルで選んだ一方式を別の家族バッチに固定して適用し、予測親での利得が残ること、無作為/親が当たりにくいバッチでC1/C2費用が許容範囲内であることを確認したい。それでも「隠しで効く」との断定ではなく、Publicで一回測る根拠が得られたという段階である。

**Q2: 099の全親A〜Dは探索として維持し、確認へ持ち込む方式は一つに絞る。**

現在登録した「他の249分子のtop1を全て親にする」比較は、可能性を見る探索として理解できる。ただしtrain親10本との比較では、情報源に加えて探索量も変わる。生成物数が増えるだけで最大f·zが上がり、3位gateを通りやすくなる。A/B/C/Dの到達率、固有親数、生成物数、誤挿入数、時間を併記する。

確認用の初期候補としては、私は次を推す。

| 項目 | 固定する案 |
|---|---|
| seed | 同じ情報条件の凍結主出力から、各queryのtop1のみ。一回だけ作る |
| 親候補 | 自分のqueryを除く。予測構造が同じ公式keyの親は一つにまとめ、どのqueryから来たかは全て記録する |
| 親の絞り方 | targetのquery由来質量と親の予測構造の質量差が、許可した1〜2段の編集と整合するものに限定。その中から、既存の同極性のスペクトル類似度を使って最大10個。比較できないものは未観測として順位の後ろへ置き、同点は固定順にする |
| confidence | 初回は新しい確信度閾値を学習しない。top1 margin等は診断に残す。異なるqueryのraw ranker scoreを校正された確率として比較しない |
| 生成 | b1_genの編集・質量許容・各親のcapを凍結。targetごとの総予算と、上限に達したときの処理も結果前に固定する |
| 選択・挿入 | 固有keyの生成物からtarget自身のf·zが最大の一つ。同じ基準リストの3位候補以上なら3位に一件挿入。候補不足、非有限score等の扱いを固定し、3位が無い場合は初回は見送る |
| 追加変更 | DB候補への加点、GL gate、親の反復更新はoff。これらは次の別比較 |

親上限10は既存のtrain-parent gt3と同じ予算単位に合わせるための初期値であり、最適値という主張ではない。現在の全親探索と候補数を揃えた診断を出すと、情報源の価値と探索量の効果を分けやすい。真の親がこの選択でどれだけ残るかは、oracleの診断として報告できるが、その値を見てKや類似度閾値を繰り返し選ばない。

親が対象自身の主リストにも既にある構造かを記録することも有用である。test親の利得が、実際には「対象自身のtop1を親にしても得られる生成」なら、集合内の家族情報の寄与とは分ける必要がある。self-top1生成を同じ予算・gateで行う診断や、サイズを揃えた無関係なpeerバッチとの比較が役立つ。

**現行コードには、評価の読みのために四点の注意がある。**

1. `TPAR`はC2のtop1固定で、C3のUNION maskとは別に注入される。前述の共通世界でseedを作る修正が必要で、現行出力をそのまま厳密なC3性能としない。
2. test親に渡す`sim=1.0`は実測の類似度ではない。生成物のtie-break等でtrain親と比較すると、test側を優遇することがある。類似度と便宜的な親重みを区別し、同点処理は固定する。同じ予測構造を持つ多数のqueryを、独立した多数の支持と数えない。
3. `par()`はappend後に件数判定するので、`--parents 0`でもtrain親が1件残り得る。Aの主出力/dump自体とは別だが、Aの生成列を「親0の基準」と読むのは不適切である。0件の意味を正す場合も、実行中のA〜Dのコードを途中で差し替えず版を分ける。
4. `b1_gen.derive`は親と同じSMILESを除くが、公式keyで同じ構造になる無変化も除く必要がある。出力は公式keyで重複を処理し、基準リストに既にあるkeyを新規挿入しない。target本人を除く検査も、oracle解析では同一identityの別rowを混ぜていないか確認する。

新規性の呼び方も既存gt3の監査範囲に揃える。現行の`novel`はraw-window不在で、DB全体での不在と同義ではない。質量許容の下限0.002 Daやaliasの違いでも、既知DB構造をwindow外と判定し得る。**shortlist内 / window内だがshortlist外 / そのwindow外 / DB全体の不在を確認したもの**を分け、C2の検索救済をC3生成の成功と数えない。DB全体の照合が無い段階では、raw-window不在規則と記録する。

DB候補へのdv1型加点は別の候補にする。同じtest親が多くの既知候補を支持すると、家族構造だけでなく人気構造・予測の共通誤りへの加点にもなる。C2だけに効かせるという真のクラスによる切替は本番ではできないので、C1を含む全queryで費用を測る。

GL gateを追加する場合は、既存044のようにDBと生成物を同じ尺度に置き、生成物の別予算で基準のGL被覆を減らさない。test側生成とGL gateを同時に選んで、親情報だけの効果と呼ばない。train親との併用も、二度3位挿入するのでなく、候補の和集合を重複処理して一つを選ぶ方式として別に固定する。

**Q3: 一枠の一対比較は適切だが、その前に「何を一変更とするか」を閉じる。**

主催者は、推論時にtestスペクトル間の関係を全自動・ラベル無しで使うことを許可している。保存済みの10/26返信は今回の方向を支持する。本番の親は同じrunの自動予測に限り、真の親・真の質量を使った探索は開発上の診断として分ける。[主催者の回答](https://www.kaggle.com/competitions/enveda-CASMI26-molecule-id-mass-spectra/discussion/752297)

最初は、**凍結v7fに、固定したtest-parent生成＋一件のgate付き3位挿入だけ**を追加する一枠が分かりやすい。DB加点、FPNet集約の変更、v8w7aやEAとの同時合成は含めない。対照は同じ資産のv7f=0.390に固定する。後で主系を替える場合は、実験の対照と登録を別にする。既存gt3との比較は同じ情報条件のローカルで行い、旧0.379上のgt3 Publicとの差をそのまま親情報の効果としない。

parityでは、最終リストだけでなく、全queryのseed top1、親選択、query由来質量、生成key、gate、挿入位置まで一致させる。testの行順を変えても、固定したID順・同点規則の下で結果が変わらないことを確認する。250/400規模での総時間、生成上限、失敗時の基準出力への復帰を確認し、処理の後半だけ打ち切られる方策を隠さない。既存の10/28枠を、この探索だけで差し替える根拠はまだない。

Publicの全体差には、C3の救済とC1/C2の押し下げが同時に含まれる。真が基準候補に無いC3で、正解を3位へ一件挿入したときの得点は1/3である。仮にoracle到達75/250の集合をそのまま使えたとしても、その構成のC3平均は最大0.10であり、Public全体では更に対象の構成比が掛かる。30%をPublicの+0.30と読んだり、親正答率を掛けただけで予測値にしたりしない。

誤った候補を3位へ入れた場合、元の真が1/2位なら不変、3〜24位なら損失は`1/r−1/(r+1)`、25位なら打ち切りで**1/25を全て失う**。この費用を挿入率、誤挿入数、真の元順位別に出す。known DBの検索救済が含まれた場合は、その利得も別に計上する。

さらに、この方式ではC3割合が変わると親bankの質も変わる。**単独のC1/C2/C3 viewの差を、固定した利得として後から線形に混ぜるだけでは足りない。** 構成比πに対して各クラスの差自体もδk(π)と変わり得るため、事前に決めた混合バッチで確認する必要がある。

Publicが改善しても、C3比率や家族の数を逆算することはできない。改善しなければ、家族が無い、親が当たらない、候補選択/gateが弱い、C1/C2費用と相殺した等が残る。既定の運用境界を使うなら+0.008/−0.015を結果前に固定し、その一回の値を見て親数・確信度・GL gateを探索しない。
