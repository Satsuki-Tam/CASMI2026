1. **生成に正解質量を使っています。** `gen_job()` は `truth_smiles` を解析し、`ExactMolWt(tm)` から各親へのdeltaを計算します。「ラベルは測定だけに使用」は不正確です。現在の表は「正解の中性質量を与えた生成診断」と改称して残し、本評価はqueryのprecursor/adductと既存pipelineの質量仮説だけで作ってください。3 mDaは157 Daで約19 ppm、1,159 Daで約2.6 ppmです。既存の10 ppm窓と同じ規則にするのか、別の固定許容幅を使うのかも先に決めます。正解質量版との対照は、質量誤差による損失を測る副表にできます。
2. **宣言した質量差と実生成物が一致する保証がありません。** `derive()` はEDITSの式差で経路を選びますが、生成後の実質量を確認しません。Sparkで `COc1ccc(OC2OC(CO)C(OC)C(O)C2O)cc1` に `dHex_glyc` の宣言差−162.052823 Daを指定すると、`COc1ccc(O)cc1` が返り、実際の差は−176.068473 Daでした。差は **14.015650 Da** あります。広い糖SMARTSが置換された糖も除くためです。各反応の宣言式差と実生成物の差の整合を確認し、SMARTSまたは質量による枝刈りを修正したうえで、最終生成物にも測定質量との一致を必ず適用してください。
3. **二段の順序を片側しか探索していません。** `combinations_with_replacement` の名前順だけで反応を適用するので、反応の適用可能性に順序依存がある場合に欠落します。親`CC`から`CCOC`への差+30.010565 Daでは `derive()` は0件ですが、`OH_al → Me_O` を順に適用すると生成できます。異なる二反応の両順序を扱い、生成後に同一構造をまとめる必要があります。
4. **max_productsは厳密な上限になっていません。** `OCCc1ccc(O)c(O)c1` に一段のメチル化を指定し、`max_products=1` とすると3件返りました。comboの全生成物を追加してから判定するためです。親ごと・分子ごとの上限、途中の反応適用数、打切り順序を明記し、公式identityで一意化した件数に対して確実に適用してください。候補数の増加は後述のmax-scoreゲートにも影響します。
5. **採点と一意化を公式keyへ揃える。** 現状は生成物のraw InChIKey14を、複数のraw/scorer keyの集合と比較しています。既存の公式scorer replicaと同じ、立体化学の扱い・tautomer canonicalization・固定RDKit版を使い、正解判定は正解の公式keyに一致することに統一します。identity groupは除外のための集合であり、その全要素を正解扱いする集合ではありません。親自身が別SMILES表記で戻ったものも、keyで重複を判定します。

生成経路の記録も直すと有用です。`hit_n` は現在、異なる親の数ではなく生成SMILESを訪問した回数です。親keyの集合と反応経路数を分けてください。`first_parent` / `combo` は最初の出現の記録で、後から最大scoreが更新されても変わりません。最高scoreを与えた親・経路を別に保存し、「生成できた経路」と「順位を決めた経路」を区別します。

**Q1：C3 viewは「既知構造を隠した生成評価」として妥当。真の新規NPの性能とは区別する。**

次の条件を揃えたviewを主にしてください。

- 真の公式key・alias・identity groupを、親の参照、候補DB、key index、既知構造の属性lookupから一貫して隠す。生成後に真が再登場しても、元のDBからtrain所属・人気・参照等を取り戻さない。評価用の仮想DBとしてmaskを共通化し、元資産を変更する必要はありません。
- 生成の入力は、query由来の質量仮説と、mask済みの親構造・参照スコアだけにする。正解SMILES/keyは採点側へ分離する。
- **正例学習で真のidentityが未見のFPNetを使う。** full_evalパネルはidentity既見なので、C3でのFP順位付けの主評価には不適格です。採用先full_evalの主C3は保留されたdev2 v2で測り、fold-0パネルC3は補助表にします。同じ未見ラベルでも異なるcheckpointの差を無印で混ぜません。
- ranker/GL等も、当該identityを学習している可能性を記録する。FPNetの負例poolに保留真が入っている点も、実際のDB未収録構造とは違います。効果の符号は決め付けず、監査できていない露出を「完全未見」と呼ばないでください。

親の除外には、**一分子ずつ隠す条件と、C3対象群をまとめて隠す条件**の違いがあります。現行の一分子ずつのC2 maskでは、他の評価分子の正解構造が親として使えます。これは「他は既知で、この一分子だけ未登録」という診断としては成立します。しかし複数の未知構造を識別する条件では、それらの正解構造は公共参照として使えません。主C3または強い感度表で、対象C3群のidentityの和集合を親・DBから除いてください。`relatedness_1026.md` でパネル内の近縁性が高いことは、この違いを確認する理由にもなります。

Tanimoto≥0.9の近縁親の除外は**感度分析**として賛成です。実際の新規NPが既知構造のごく近い誘導体であることはあり、0.9以上だからリークとは限りません。基本条件は公式identity/aliasの除外、追加条件は近縁親への依存度の測定として分けます。近縁親を除くときは、除外後にtop-Pを選び直し、単にtop-10から落として親数だけを減らさないでください。真と親の距離別、parent recall、反応で到達した率、選択された生成物の率を併記すると切り分けられます。

既知NPの近縁体が多いことは楽観要因ですが、現在は変換順序の欠落・質量外れのデコイ等、性能を下げる要因もあります。「楽観側の代理」という位置付けは妥当でも、隠しC3に対する数学的な上限とは呼べません。上限として扱えるのは、同じ固定集合・同じ生成集合での到達oracle等です。

**Q2：w3=0.3は一シナリオ。候補選択は保護とC3利得の両方を先に固定する。**

30〜40%という外部推定や較正のzero成分は、w3≥0.3の根拠ではありません。w3=0.3を「控えめな値」として合格条件にすることには反対です。C1/C2の集約方法も固定してください。局所の分子数比で混ぜたΔ_C12は開発用macroであり、隠しの混合比ではありません。

推奨は、tuneで**各C1/C2保護層のΔ≥−0.01を満たす候補の中から、統合後のC3利得を比較する**形です。選ぶ規則は一つに固定し、evalではその規則だけを読む。w3については全範囲の損益曲線を副表にします。Δ_C12=−L<0、実際に挿入したリストでのΔ_C3=G>0なら、仮定した集約における損益分岐は

`w3* = L / (L + G)`

です。C3代理からの転用が弱まる感度表も出し、Gを割り引くと分岐がどう動くかを示してください。Δ_C12が非負なら最低C3割合を必要としない場合があり、後述のC2救済を測る意義があります。比率や予測値をPublicから事後に選び直さないことが重要です。

統合規則には、次を追加することを勧めます。

1. **生成なしを選べる対照と棄却を入れる。** g1の「強いとき1位、それ以外でも必ずk位」は、証拠が弱い生成物も挿入します。生成なし/閾値未達時は挿入しない方策を比較に含めてください。空き枠への追記も、基準順位を悪化させない別の対照になります。
2. **同じスコア尺度を使う。** rawのf·zなら同じquery logits・bit集合・fingerprint関数を使用します。標準化するなら、DB側の固定した参照集合の平均/標準偏差を生成側にも使い、DBと生成を別々にz化しません。生成件数が多いほど最大値が上がるので、P、変換数、mass仮説数、生成上限を固定し、件数別の誤挿入も測ります。
3. **g2の比較集合と欠測を固定する。** 主順位のDB上位5個だけとの比較は、DB候補全体の最良FP/GLとの比較ではありません。その限定を登録し、生成物とDBの両方に同じ条件のGLがある場合だけ使います。GL欠測を通常の数値0として勝たせず、比較不能時の方策を固定します。
4. **元の順位を保持しても、MRRは保持されない。** 誤生成物をk位に挿入すると、k位以降の真は押し下げられ、元25位の真は0点になります。top-25切詰めと公式identity重複除去まで通した最終リストでΔを測ります。

δの値、k、g1/g2の候補数は本評価前に有限の一覧で固定してください。「生成側の上限やGL対象を変えながらδも選ぶ」と、大きな探索になります。採用先は今の登録主出力anaw0.5に固定し、将来v7fへ対照を更新するときは、DB上位5やscoreが変わるので同じ規則を改めて評価します。

**Q3：DB内救済・局所未収録・本当のClass 3を分け、基準の計算予算も守る。**

生成物は公式keyで、少なくとも次の出自に分けてください。

| 生成物の所在 | 意味・扱い |
|---|---|
| 既存shortlist内 | 重複追加しない。特徴による再順位付けの問題 |
| 元のDB窓内だがshortlist外 | **DB候補の到達救済**。C2等の改善になり得るので、窓内だから一律に捨てない |
| 使用DBにはあるが元の窓外 | 質量/adduct/正規化/検索範囲を点検する。新規構造とは呼ばない |
| 使用DB資産には未収録 | ローカル未収録の生成物。PubChem等の全体に存在しないことを保証するものではない |

C3シミュレーションでは「元資産に存在したか」と「mask後のviewに存在するか」を両方記録します。真のkeyを窓からだけ消して新規扱いし、別のlookupで既知の属性を復活させる状態は避けてください。公式定義とローカルDBの収録範囲は別なので、全window keyとの非一致をそのままClass 3判定にしません。C2救済を含む実用上の利得を測る方が、w3の推定に頼らず前進できる場合があります。

GLACIERへ生成候補を追加すると、既存候補のGL被覆・fallback判定・実行時間が変わり得ます。**「基準順位はそのまま」という比較では、まず元のDB出力を完成させ、生成側に別の固定予算を与える**か、同等の順序保護を実装してください。生成追加後の総候補数で元のGL被覆の分母を増やしたり、全候補で正規化し直して基準順位を変えたりしないことが必要です。生成側が未完了なら基準出力へ戻れる形にし、GL計算と挿入を含めたparityを確認します。

規則面では、[公式データ説明](https://www.kaggle.com/competitions/enveda-CASMI26-molecule-id-mass-spectra/data)は新規構造のde novo予測を課題に含みます。公開された許可済み親と各queryから自動生成する方向は、その目的に沿っています。現在Webから本文を取得できなかったため、ここは保存版による確認です。未知testの正解を使わず、通常の公式identity・有効SMILES・25候補以内の提出処理を適用します。テスト間処理の未回答の議論752297とは別の経路なので、今回の候補に混ぜる必要はありません。
