新規性の監査は、記述を次の範囲へ正確に限定すれば受け入れられます。

- **1,123 は一意構造数ではなく、query×view の挿入イベント数**です。生成物の公式 key は 973 種類でした。一致 2 件は同じ F の query `COOXMAGVIUSQDU`、同じ生成物 `WIHKWCJAOVNKLJ` の C1/C2 で、今回の照合ではどちらも tier への一致です。
- 2/1,123 = 0.18% は、生成物の質量 ±10 ppm・同じ未標準化分子式という探索範囲で検出した割合です。「全 DB に公式 key が存在しない率 99.8%」とは言い換えないでください。query 由来の実際の窓とも検索中心が異なります。
- 公式標準化は未標準化の分子式・質量を常に保ちません。小例では酢酸 `CC(=O)O` と酢酸イオン `CC(=O)[O-]` は公式 key が同じ QTBSBXVTEAMEQO ですが、式・質量は異なります。この監査のフィルタで全ての公式同一性を尽くせるわけではありません。実データで追加の見逃しが何件あるかは未集計です。

**Q2：fold-1 dev / locked の使い方**

この方向を支持します。既存の fold-0 集合を繰り返し確認集合として使うより、未使用 identity を持つ fold-1 で規則の移りやすさを測る方がよいです。選択 manifest の交差検査は dev/locked 0、既存集合との identity group 交差 0、one-per-group 1 でした。dev は C/D/E/F/G 各 100、計 500 identity です。公開の `make_split.py` は指定 fold とパネルの identity group を除外し、`train_fivefold.py` に fold/panel の学習重複検査があることも確認しました。

ただし、**規則の効果は必ず同じモデル・同じ query・同じ候補資産の内部差で測ってください。**

| 評価ブロック | 両側で共通にする FPNet | 比較 |
|---|---|---|
| dev2 v2 | full_eval | 第 2 段 − gt3、および各々 − anaw0.5 |
| fold-1 dev | fpnet_fold1 | 同上 |
| fold-1 locked | 選択時と同じ fpnet_fold1 | 選んだ一規則 − gt3、および主出力比の保護 |

fold-1 の絶対 MRR と dev2 の絶対 MRR の差は、分子分布と checkpoint の差を両方含みます。それを規則の利得にしないでください。full_eval を fold-1 にそのまま当てる、あるいは fpnet_fold1 を fold-0 dev2 に当てると、学習済み identity が混ざり得ます。モデル差を調べるための入れ替えでも、未見 C2/C3 という解釈を保てるとは限りません。

選択時の「C3 NP 等重み」は、**ブロック内で C/D/E/F を各 1/4、二つのブロックを各 1/2**と明記するのが自然です。各ブロックの `候補−gt3` も別に残し、統合値だけで符号の不一致を隠さないでください。両ブロックで正を必須とするかは元の登録には書かれていないので、後から合否条件を足す場合は変更履歴を残します。C1 は usable の数が層ごとに異なり、C3 と同じ分母ではありません。

**修正が必要な記録上の不整合もあります。** `eval_set_f1/p2_select_manifest.json` は `counts.fold=1` なのに、トップレベルの `fold_identity=0` です。`p2_select_v2.py:114` のハードコードが原因で、選択条件そのものは `a.fold` を使っています。保存済みの分子を再抽選せず、`fold_identity=a.fold` と実際のモデル sha を記録する manifest へ訂正してください。fold-0 の `SPLIT_AUDIT.json` を fold-1 の証明に流用せず、fold-1 の checkpoint と学習除外の対応を追える形にします。

**Q3：第 2 段の実装で、候補選択・locked 開封前に直す点**

**最優先は view 間での上位 K の混入です。** `gen_eval3.py:220–223` は各 view の上位 5 を和集合にして GL 入力へ渡します。計算の共用自体は可能ですが、採点側 `283–286` が `nov[:a.gl_k]` でなく **全 `nov`** を走査し、共通 GL 辞書にあるものを全て使います。そのため、別 view では上位 5 に入った候補が、当該 view では 6 位以下でも採用されます。

現行採点ブロックを小さな入力で実行すると、6 番目の候補だけ GL が高い場合に `n_gen_gl=6` となり、gg3 / gg1d1 がその候補を選びました。実際の保存済み開発 CSV の `n_gen_gl` でも確認できました。

| 表 | query×view 行数 | GL 候補数 > 5 の行 | うち C3 | 最大候補数 |
|---|---:|---:|---:|---:|
| stage2_p2dev | 1,292 | 58 | 18 | 10 |
| stage2_f1dev | 1,294 | 54 | 15 | 10 |
| stage2_panel | 500 | 72 | — | 10 |

合計 184 行、主指標に関わる C3 でも 33 行です。5 個以下でも、本来の上位 5 の欠測を別 view の候補が埋めている可能性があるため、この件数は影響候補の下限です。どの規則の RR が何件変わるかはまだ計算していません。

**採点対象をその view で事前に選んだ上位 5 の台帳へ制限し、現開発表を再評価してください。** 台帳には view、official key、使用 SMILES、FP 順位、選択フラグ、GL 状態を持たせます。union の GL cache は保存でき、同一入力条件のスコアを再利用すれば、この修正のためだけの GPU 再計算は通常不要です。基準 `main` と `gt3` が以前の同一ブロックの値と変わらないことも確認します。修正前の表で選んだ候補は登録選択の根拠にしません。

併せて、次の点を固定してください。

- **有限値と尺度の成立条件。** `gsc is None` だけでは NaN / ±inf を除外できず、小例では +inf の GL が gg1d1 の 1 位へ通りました。生成 FP/GL と最終 S の有限性を検査します。DB の有限 GL が 2 個以上でも標準偏差 0 に 1e−9 を足すだけでは、差を極端に増幅します。FP/GL の尺度が成立しない場合の棄権、ggt3 の gt3 fallback を明文化してください。
- **「GL がある」の定義。** 現在の ggt3 は DB に有限 GL が 2 個以上なら gg3、それ以外なら gt3 です。基準 ranker の `min_gl_cover=0.5` と同じ判定ではありません。DB 側の尺度は成立するが生成 GL が全欠測なら、現実装は主出力へ戻ります。この分岐を登録文に明記します。また比較順位 k が DB に存在しないとき、現在の `sdb_at` は −inf を返し挿入を許すので、単に「比較候補の GL がなければ挿入しない」という説明では不十分です。
- **未対応と実行失敗の区別。** 保存済み GL の E/F は、元 runner が `status=ok, n_mols_covered=0` なのに resume 側で `error` と表示されています。これは GPU エラーの証拠ではなく、未対応 query の扱いです。一方 fold-1 C は covered 74 に対して scored 73 なので、未採点の 1 件は原因を記録します。未対応・構造拒否・timeout・ファイル欠落を同じ None に潰さず、評価の分母は全 query のままにしてください。
- **部分完了の扱い。** `ice_resume.py` は一つでも score がある分子を done とし、元 runner が ok なら残りを再試行しません。候補上限・heavy filter・adduct・CE/proxy 条件と、上位 5 のどれまで採点されたかを確認します。登録した「GL のある生成物だけを使う」規則は維持できますが、実行障害まで GL 非対応として採用判断へ混ぜないでください。`gen_eval3.py:228–229` のファイル読込失敗をログだけで続行する経路は、登録評価では失敗として止める方が明確です。
- **locked の出力制限。** 現コードは採用規則を一つ指定する機構がなく、全 gg 規則を表示し、CSV には gk2/gk3all/dv1 等も残ります。「選んだ一規則と gt3 だけを出力」という登録とは一致しません。開封用の集計・stdout・CSV を選択規則、gt3、主出力と必要な監査列へ制限してから実行してください。全規則を見てから列を削除しても一回確認には戻りません。

現在の DB 尺度を固定し、生成 GL を別入力・別予算にした方針は妥当です。上の問題はその方針を否定するものではなく、登録された候補集合と欠測処理を実装へ揃えるための修正です。

**その他の解釈・次の優先順位**

gg1d1 / gg1d2 は gt3 と異なり先頭候補を動かします。S は FP+GL の尺度で、library priority や learned の信頼度そのものではありません。C1 clean、強いライブラリ一致が発火した query、GL 不足の各群で、1 位の入れ替え数と損益を別記してください。保護条件の main 比 −0.01 に合格しても、gt3 比の保護層の差を併記する価値があります。Public を見てから +1/+2 や K を選び直さず、固定した一規則だけを次の比較候補にします。

親を pool 構造へ広げる案は、044 の GL 追加とは別仮説として開発を続けるのがよいです。D の 20 分子で被覆が 10%→20%でも、候補が 4→64、上位 1 が不変なら、まず生成 recall、FP 上位 5 の正解到達、GL 採点可能な上位 5 の到達、最終順位、計算量を分解します。親を増やすほど K=5 の入口が律速になる可能性があります。query 由来の質量、view に応じた親の eligibility・identity 除外を維持し、044 の確認直前に親集合まで変更しないでください。同じ fold-1 locked を一度開封した後、この別仮説の未使用確認として再利用することも避けます。
