089の主融合E−Fはfold1が+0.0083、fold2が+0.0047で、**両方とも登録した+0.01に届いていない**。結合CIが正でも、進行条件を満たさないという判定は妥当であり、DreaMSの段(b)へ進まない判断を支持する。E05等の診断列でこれを救済しない。

Fs−Fの正の差は、次の仮説を立てる根拠になる。一方、`ES−Fs ≈ 0`から言えるのは「登録の重み1では、FsにDを足す追加利得がこの集約でほぼ無い」までである。E−Fの利得の大半が集約方法に由来した、という**因果的な配分**までは証明していない。F→FsとF→Eが同じ分子を救ったか、別の利得・損失が相殺したかも平均だけでは分からない。「Dを足す前にFsを試す価値が見つかった」と記録するのがよい。

089はfold1/2の適格なCOCONUT identityを全て評価している。したがって、091のf1/f2 devのうち同じpool identity・適格条件に当たるCOCO分子は、既に089の対象に含まれる。非COCOの5,000抽出にも重複があり得る。別の表・query選択・候補集合・最終出力へ移しても、identity単位の独立性は生まれない。正確な重複件数は今回集計していない。

よって091は、**探索で見つけた集約方法が、既存pipelineの出力へ移るかを測る開発上の比較**として適切である。089の不合格とは別に記録し、結果を読んだ後に重み・対象・閾値を変更しなければ、主判定の救済にはならない。独立した確認という主張には、候補固定後の未使用identityが別に必要である。083を使うなら用途の割当てを別途登録し、今回ここでは開かない。

**+0.003という閾値は、結果前に固定した追加検証への進行基準としては許容できる。ただし理由は「無費用の原理的修正」から変更したい。**

**Q2: 三つの近似はいずれも、過大・過小の両方向に働き得る。**

| 近似 | 過小評価になり得る経路 | 過大評価になり得る経路 |
|---|---|---|
| mergeで選んだ候補行に固定 | Fsなら窓から拾えた真を追加できず、到達改善が見えない | mergeなら残るがFsでは落ちる真を保持し、Fsで新たに入る強いデコイを入れない |
| `fp_rank_window`の旧順位を新しい順へ割当て | 本来Fsで大きく改善した窓内順位を表せない | 窓外ならぬ「保存shortlist外」の候補にFsで抜かれることを表せず、不当に良い順位を与える |
| merge特徴で学習したrankerを固定 | Fsの新しい順位・信頼度を活かせず、有効なFP改善を消す | 古い閾値に偶然好都合な尺度で入り、この開発集合だけで有利になる |

旧shortlist固定の値は、Fsを本番全経路に入れたときの下限でも上限でもない。再生成すると、到達以外にもz正規化の母集団、候補数、GL被覆率による分岐、aliasの代表構造等が変わり得る。旧候補に計算済みのGLだけを貼って新候補を欠測扱いにすると、その欠測方策の効果まで混ざる。

窓内順位の割当ては特に注意したい。`fp_mean_score.py`と`addrw_m.py`は、旧順位の多重集合を固定して、保存された候補の新スコア順に配り直している。**新しいfull windowでの順位を推定する根拠は無く、対応する値を仮置きしたもの**である。同じ近似をmerge対照にも施すと非対称性は減るが、rankerが非線形なので誤差が相殺する保証はない。C1/C2の和集合上で一度割り当て、後から各viewを抽出する点も、本番の候補・aliasの扱いと照合が必要である。

rankerにはraw `fp`、`z_fp`、`fp_rank_window`等が入る。Fsでraw logitや候補間の幅が変わると、順位が良くなっても既存の木の閾値や`2*z(rank)+z(S)`での扱いが変わる。したがって091の不合格は「Fs＋現在のranker・近似特徴が不合格」であって、Fsの表現自体が無価値という結論ではない。

**同じPCのmerge対照は必要だが、旧表との差を全てbf16/Spark差と断定しない。** 登録書にある相対差は手法差ではなく照合対象であり、checkpoint、bit順、選択query、CE・adduct・precursor、electron補正、候補の代表SMILES、batch/padding、計算精度も確認する。スコア差が小さくても候補間のmarginより大きければ順位は変わるため、raw scoreの相対誤差だけではparityを判定できない。

追加確認は次の順序がよい。いずれも主担当が行う次段の提案で、実行中のジョブは変更していない。

1. **同一入力での対照を成立させる。** queryの選択行ID・順序、checkpointとFP bit定義、前処理を固定する。overrideの`(set, molecule, smiles)`に欠落・重複が無いこと、予期しないNaNが無いことを確認する。現在は未対応keyをNaNにして先へ進めるため、対象行が黙って別の欠測方策へ移らないようにする。
2. **元の出力への対応を確認する。** `旧表の出力 → PC再計算mergeの出力 → PCのFs出力`の二つの差を分ける。raw FPだけでなくFP順位、使用特徴、最終ordered top25・RRの変化を確認する。特に単一行のqueryではFsとmergeが同じ入力になるので差が無いことを確認する。同一計算条件で各極性1行ずつのqueryも、理論上同じ集約になる。
3. **同じ質量窓全体でFとFsを採点し、真の窓内順位を作る。** まず旧shortlistに対する再順位効果を、順位割当て近似を外して測る。候補identity・重複処理・tie-breakは本番と揃える。推論logitと既存候補のFPを再利用できれば、窓内全候補の順位のためにスペクトル側forwardを繰り返す必要はない。
4. **Fsでshortlistを作り直した全体比較をする。** 同じquery・中性質量・窓・K・prior・libraryルールを使い、FPとFP+prior等の選択にFsを反映する。旧新の共通到達、Fsだけ到達、旧だけ到達、両方未到達を全分母で出す。窓そのものの到達は、この変更だけなら変わらない。新候補のGL等も定義どおりに採点し、実際の被覆分岐・時間制限込みでstrict MRRとC1保護を確認する。
5. **その実装について本番との一致と実行費用を確認する。** 091の近似合格から直接kernelへ進むのでなく、正確な評価でも利得・保護が残ることを確認する。既存v7fとの一対として、query選択やFP checkpoint、prior、rankerを途中で同時変更しない。提出は別の許可された段階で扱う。

Fsでrankerを再学習する対照は有用だが、**固定rankerのままで正確な全体比較・保護を通るなら、採用のための必須条件ではない**。逆に、FP単独の改善が主出力へ移らない場合に初めて、同じfit identity・重み・木の設定でFs特徴へ適応したrankerを別登録で試す。学習表もFsの特徴定義へ揃え、各行には対応するfold-safe FPNetを使う。現在のrankerとFs再学習rankerを、merge/Fs入力で交差して比較すれば、集約方法と適応の効果を分けやすい。候補生成まで変更する場合は、その学習・評価の候補方策も明記する。

**Q3: 生の本数より、選択後の本数・極性内の本数・取得条件の違いが重要。**

1〜16行/分子・中央値3・timsTOFという情報は、保存済みの公式Data記載で確認できる。一方、各本数の割合やadduct/CEの組合せまでは、この要約から復元できない。公開ダミーの詳細な割合を隠しの重みに使わない。`docs/validation_design.md`の過去の「公式に使えるのは400分子・timsTOF・3クラスのみ」という記述は限定しすぎており、本数の要約は公式情報として引用できる。

今回の選択は最大8行なので、16行を持つ分子でもそのまま16行の平均にはならない。生の行数と選択後の`n_query`を分ける。091の途中で全16行を使うように変えると、集約方法と選択量の二変更になる。

極性groupをg、行数をng、合計をNとすると、現行mergeは`Σ ng*z_merge,g / N`、Fsは`Σ z_i / N`である。**各極性に1行以下なら両者は同じ**なので、「2行だから改善機会がある」とも限らない。逆に同じpositiveにH/Na等が混在すると、mergeはprecursor中央値・最頻adduct・CE平均という一つのメタデータへ圧縮するが、Fsは各行の条件を保持する。この違いはFsが効く機構の候補であり、本数の多いlibrary群で効いた理由と同じかは確認が要る。

また、公式Dataの`collision_energy_ev`は、複数値なら複数CEの取得を既に合成したスペクトルを表す。したがってFsは**供給されたスペクトル行ごとの予測平均**であり、単一CEの取得へ分解してから平均する手法ではない。既存コードは各行のCE平均を使うので、その前処理も現在の比較では固定する。

報告する層としては、登録済みの1/2〜3/4+に加え、以下を診断として使うのがよい。

- 選択後のpositive/negative行数、各極性内のadduct種数、同一adduct内のCEの広がり、CE欠測・既に複数CEを含む行の有無。
- GLあり/fallback、timsTOF/他装置、C1のidentity学習済み/未見条件。
- 同じ条件の繰り返しが多い場合と、異なる条件の証拠が増えた場合。行数の増加は独立な情報の増加と同義ではない。

089の`addcls`は選択した最初のqueryのadductで付けているため、H群等を「全行が同じadduct」と解釈しない。異種adduct混合の診断には上記の種数を使う。

089の4〜8行での+0.015を、中央値3の隠し全体へそのまま移さない。091では1行群の差0、2〜3行群、4+群を別々に読み、未知の層比には感度分析を使う。単一行は構造上の対照になる。各identityのスペクトルを減らした比較を追加するなら、queryの選び方と本数を先に固定し、本数群間の成績差を「本数を増やした因果効果」と取り違えない。

本数で重み付けしたlogit平均は登録どおり維持する。条件ごとの等重み化、品質重み、logit平均から確率平均への変更は別の方法である。少数の良いスペクトルと多数の似た低品質スペクトルが混ざる場合、単純平均が常に有利とは限らず、今回の結果を見て重みまで選び直さない。

判定の段階は、**091の同一PC・固定候補の比較 → 正確な窓内順位 → Fsによる候補生成を含む全体比較 → 本番parityと費用の確認**とすることを推す。091の性能結果は未読のため、現時点ではその採否を判定していない。
