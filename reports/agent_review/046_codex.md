**ggt3h の不採用は妥当です。gt3 は、新たな F/C1 の損失を明示して一変更比較に出す判断を支持します。ただし「登録済みなので新しい損失は採否に関係しない」とは扱わず、比較・暫定昇格それぞれでこのリスクを受容するかを Public 前に記録してください。047 は進めてよい設計ですが、確認集合の独立性の説明と、開発時の層別保護を補うことを勧めます。**

**Q1：F/C1 の観察を踏まえた gt3 の提出**

開封済みの `hybrid_f2lock.csv` と `s2ref_f2lock.csv` を一対一で照合しました。両方1,314 query×view行で、mainは全行一致しています。

- F/C1の50分子は全てGL尺度不成立・生成GL候補数0で、hybridと参照ggt3の出力RRは全行一致しています。損失は **−0.012586、改善0・悪化10** でした。
- 悪化の内訳は **3→4位が6分子、4→5位が2、6→7位が1、13→14位が1** です。この集合では正しい既存候補の前へ誤生成物を挿入したコストだけが出ています。

このため「hybridのDB親だけがFを壊した」という解釈は違います。共有するanalog-onlyのgt3 fallbackの弱点です。一方、失敗が参照にもあることは、登録したhybridの保護失敗を取り消す理由にはなりません。hybridの不採用を維持してください。

**gt3の提出を止めるほどの反証とまでは判断しませんが、既知の追加リスクとして扱います。** W7やfold-1での結果、生成によるC3到達と、今回のF/C1の損失を合わせた探索的比較としては意味があります。ただし、今回の観察はgt3専用の登録確認ではなかったという理由で無視もできません。比較前のdecisionへ、次を追記するのがよいです。

1. gt3はF/C1で新たに相対保護 −0.01 を下回った。D/C2の累積未達とは別のリスクである。
2. この一比較でFのリスクを受容するか、Publicが良かった場合の暫定昇格にも例外を認めるかを区別する。従来の全保護条件に合格したとは記載しない。
3. Publicの基準は同じ凍結0.379、既定の境界は維持する。結果を見てからgateを変更した出力へ同じ実験名を使わない。

運用上の全保護条件を例外なく維持するならgt3は保留になります。今回は上記を明記した比較を支持する、という判断です。これは実験担当側の判断記録で、ユーザーへの再承認依頼は不要です。

Publicが負でも、原因をFやGL非対応に特定することはできません。正でも、この局所損失が消えたことにはなりません。fold-2側はFPNetにidentity未見なので、本番のidentity既見C1と損失率が同じとも限りません。隠しのclass比率・GL非対応率をスコア差から逆算しないでください。

**Q2：GLなしのgateを締める次の仮説と確認集合**

まず、**「主出力2位のFP以上」は、現在の「主出力3位のFP以上」より厳しいとは限りません。** 主出力はranker・GL・prior・analog等で並び、FP順ではありません。既存パネルC2の基準リスト250件を確認すると、93件で `FP(主出力2位) < FP(主出力3位)` でした。単純に閾値を2位へ置き換えると、その群では条件を緩めます。

候補を二つに絞るなら、次のように定義できます。

- **fallbackの生成を止める候補**：対象条件では基準リストへ戻す。ggt3の「GL尺度成立かつ上位Kに有限GLがある」経路だけを残す意味なら、これは既に044で比較した **gg3** と同じです。044開発のC3平均はgg3 +0.0117、ggt3 +0.0204で、C3到達を減らす代償を既に観測しています。新しい未試行案として扱わず、既存候補の再検討と記録します。gt3のFP gateを、queryのGL対応可否だけで有効化する案なら別規則なので、その違いを明記します。
- **現在のgateとの積集合**：`生成FP >= max(FP(主出力3位), FP(主出力2位))` とする。これなら現在通らない候補が新たに通ることはありません。比較位置がない、FPが非有限といった場合の動作も固定します。挿入位置は3位のままにして、位置変更とgate変更を一度に混ぜません。

「GLなし」も一つの状態ではありません。queryが非対応、DB尺度が成立しない、上位K生成物が全て未採点、実行失敗、deadlineによる棄権を区別してください。Fという評価用層名を推論時のgateへ直接使うことはできません。観測可能な条件で規則を固定し、計算障害による欠測まで同じ科学的条件として混ぜない設計にします。

開発には、既に開いたfold-1/2 lockedを含む既知の結果を使って構いません。その時点からそれらはこの新仮説の開発資料です。F/C1だけでなく、C1/C2の全保護層、C3の生成到達を失う量、gateが変わったquery数と一対差を出し、一つ選びます。Fの今回の10損失を消せることだけでは採用を決めません。

**確認はfold-3b/4bをranker用のまま予約し、別の未使用identity群を確保する案を推奨します。** 具体的には次の順序です。

1. fold-0/1/2のうち未使用のidentityから、新しい確認集合を結果を見る前に固定する。元のraw keyだけでなくidentity groupで、従来のfit/tune/dev/locked、パネル、今回のtrain_pool全半分、生成・rankerで選択に使った集合との交差を除く。
2. 各queryには対応する公開fold-safe FPNetを使い、両規則でモデル・候補資産・参照maskを共通にする。**新しいfold-0分子にfull_evalを使えば未見になる、とは限りません。** full_evalの除外は旧dev2等の固定集合であり、fold-0全体ではありません。
3. GL非対応だけに確認を限定せず、GL経路が成立する群も含める。GLなしのC1はF以外にも存在するので、装置・参照条件を含む観測可能な層で件数を先に決める。主要C1の有効件数が少ない場合は、その検出力の限界も記録する。
4. 選んだ一規則と固定対照だけを開封し、主指標・保護・C3の扱いを事前に固定する。未見FPの確認と、既存パネルC1 cleanでのidentity既見の保護は役割を分ける。

新規集合を確保できなければ、既知集合での開発と診断までにとどめます。予約済みのranker確認を、結果を見ながら別の仮説へ転用する必要はありません。将来同じ確認集合を複数の候補に使うなら、双方の候補と判定を開封前に固定した共同確認として設計する必要があります。

**gen_eval5の出力上の注意もあります。** RR列の `gt3` はanalog-onlyですが、`--dump_choice` の `gen_okey/gen_smiles/gt3_insert` は現在も全親の `nov` を使います。さらに冒頭docstringはggt3をanalog-onlyと説明していますが、`db_parents=10`時のRR列ggt3は第3段ggt3bです。確認ジョブは参照をgen_eval3の別runから取っており、今回照合したhybrid不合格の計算にこの混同はありません。ただし、次のgate分析やparityへdumpを使う前に、analog-only / all-parent / hybridの選択を別名・別列にして揃えてください。

**Q3：047の設計で補う点**

旧fitを残す、3a/4aだけを明示的にfitへ加える、パラメータ固定、v4b再現対照、3b/4bをrankerの学習へ入れない、という主設計を支持します。poolの選択manifestでは、a/b間と既存集合とのidentity group交差0を確認しました。次の点を追記するのがよいです。

| ranker学習特徴を作るモデル | fold-3bのidentity | fold-4bのidentity |
|---|---|---|
| fpnet_fold3（3aを特徴化） | 除外 | 学習に含み得る |
| fpnet_fold4（4aを特徴化） | 学習に含み得る | 除外 |

3bをfpnet_fold3で評価すれば、そのquery自身はFPNet未見で、rankerのfit行にも入りません。一方、4aの学習特徴を作るfpnet_fold4には3bが含まれ得ます。4bについても逆が成立します。従って、3b/4bは **「rankerの学習外、各query自身のFP特徴はfold-safeで、候補選択にも未使用」** という確認であり、全上流モデルから独立した確認とは呼ばないでください。この依存だけで実験を止める必要はありませんが、限界の記述は確認側まで広げます。全モデル未見の厳密な確認が必要な段階では、外側の確認identityを学習用FPモデルからも除く設計が必要です。

**開発の保護対象にC2 NP各層を明示することを勧めます。** 現047ではfold-1/2のC2 C/D/E/Fは主マクロに入りますが、層別 −0.01 条件に入るC2はGだけです。例えばDの大きな正でCの大きな負を隠したまま、貴重な確認へ進めます。確認では全層を保護するので、開発でもC2 C/D/E/Fを同じ条件に入れるのが一貫しています。結果未読なら登録を補足し、既に結果を見ているなら「元の登録条件」と「追加の運用上の保留理由」を分けて記録してください。後から元の合否定義を書き換えません。
