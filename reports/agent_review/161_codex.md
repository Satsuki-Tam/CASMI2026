# 161 レビュー — 基準の採否、PE の移植、源と被覆の診断

結論: **FH-PEB の 3 seed は登録した開発関門を満たす。一方、現在の固定 FH-PE をそのまま凍結・開封する案には反対する。** 理由は、C1 保護の下限が登録値を下回ること、現 PE も生成由来の特徴を実際に使っていること、PE を通常実験にする案が固定した予測契約と異なることの三点。工数を抑える方針なら、次の一案は「生成を計算しなくても全特徴を作れる PE」を明示して開発評価するのがよい。それが通るまで e は開けない。

161 の依頼・結果、160 の判断、v2 の verification / aux の JSON、保存された source と PE のモデル定義、x161 のスクリプト・小さな結果を確認した。基準 3 件の adapter が G0 snapshot と一致し、verification が true であることも確認した。追加の集計は開発用 stress CSV 等だけで、学習・提出・ワークスペースの編集・e の性能の読み取りは行っていない。

## Q1. 漏れと、源の反実仮想の妥当性

**学習器へ正解列が入る新しい経路は、今回の確認では見つからない。** FEATS、学習 fold の選択、ラベルを特徴から除く境界は前回確認した版のまま。COCONUT 所属や E の得点・欠損は本番で観測可能なので、その利用自体は漏洩ではない。

ただし、母集団を COCONUT 所属で選んだ結果、正例に対する源の事前分布が極端になっている。これは**母集団選択による偏り**として扱う。`w135_census.py` は fold を変えても COCONUT 条件で絞るので、同じ設計の e で成功しても、源の外への頑健性を確認したことにはならない。

また、「C2 の +0.145 の大部分が源の旗だけによる」とまではまだ言えない。今回の介入は旗だけでなく e2_score、順位、ライブラリ・analog の情報、F の順位をまとめて変える。**E の証拠への強い依存**は示すが、その中の source prior とスペクトルによる識別の寄与は分離していない。

反実仮想には、次の正しさの問題がある。

1. **E-only と呼ぶ分岐の F_cf が更新されない。** `x161_stress.py` は `in_P==0` の場合に continue し、後で FH の真の枠だけを PAD にする。F_cf は元の f_rank から計算されるため、「両方 RR=0」という説明と一致しない。主対象 429 件のうちこの分岐は 15 件で、そのうち 6 件の F_cf が非ゼロのままだった。この一点だけ F_cf=0 に直す仮計算では、混合の交点は 0.4806→0.4818。これだけで脆弱性の方向は反転しない。
2. **`in_P==0` は「E が無ければ U2 から消える」と同義ではない。** 上の 15 件を開発表で照合すると、5 件は in_B=1 だった。E を失っても B 経由で残るため、一律 PAD は不適切。B の代表と特徴に戻して再採点すべきであり、削除すべきなのは P にも B にもない場合である。PE だけの試験と PEB の試験でも挙動を分ける必要がある。
3. **OOF の「完全再現」は現コードでは RR の一致だけ。** 比較しているのは `rr0` と `rr_true` で、予測行列そのものではない。保存 OOF と全 valid slot の値・PAD・ID を明示した許容差で比較する。順位や正解の RR が同じでも、異なるモデル得点を完全再現と呼ばない。

さらに、他候補の E 順位、E25 の補充、n_e/n_e25/n_u2、代表や関連する特徴を据え置くのは、整合した「源が無い世界」ではなく局所的な入力破壊である。完全な E 順位から対象を除き、順位を詰めて E25、U2、F、Q、相対特徴を再構成すれば、この近似の大きさを測れる。修正前の結果は残し、修正版を別の診断として読む。

**q≈0.48 は隠れた test の採否の境界に使わない。** 対象は全 C2 503 件ではなく、元々 U2 に真があり E の証拠もある 429 件。そこに正解依存の介入を行った二状態の混合である。自然な源外分子は、候補到達・化学構造・P の強さ・残る参照がこの対象と異なる。実際、現在の C2 全体の差は +0.1435 で、条件付き対象の +0.1683 とは異なる。

したがって、軽微な F_cf の修正だけなら交点はほぼ変わらないが、整合した再構成と母集団の変更の影響まで小さいとは言えない。「源が不利になると大きく崩れ得る」という警告は残し、交点はこの人工的な感度分析の値として限定する。panel の COCONUT 所属率も、隠れた C2 の E 窓外率 q の推定値ではない。

## Q2. どの候補を先に凍結するか

まず、保存された `reports/aux/PE__vs__F.json` を見ると、固定 PE は保護を一つ満たしていない。

| 候補 | 主差 / 組の下限 | π0.3 C1 の差 / 組の下限 | 登録条件 |
|---|---|---|---|
| PEB seed 11 | +0.080705 / +0.063726 | +0.009662 / −0.005933 | 合格 |
| 固定 PE seed 11 | +0.061813 / +0.046499 | +0.002877 / **−0.010600** | C1 保護が未達 |

PE の C1 平均差は正であり、害が証明されたという意味ではない。しかし下限 ≥−0.01 の非劣性を確認できていない。差が僅かでも、丸めたり、通る family 区間へ後から切り替えたりして合格にはしない。同じ計算を exploit として再登録して一致させても、この結果は変わらない。

PEB を先にする根拠はある。3 seed 全てが F に対する保護を満たし、seed 11 の PE に対する主差は +0.01889、組の区間は [+0.00932, +0.02865]。生成物の上乗せの**大半**は C3 だが、C1/C2 の差が厳密にゼロという結果ではない。PEB−PE の C2 は −0.00179、区間は [−0.01079, +0.00541] で、「PE と比べて無害まで証明した」とは言わない。登録した保護の対照 F には合格している。

工数から PE を先に検証する戦略は理解できるが、**現 PE は生成計算を省けるモデルではない。** PE の全 7 モデルの split_feature を確認すると、全てが log_nb、log_nu2、n_peer_struct、n_train を使用し、一部は apsc、log_npar、n_steps も使用している。これらは候補を PE に限定しても残る生成由来の情報である。159/160 で区別した「生成物を出さない」と「生成を計算しない」の違いが、ここで実際に効く。

推奨は次の順序。

- 完成候補として現在資格があるのは PEB seed 11。B も含めた移植が現実的なら、その候補を維持する。
- B の生成・採点を避ける方針なら、まず生成由来の情報に依存しない PE を一案作り、主差と全保護を測る。固定 PE の +0.0618 を、その新モデルの実測値として引き継がない。
- どちらを最終候補にするかを、移植可能性・開発関門・parity を含めて決めてから e を一回だけ開く。e で PE が駄目なら PEB を続けて開く、という選び方はしない。

運用上も、現在の [g0_spec.md](/C:/kaggle/competitions/casmi-harness-v2/docs/g0_spec.md) §6 は「ハーネスの実験は FH-PEB だけ」、§7 は PE を固定参照として扱う契約になっている。adapter だけを変えて PE を通常の exploit に混ぜるのは、その契約に反する。PE を候補化するなら、凍結済みの v2 を残し、PE 専用の予測契約を別に正式化する。必要なら同じ分割・資産を再利用する別ワークスペースにする。PE と PEB の異なる提出資格を、PAD を含む単純平均で自動 ensemble に混ぜない。

## Q3. 移植と parity に足りないもの

世界の資産を notebook 側の builder に渡して全行の特徴を照合する案はよい。ただし、先に**どの PE を移植するか**を確定する。

現在の固定 PE を忠実に移植するなら、生成件数・親情報に加え、E∩B の生成特徴、同じ SMILES の B から再利用した GL、元の U2 の大きさ等も必要になる。これらを本番で 0 に置き換えるのは同じモデルの移植ではなく、未評価の入力変更である。

生成を不要にする新 PE では、少なくとも次を学習時から揃える。

- 入力候補は P25∪E25。B 由来の列と query 要約を除くか、生成を使わず計算できる定義へ変更する。例えば候補数は PE の候補数と明示する。
- E 代表の GL は、生成 B に存在するかどうかで利用可否を変えない。常に未計算とするか、既存 P 経路で同じ SMILES の値を取得できる場合だけ使う等、同じ規則を学習・本番に適用する。
- 相対順位・z 値・重みは PE の集合で再計算する。旧モデルに、列名だけ同じで定義の違う数値を渡さない。

parity は特徴だけで終えず、以下まで通す。

1. **入力と集合**: query の選択・統合、adduct/質量・電子補正、源と alias/official key、P/E の代表 SMILES、E の全窓順位、PE の資格を一致させる。C1 の参照除外、C2 の train 隠し、空 P/E、同点、E∩B だったケース等を固定例に含める。
2. **特徴**: 生の候補値だけでなく、query 要約、欠損、相対特徴、列順・dtype・有限値を比較する。整数・key・mask は完全一致、浮動小数は許容差を先に固定する。
3. **得点と出力**: 対応する各 fold モデルの予測、7 モデルの平均、提出資格、同点規則、上位 25 の official key と提出 SMILES、CSV の全 ID・重複・空候補の扱いを比較する。全実在枠を採点する PEB と、PE 外を提出しない PE の契約を区別する。
4. **実行条件**: Kaggle 側の実際の asset/model/hash、ライブラリ版、ネットワーク無効での実行、所要時間・メモリを固定する。世界のデータを受け取る adapter だけの一致は、通常の notebook 入力からの前処理まで保証しない。

dF1 の開発行を 7 fold 全モデルで採点しても parity の数値照合には使えるが、その平均の MRR を OOF と呼ばない。6 モデルはその行を学習している。開発性能は対応する保留 fold のモデル、e と本番の推論は登録どおり 7 fold の平均、と分ける。

## Q4. source dropout と Public の比較

**いま直ちに二候補を Public で選ぶ方針は勧めない。** 正しい源ストレスと、生成を省ける PE の定義を先に整える。源の頑健化を試す価値はあるが、「世界では必ず悪化し、利点は Public でしか見えない」は未検証の仮定である。

最小の比較では、一つの欠損率・seed・対象ブロックを事前固定し、同じ identity/alias にはラベルを使わず同じ規則を適用する。正例だけを狙う現在の stress を学習拡張に流用しない。`in_coconut` 一列を消しても、E の得点の有無、e_miss、E25、F の順位などに代理情報が残るため、何への依存を抑える試験なのかを決める。

区別したいのは二つ。

- **特徴の block dropout による正則化**: 候補の存在は維持して証拠を欠損させる学習法。これを、DB から構造が消えた世界と呼ばない。
- **E 経路の欠落に対する評価**: ラベル非依存の identity の除外等を E の全窓に適用し、順位・E25・候補集合・F・要約を整合して作り直す感度試験。主集合の成績と、源に不利な条件での費用を両方測る。

可能なら、COCONUT 所属を選択条件にしない小さな未使用 C2 集合も補助確認に使う。ただし、その集合の設計やモデルへの露出条件を固定し、既存 CV/e の代わりにはしない。今夜の候補移植を、その追加集合の完成まで全面的に止める必要はない。

Public 比較を行う場合も G3 の対象を具体的な成果物で固定し、正則化の率や複数の seed を Public で探さない。Public の差から q を逆算したり、「源の事前分布が移ったことを単独で証明した」と読んだりもしない。

## Q5. C1/C2 の 116 件は本当に窓で落ちたのか

**現在の結果からは未確定。先に訂正すべき推論がある。** `w135_p.py` の rP は `b1_locked_eval.view_frame()` が返す表での正解順位で、その関数は `in_short_c2` と源の資格で絞る。`b1_world.py` も FP・FP+prior・library 等の shortlist の和集合から候補表を書いている。

従って、`P.parquet` の rP=0 は「P の最終の再順位付け対象にない」ことであり、**B1 の生の質量窓にないことを証明しない**。22/1,198=1.8% は「E の全窓にいて U2 にいない」件数であって、全経路を通じた shortlist 問題の総量ではない。

最小の検査は、116 件の開発 query に対する脱落段階の台帳。まず保存済みデータで次を結ぶ。

1. 事前の DB に official key / alias があるか。母集団選択の COCONUT 判定と、実際の pool/coco 資産の key・構造・版が一致しているか。
2. B1 の保存された全窓 `gen_*_window_okeys.parquet` に正解があるか。`b1_molecules_*.csv` の truth_in_window / truth_in_shortlist も照合する。raw key のみでなく official key と alias で確認する。
3. 全窓にはある場合、FP/lib/prior の短縮、源の資格、official key の統合、P の view のどこで落ちたか。
4. 全窓にもない場合、query ごとの中性質量推定、正解各表記の質量、最小 ppm 差、adduct・charge・同位体・塩等の正規化、mask による除去理由を記録する。

C1 の参照除去はライブラリ証拠と shortlist を変え得るが、構造の生窓から直ちに消える理由にはならない。C2 の train 隠しも、合法な COCONUT の経路が本当に残るなら構造自体を消す理由にはならない。まず「外部の源にあるはず」という前提が、実際の質量・key・使用資産で成立するか確認する。

なお B1 の保存全窓は C3 の構造 mask 後であり、truth_in_window は raw/pool alias に依存するため、台帳一列だけで最終断定しない。必要な場合だけ少数の失敗例で mask 前後の候補集合を再現し、無関係な query の mask や alias 統合で落ちたのかを調べる。mask を解除した性能を C2 の正式な性能にはしない。

優先度は高い。保存台帳でできるこの切り分けは、次のモデル学習に並行できる。116 件が全て回復できる改善量は上限にすぎず、原因を確認する前に ppm や shortlist を一律に広げない。

## Q6. 残りの lane

既消費は exploit 3/6。**固定 PE を同じ計算で通常実験へ移すだけの 4 件目は使わない。** 新しい効果の検証にならず、保護の未達と生成への依存も残る。

推奨する配分は次のとおり。

- 最初の一件: 生成を省ける PE を選ぶなら、その定義を固定した一案を評価する。予測契約の変更を正式に扱い、対応する lane に計上する。既存 v2 の固定ファイルは変更しない。
- 次の一件: その結果に応じて、源の頑健化一案、または C1 の費用を抑える一案。事前に固定し、複数率・複数 gate の総当たりはしない。
- 残り一件: 工程上必要な確認、または登録した ensemble のために留保する。通る完成候補ができたなら、枠を埋めるためには使わない。

源ストレスの修正、被覆台帳、移植の parity は、モデルの性能改善とは分けて、費用と作業を記録する。別の予測契約・ワークスペースに移しても、同じ 48 時間に既に使った 3 件を無かったことにして探索予算を再開しない。
