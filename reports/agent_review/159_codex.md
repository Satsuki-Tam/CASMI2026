# 159 レビュー — v2.1 と v2 ワークスペースの G0 材料

結論: **62 特徴と F-world に対する +0.01 の関門には賛成。G0 に出す前に、receipt の検証、診断の U1 の独立した再構成、FH-PE の固定方法を直す。** データの完成後に下記の全件検査を通せば、FH-PEB の開発を始める設計としてよい。FH-PE の学習完了を、その開始の必須条件にはしない。

159_request、158_decision、記載の上流・U2・書き出し・診断コード、v2 ワークスペースの src・refs/fhpe_ref.py・g0_spec・harness.yaml・D1〜D7 を確認した。実データでの到達・性能、e のラベル、Public は読んでいない。実行したのは adapter の人工 3 候補による特徴検査だけで、学習・GPU・Spark の追加計算は行っていない。依頼文の 7 query の技術 PASS は、37 世界の全件 PASS とは区別する。

## Q1. 上流・U2 は 158 の判断に沿っているか

主要な修正は反映されている。源の行の資格を official key への統合より先に決めること、B1 gen dump と zlog を比較すること、MAX_REF 後の参照を記録すること、E が空なら採点を呼ばないこと、P が空なら F は空・E が空なら F=P とすること、同じ代表 SMILES の E∩B で GL を再利用することは妥当。GPU lock、no-overwrite、系列内の失敗を最終 exit code に反映する変更もよい。

ただし、次の二点は結果を読む前に直してほしい。

**A. receipt は「記録」されているが、入力・世界・コードの来歴をまだ検証していない。** `spark_v2_1_world_e2.sh` の `receipt_ok()` と `w135_fh2.py:34` 付近は、いずれも `rc["outputs"]` に列挙されたファイルの hash だけを調べる。`world`、`version`、`inputs`、`code`、`model`、検査の成功は照合しない。空の outputs も `all(...)` では成功になる。これは 158_decision の 5・6 の「この世界・この入力から完成した資産を受領する」という条件には足りない。

共通の検証関数で、少なくとも次を結ぶ。

- 期待する世界・版・必要な出力ファイル集合と、実際の receipt の完全一致。
- world_masks、batch CSV、B1 gen dump、analog の比較先 P の hash と、各段階 manifest の同じ入力の hash の一致。特に ewin と e2f の masks / eval_csv の一致は、現状の採点前の「ewin 表の hash とキー集合が一致」だけでは保証されない。
- 登録したコードの snapshot、E2 model の完全な SHA-256 と 800 本・21 特徴、各検査の成功。`e2_score_world.py:22` は現在も model の先頭 8 桁だけを受理条件にしている。
- U2 の meta に親 receipt と元の P/B 世界資産の manifest/hash を持たせ、export まで引き継ぐ。現在の U2 meta は U2/Q2 自身と一部コードの hash が中心で、親 receipt への接続がない。

コードの hash をジョブ終了時に可変な作業ツリーから集めるだけでは、途中でコードが変わった場合の実行版を確定できない。開始時に snapshot を固定し、各段階がその版を使ったと確認する。既に作成中の資産は、保存済み manifest と実行履歴から一致を確認できれば再利用してよい。**検証追加だけを理由に 37 世界を一律に再生成する必要はない。** ただし、古い receipt の hash を新しいコードに付け替えて一致したことにはしない。追加監査を別記録にし、一致を説明できない段階だけ作り直す。

**B. `x158_diag.py` の U1 到達は U2 から逆算しており、C3 の不変条件の検査が独立していない。** `load()` は `t = U[U.y == 1]` から in_U2 と in_U1 の両方を作る。例えば、元の B にあった真の候補が U2 の統合時に消えた場合、両方が False になり、現在の C3 検査は通ってしまう。

U1 は凍結した元の P25∪B、E25 は e2s の上位 25、U2 は U2 表から別々に再構成し、query ごとに候補集合も `U2 = P25∪E25∪B` と照合する。その上で C3 の到達一致を見る。P の基準順位も元の P と照合する。E 台帳と Q の名簿・一意性を先に検査し、欠損を許さないこと。現状の `map(L.truth_in_ewin).astype(bool)` は、台帳にない query の NaN を True にしてしまう。

段階 3 の説明にある「共通候補の順位変化」「失敗」は現状の出力に十分実装されていない。登録した集計を追加するか、未測定と明記する。E 源の外の層が無ければ、その層の結論は出せないことも出力に残す。

これらは漏洩を実データで発見したという意味ではなく、異なる世界の混入や候補の脱落を、現在の検査では排除し切れないという指摘である。

## Q2. 62 特徴の可観測性

**現在の FEATS に明示的なラベル由来の列は見当たらない。** y・truth・wclass・pi・world・fam・uid・iid・key・SMILES 自体は学習行列に入らない。人工的な P/E/B の 3 候補で、62 列が重複なし・有限値であること、y と管理列を変更しても特徴行列が完全一致することを確認した。これは featurize の確認であり、上流モデル・参照の学習履歴を保証する試験ではない。

| 特徴 | 判断と意味の固定 |
|---|---|
| f_score | 固定した P/E の順位による RRF 得点なので使用可。全 U2 行に計算され、F の候補資格がない行にも値を持ち得る。実際に F に出た証拠とは区別する。 |
| f_rank / f_rank_frac | 実際の F の出力順位。圏外は 26、特徴は 26/25=1.04。正解順位ではなく固定予測の順位なので使用可。欠損の意味を維持する。 |
| in_F_pool / f_applied | F の候補資格と適用分岐。P 空では pool も F も空、E 空では pool=P・F=P。上位 25 に残ったかとは別の旗。 |
| e2_rank_frac | E の**全窓**の n_e を分母にする順位。未採点は 1 と e_miss で区別する。U2 の候補数で割っていない点は妥当。 |
| in_B_added | `in_B and not in_P and not in_E25`。B 経由で U2 に追加されたことを表す。正解かどうかには依存しない。 |
| gen_only | `in_B and not in_P and not in_Ewin`。上の in_B_added と異なる。FH-PE の候補除外にこの列を代用しない。 |
| rep / rep_E / rep_B | P→E→B の代表選択に由来する計算・欠損の識別子。正解を見て代表を選んでいなければ使用可。E窓にはあるが E25 に入らない B 候補でも rep=E になり得る。 |

`e2_z` の標準化対象は「U2 内に残った E 採点済み候補」であり、E の全窓ではない。これも観測可能な特徴だが、その意味を仕様に書く。FH-PE では候補を制限してから相対特徴を再計算するため、PEB と数値が変わるのは意図した処理になる。

f_rank から F の予測が推測できること自体はラベル漏洩ではない。一方、source 所属・lib_sim_w・ana_ap_w の合法性は、Q1 の mask と参照の来歴の検証に依存する。列名の allowlist だけで上流の漏洩まで保証したことにはしない。

## Q3. F-world +0.01、組の下限 >0 の関門

**賛成。現在の完成候補 F を超えるかを測る新しい段階の関門として妥当。** 以前の P 対照の関門で NO だった試験を、後から成功に読み替えるものではない。Public 0.414 にローカルの +0.01 を足して次の Public を予測することもできない。

主指標は π3=0.3 の F/R 12 世界・1,198 query のまま固定する。保護は F-world に対して、π0.3 の C1/C2 と π0 の C1/C2/全件で下限 ≥−0.01。P に対する差も残す。進行条件の「親に対する差」と、採用条件の「固定 F に対する差」は混ぜない。

開発の batch-pair の区間は、独立な組が少なく、反復探索もあるため探索上の関門と読む。cU1 の退化した区間を補強材料にしない。e 開封前には、候補の source/config/seed/ensemble の全て、e 上の集計・区間・判定条件を固定する。e はこの v2 の一候補を一回だけ確認し、失敗してから次点へ切り替えて再読しない。π0 の保護を開発側で確認する方針も明示どおり維持する。

## Q4. FH-PE を後から固定ジョブで作ってよいか

**後から作り、完成・照合までは比較に使わない方針でよい。** P/F/PE をハーネスの学習実験や自動 ensemble に混ぜないこと、PE の資格を `in_P or in_E25` にして非資格の枠を提出対象外にすることは正しい。

ただし、現在の `refs/fhpe_ref.py` を固定するだけでは十分ではない。このスクリプトは実行時の可変な `src/adapter.py` を import し、その時点の TUNABLE を使い、rounds は 300 に固定する。ハーネスの実験は config で params/rounds を変えられるため、後日の PE がどの PEB と同条件なのか定まらない。`aux_reader.pe_reference()` も、保存された adapter/config/data_manifest 等の来歴を対応先に照合していない。

今回の「G0 後に seed 11 で一回」に最も素直なのは、**G0 時点の adapter と設定を snapshot にして、初期 FH-PEB の seed 11 と対応する固定 PE を作る**こと。その二者の差を、候補資格を変えた比較として読む。後で最適化した PEB とこの初期 PE の差は、学習設定の改善も含むので「生成物を許した純粋な増分」とは呼ばない。最終候補に対応する増分が必要になった場合は、結果を見る前に別途その候補の snapshot/config/seed に対応する PE を登録する。

manifest と reader は、現在の可変な adapter ではなく、この登録済み snapshot・設定・seed・名簿・data_manifest・test_slots・予測 hash に結び付ける。PE の有限値、非資格枠が PAD、資格のある実在枠が全て採点済みという契約も確認する。候補集合を制限しても Q の B 件数などは残るため、この比較は「B 由来の追加候補を出せる効果」を含む比較であり、「生成計算や B の情報を一切使わない系」とは区別する。

実行上の修正も一つある。モデルを `reports/refs/.fhpe_s11_fold0.txt` に保存してから、最後に `os.makedirs(out)` している。確認時点で `reports/refs` は存在しなかった。学習の前に出力親ディレクトリを用意し、no-overwrite と途中失敗の扱いを決める。費用は固定対照ジョブとして別途記録し、参照という名目で seed や設定を繰り返し選ばない。

## Q5. データ完成後、G0 前に必要な確認

下記を性能を開かない技術検査として残せばよい。

1. **資産の受領**: 37 世界の期待集合と receipt を Q1 の条件で確認し、未完了・別版・混入を拒否する。実行コードと各親資産から U2、export、data_manifest、validation/test_slots までの hash の接続を保存する。
2. **世界と候補**: 全 query の zlog 許容差、mask 後の源・代表・実際の参照・analog を確認する。独立な P25/E25/B との集合一致、C3 の U1/U2 一致、各旗の定義式、E の全順位と n_e、最大 100 枠・一意 key・有限値を確認する。ゼロ候補 query も名簿から落とさない。
3. **P/F の順序の往復**: 元の固定 P と fuse_rrf の F が、U2→export→100 枠→補助 reader で全く同じ順序になることを確認する。現在の cv の「F が U2 の部分集合」だけでは順序や順位の誤りは検出できない。F の重複なし・長さ ≤25、f_rank / f_applied / in_F_pool との整合、P空/E空、同点、P∩E、E∩B の同一/別 SMILES を含む小さな人工例も使う。
4. **学習境界**: 開発 31 世界・3,095 単位、主 1,198、7 fold、特徴だけの test 596 という名簿を確認する。truth/iid が fold を跨がないこと、全行の y の定義、管理列が FEATS に入らないこと、test にラベル・対応表・F の参照リストがないこと、salt/対応表がワークスペース外にあることを確認する。e の性能は出さない。
5. **予測の契約と凍結**: PEB は全ての実在枠を確率で採点し、PAD は余白だけ。7 fold の test を同一枠・同一資格で平均する。PE は別参照のままにする。reader の hash/名簿/shape の拒否条件を人工ファイルで確認し、設定・コード・検査ログを G0 の材料に含める。現段階で追加のモデル学習は検査のために不要。

細部として、analog の比較は `np.allclose(..., atol=1e-9)` だけで rtol を省略しており、絶対誤差 1e-9 の検査ではない。P 側の保存時の丸めと E 側の生値をどう比較するかを固定する。同じ桁に丸めて照合するか、rtol/atol を両方明記し、キー列の一致と値の許容差を分けて記録する。

`g0_spec.md` はまだ完了していない全件の zlog/analog 検査を完了形で書いているので、完了ログを得るまでは「G0 前の必須条件」とする。また、学習設定や lane の数え方を可変な v1 の仕様に依存させず、必要な規則を v2 に転記するか、参照する v1 仕様の snapshot/hash を固定する。D6 の利用者端末での補助 reader、D7 の Judge のモデル分離と呼出上限は改訂どおりでよい。
