**Q2：T一本ではpool内の寄与を分解できない。補集合を一緒に測る。**

T=train、B=COCONUTかつ非train、P=そのどちらでもない候補、K=T∪Bとする。所属は023bで固定した「そのrunの候補出典」で、T/Bを公式C1/C2と同一視しない。

元出力について`M=M_T+M_B+M_P`。T probeは`P_T=M_T+G_T`だが、G_TにはPcを除く利得に加えてBを除く利得も入る。pool出力のT真値からの寄与をQ_T、B真値からの寄与をQ_Bとすれば、

`P_K=Q_T+Q_B`、`P_T=Q_T+H_T`、`H_T≥0`

従って`P_K−P_T=Q_B−H_T`であり、COCONUT-only寄与そのものではない。T probeまでで得られる安全な一般的範囲は、

`max(0, M+P_T−1) ≤ M_T ≤ min(P_T, P_K, M)`

今回なら`max(0, P_T−0.646) ≤ M_T ≤ min(P_T, 0.336)`。通常は下限0で弱い。B側の元寄与には`M_B ≥ max(0, 0.308−P_T)`が付くので、Tが低ければ情報になるが、TがMに近いだけでは「元の得点の大半がT」とは言えない。

**B-onlyも出すと、既存pool/Pcを生かして次が測れる。**

- `P_T+P_B−P_K`：すでにPcを除いたpool内で、T/Bの所属を完全に選ぶことによる追加回収量。
- `P_T+P_B+P_P`：三群それぞれの内部順位を固定した所属oracleの得点。
- `max(0, M−P_B−P_P) ≤ M_T ≤ min(P_T,P_K,M)`。今回の下限は`max(0,0.308−P_B)`。

`b1_probe027/b1_pipeline.py`には既に`coconut = not in_train and in_coconut`の出力があるので、追加するのは**COCONUT全部ではなく既存のprobe_coconut**である。T/B二本は同じレシピで先に固定し、一方のPublicを見て他方の順位を変更しない。

順位帯probeの測定量も、次のように固定する。真の元順位をr、bandの得点をP_26とすると、

`P_26 = mean(1[26≤r≤50] / (r−25))`

これは「26〜50位に真がある割合」ではなく、その帯を1〜25位へ繰り上げたMRRである。その割合qについては`P_26≤q≤min(25*P_26,1)`という幅しか付かない。**P_26=0.01でも、真の25%が元50位にある例と両立する。** また51位以降に真がある場合は全て0になるので、低い値から候補未到達やclass3が主因とは結論できない。

元top25と帯の正解identityが互斥なら、二つの固定リストを分子ごとに完全選択したoracleは`M+P_26`。P_26はそのoracleの追加得点であって、そのまま実装で獲得できる利得ではない。

**Q3：較正の予測失敗を能力の上限にせず、まず測定の欠落を直す。**

`calib_public2.py`を確認したところ、重要な制約がコードに入っていた。

欠落の候補として「基準版で0だった分子の救済」は妥当だが、Publicの利得の原因として確定していない。実データから次を確認した。

次の手法仮説は、以下の順を推奨する。

1. **同じFPNet・候補・forwardで、pool内の順位付けを改善できるか。** 候補ごとのFP正例露出とFP/GL/参照の関係を較正するranker、またはE0のpool内順位付けの部品を自前のfitだけで学習した版を、一つの対照実験にする。E0の全train学習済みrankerをそのまま持ち込んだC2比較は未見性能の検証にならない。単に全Pcを下げる案は既に診断範囲が限られている。
2. **候補を追加する必要があるなら、救済と順位損失を分離する。** まず既存の候補・順位台帳で層別の到達損失を確定する。k60の全体差だけで判断せず、同一FP条件で新規到達の得点と既存到達分子の差を測る。実採用するcheckpointで確認する。
3. **負例poolの影響は、測定条件の問題と手法改善を分けて対照実験にする。** 以下の監査を済ませてからFPNet再学習へ進む。全COCONUTを一度に除く変更を最初の実験にはしない。

負例について、`Data.negatives()`がsplitで絞らない質量窓から候補を引くこと、rank lossが候補FPと予測logitの内積に対するcross entropyであることは確認した。従って「正例として未見」と「負例候補集合にも無い」は異なる条件であり、hidden Pcを模す評価に重要である。

ただし**poolに入っていることと実際にサンプルされたことは別**で、約1,900回は総draw数をpool全体で割った平均にすぎない。質量・正例分布・窓密度で頻度は大きく変わる。さらに、別queryの負例として使うことは、その構造を全queryで誤答と教えることではない。適切な識別を学ばせる利益もあり、効果の符号はコードからは決まらない。「Pc代理は必ず厳しい」や「COCONUTを除けば改善する」とはまだ言えない。現診断でもCOCONUT真のFP-only平均はfull_rk/full_evalで改善し、悪化はC層に偏っている。

最初の対照は、**正例学習から除外した固定identity群を、負例samplerにも入れる／入れない**の比較とする。正例・初期化・更新数・augmentation・負例数・質量窓の難しさを揃え、正例サンプリングと負例サンプリングの乱数を分ける。同じseedだけでは、負例抽出の変更が後続の正例抽出まで変える可能性がある。負例への包含・期待頻度・可能なら実drawを記録し、正例未見/負例候補内と、正例未見/負例候補外を分けてFP順位・到達・最終RRを測る。

これはまず、現在のC2代理と隠しPc側の条件差の大きさを測る実験である。hidden COCONUTの真が負例poolにあることは実運用で自然なので、評価条件を直すための除外と、製品版の負例poolを広く削る判断は分ける。公開系譜でも同じsamplerを使うなら、その存在だけでE0とB1の差を説明することもできない。

どの仮説でも、同じ土台内の差に加えてM2xからの変更全体の保護条件を維持する。新ranker二版とw=2〜4を提出しない根拠は、その条件未達であり、較正が小さい利得しか予測しないことではない。
